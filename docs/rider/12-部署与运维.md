# 部署与运维

本文描述 A12 提供的可复现构建、不可变发布、N-1 回滚、深度 readiness、CI 和门店打印代理。数据库备份业务内容与 `BackupService` 内部实现属于 A7，不在本文修改范围；本文只操作标准 `mysqldump` 和隔离恢复库。

## 1. 生产边界

- 公网入口只允许 HTTPS。管理后台、API、小程序和门店打印代理均不得使用生产 HTTP。
- 唯一的 HTTP 例外是机器内部回环通信：Nginx 到 `127.0.0.1:8080`，以及打印代理本机开发时的 `localhost`/回环地址。
- 后端只绑定 `127.0.0.1`，不能直接暴露 8080。
- 服务器、JVM、数据库连接统一使用 `Asia/Shanghai`。
- PM2 只运行一个后端实例。当前应用没有跨进程锁，禁止 cluster/多实例。
- 发布物不可变：每个版本一个目录，旧 jar、旧 dist 和 N-1 目录不得覆盖。

## 2. 版本化拓扑

```text
/opt/yulin-youxian/
├── releases/
│   ├── 2026.08.12-1/
│   │   ├── server/fresh-delivery-server.jar
│   │   ├── admin/dist/
│   │   ├── ops/
│   │   ├── VERSION
│   │   ├── BUILD-METADATA
│   │   └── SHA256SUMS
│   └── 2026.08.05-1/
├── current  -> releases/2026.08.12-1
└── previous -> releases/2026.08.05-1

/var/lib/yulin-youxian/
└── data/                 # 稳定数据目录，不在 release 内

/var/log/yulin-youxian/   # PM2 日志
/etc/yulin-youxian/server.env
```

`deploy/pm2/ecosystem.config.cjs` 明确：

- `instances: 1`、`exec_mode: fork`；
- `cwd=/var/lib/yulin-youxian`，使仍使用相对 `data/...` 的旧代码落到稳定数据盘；
- jar 使用 `/opt/yulin-youxian/current/...` 绝对路径；
- profile、storefront、printing、backup、delivery upload 全部使用绝对数据路径；
- `TZ=Asia/Shanghai`、`-Duser.timezone=Asia/Shanghai`；
- `--server.address=127.0.0.1`。

上线脚本固定执行：

```bash
pm2 startOrReload /opt/yulin-youxian/current/ops/pm2/ecosystem.config.cjs --update-env
pm2 save
```

因此环境变量变更不会继续沿用 PM2 daemon 的旧值，机器重启后也恢复同一进程清单。

## 3. 固定工具链和环境

版本唯一来源是 `deploy/versions.env`：

- Java 17；
- Node 22.14.0；
- npm 10.9.2（随 Node 22.14.0 固定发布）；
- Flyway 与业务表基线以 `deploy/versions.env` 里的
  `EXPECTED_FLYWAY_VERSION` / `EXPECTED_BUSINESS_TABLES` 为准（当前 V20、40 张），
  `check_release_contract.py` 会强制三方一致。

后台发布构建只认 `art-lnb-master/package-lock.json`：

```bash
npm ci
```

不允许 CI 或发布机自动更新 lockfile。`build-release.sh` 会拒绝错误 Node/npm/Java 版本、缺失 lockfile、脏工作区和已存在的版本号。临时本地演练可以显式设置 `ALLOW_DIRTY_BUILD=1`，正式发布禁止。

Go-live 还会读取 release 内的 `ops/versions.env`，再次检查服务器 PM2 所用 Node 与 `/usr/bin/java` 版本；版本不符时会在停服务和备份之前失败。

生产配置：

```bash
install -d -m 0755 /etc/yulin-youxian
cp deploy/env/server.env.example /etc/yulin-youxian/server.env
chmod 600 /etc/yulin-youxian/server.env
# 编辑并替换全部 __REQUIRED__
bash deploy/scripts/validate-env.sh /etc/yulin-youxian/server.env
```

部署校验会在以下情况失败：

- `TZ` 不是 `Asia/Shanghai`；
- 路径不是绝对路径；
- MySQL、TLS、管理员密码缺失；
- 管理员密码仍是默认/弱密码或少于 12 字符；
- JDBC URL 没有 `serverTimezone=Asia/Shanghai`；
- 对外通知 URL 不是 HTTPS；
- TLS 文件不可读。

业务层“生产环境默认管理员密码缺失即拒绝启动”由 A1 实现；A12 的脚本是部署前第二道门，不能替代业务启动检查。

## 4. 构建发布物

在干净提交上执行：

```bash
bash deploy/scripts/build-release.sh 2026.08.12-1
```

输出：

```text
deploy/out/2026.08.12-1/
deploy/out/yulin-youxian-2026.08.12-1.tar.gz
deploy/out/yulin-youxian-2026.08.12-1.tar.gz.sha256
```

构建过程：

1. Maven wrapper 在独立 staging target 中构建 jar，不复用旧 `server/target`。
2. npm 按 `package-lock.json` 执行 `npm ci`，Vite 直接输出到 staging，不覆盖源码目录现有 `dist`。
   先 `vite build` 再 `vue-tsc --noEmit`：`ref`、`ElMessage` 这些全局符号的类型声明由
   unplugin-auto-import 在构建时生成且不入库，先跑类型检查会在全新 clone 上误报几百条。
3. PM2、Nginx、readiness、回滚脚本随 release 一起版本化。
4. 使用 Git 提交时间作为 `SOURCE_DATE_EPOCH`。
5. 目录内生成逐文件 `SHA256SUMS`。
6. tar 固定顺序、mtime、owner/group，gzip 关闭时间戳，便于同提交同工具链复现。
7. 版本目录或 tarball 已存在时直接失败，绝不覆盖。

### 连骑手端 APK 一起打（不是 OTA）

`build-release.sh RIDER_APK=1` 只把签名 APK 打进服务器发布 tarball，**不会**登记
`/api/public/rider/app/latest`，也不是正式骑手发布入口。正式发布见第 14 节
`scripts/rider-publish.sh`。

要出「后端 + 后台 + 骑手端」的完整包，在装了 Android SDK 且配好签名的机器上执行：

```bash
export ANDROID_HOME=/opt/android-sdk
RIDER_APK=1 RIDER_ABI=arm64 \
  bash deploy/scripts/build-release.sh 2026.08.12-1
```

- `RIDER_APK=1` 打开这一段。前置条件（Gradle wrapper、`rider-android/gradle.properties`、
  `ANDROID_HOME`）缺任何一项都直接失败，不会悄悄跳过 —— 半个包比没有包更危险。
- `RIDER_ABI=arm64` 只打 64 位，包体从约 100 MB 降到约 71 MB；不设则同时打
  `arm64-v8a` 与 `armeabi-v7a`，兜住极少数 32 位老机。
- 签名材料读工作区外的 `~/.yulin/rider-signing.properties`（Windows 为
  `%USERPROFILE%\.yulin\`）或同名环境变量。缺项时 Gradle 在配置阶段就失败，
  不会产出未签名包。
- 这一段会先跑 `testDebugUnitTest` 与 `lintDebug`，再 `assembleRelease`，
  最后用 `verifyReleaseSignature` 校验签名。
- APK 落在 release 目录的 `rider/yulin-rider-<version>.apk`，一并计入 `SHA256SUMS`。
  `BUILD-METADATA` 里的 `rider_apk=0|1` 记录本次是否包含。

传到服务器后先检查 tarball 的 `.sha256`，解压后再检查目录内 manifest。

## 5. Go-live 演练与上线

只做检查、不改进程/数据库/符号链接：

```bash
bash deploy/scripts/go-live.sh --preflight \
  /srv/releases/2026.08.12-1 \
  /etc/yulin-youxian/server.env
```

预演会验证 env、TLS 文件、数据库登录、版本未安装和 release SHA256。

正式上线：

```bash
bash deploy/scripts/go-live.sh \
  /srv/releases/2026.08.12-1 \
  /etc/yulin-youxian/server.env
```

脚本按以下顺序执行：

1. 停止已有 PM2 进程；
2. 用 `mysqldump` 生成 `pre-deploy-<version>-<time>.sql.gz`；
3. 执行 gzip 完整性检查和 SHA256；
4. 把 release 复制到新的、只读的版本目录；
5. `previous` 保存旧 current，原子切换 `current`；
6. `pm2 startOrReload ... --update-env`、`pm2 save`；
7. 渲染 Nginx，`nginx -t` 成功后 reload；
8. 重试深度 readiness，最长约 3 分钟。

备份失败时不会继续切换。readiness 失败时保留现场，不会擅自做数据库恢复；按第 7 节回滚 N-1。

## 6. Readiness 不是 ping

`deploy/scripts/readiness.sh` 必须全部通过：

1. `current` 必须是受管 release 符号链接；
2. jar、admin `index.html`、`SHA256SUMS` 存在；
3. 当前 release 的每个文件 SHA256 正确；
4. MySQL 可执行真实查询；
5. `flyway_schema_history` 无失败项，基线版本成功且最高版本与 `versions.env` 一致；
6. 业务表张数与 `versions.env` 一致，且预期表名逐一存在；
7. data、uploads、backup 目录真实可创建并删除探针文件；
8. 数据盘可用空间不低于 `MIN_FREE_MB`；
9. 最新 `backup-*.zip` 或 `pre-deploy-*.sql(.gz)` 不超过允许年龄；
10. 最后才检查回环 Actuator 返回 `UP`。

数据库判据位于 `server/scripts/readiness.sql`。V10 新增 7 张抽奖表，V11 新增 `auth_session`，V13 新增 `marketing_lottery_draw_guard`，V14 新增 `delivery_route_plan_failure`，合计 38 张业务表；V15 只给 `delivery_wave` 加列和索引，不新建表，张数不变；`flyway_schema_history` 不计入业务表。

单独执行：

```bash
bash /opt/yulin-youxian/current/ops/scripts/readiness.sh \
  /etc/yulin-youxian/server.env
```

不要用 `/api/ping` 代替它。ping 正常不能证明 Flyway、业务表、存储或备份可用。

## 7. N-1 回滚

先演练：

```bash
bash deploy/scripts/rollback.sh --check /etc/yulin-youxian/server.env
```

它会验证 current 与 previous 指向不同受管版本，校验两个版本的 manifest，并确认服务器 Node/Java 满足 N-1 元数据，不做切换。

正式回滚：

```bash
bash /opt/yulin-youxian/current/ops/scripts/rollback.sh \
  /etc/yulin-youxian/server.env
```

脚本交换 `current`/`previous`，重新执行 PM2 `startOrReload --update-env`、`pm2 save`、Nginx reload 和 readiness。它不复制旧 jar/dist，也不删除失败版本。

代码回滚不回退 Flyway DDL。N-1 必须与当前基线 schema 向后兼容；禁止自动 `DROP TABLE`。如果 N-1 readiness 也失败，停止操作并升级处理。

## 8. 隔离恢复演练

恢复脚本只接受标准 `.sql` 或 `.sql.gz`，只创建 `restore_drill_*` 隔离库，不调用或修改 `BackupService`。

```bash
export MYSQL_ADMIN_USER=root
export MYSQL_ADMIN_PASSWORD='从密码管理器临时读取'
bash deploy/scripts/restore-drill.sh \
  /var/lib/yulin-youxian/data/backups/pre-deploy-2026.08.12-1-20260812-030000.sql.gz \
  /etc/yulin-youxian/server.env
unset MYSQL_ADMIN_PASSWORD
```

步骤：

1. 强制要求相邻 `.sha256` 并先校验；
2. 创建随机隔离库；
3. 导入备份；
4. 用同一 readiness SQL 验证 Flyway 基线与业务表张数；
5. 成功后删除隔离库。

设置 `KEEP_DRILL_DB=1` 才会保留隔离库供人工核对。脚本生成的库名不可能等于生产库名。

## 9. Nginx 与 SSE

`deploy/nginx/yulin-youxian.conf.template`：

- 80 端口只重定向到 HTTPS；
- TLS 仅允许 1.2/1.3；
- `/api/admin/delivery/board/stream` 单独关闭 `proxy_buffering`、`proxy_request_buffering`、cache 和 gzip；
- SSE 响应增加 `X-Accel-Buffering: no`，读写超时为 1 小时；
- 其他 API 和上传只代理到 `127.0.0.1`；
- admin root 始终指向 `current/admin/dist`。

验收：

```bash
curl -N -I https://正式域名/api/admin/delivery/board/stream
```

必须看到 `X-Accel-Buffering: no`。还要在调度台保持连接 10 分钟，确认事件实时到达而不是成批出现。

## 10. 打印代理

打印代理 1.2.1 的生产约束：

- 正式 API 非 HTTPS 直接拒绝；只有 localhost/回环开发地址允许 HTTP；
- AccessKey 使用 DPAPI `CurrentUser` 加密，旧版明文配置首次读取后自动迁移；
- TLS 只启用 1.2；
- 业务日志 5 MB 轮转、保留 5 份；监督日志 2 MB 轮转、保留 5 份；
- `supervise-agent.ps1` 监督异常退出，5–60 秒退避重启；
- 任务计划程序再配置失败重启，并绑定配置密钥的同一 Windows 用户；
- 构建后规范化旧 C# 编译器的 PE 时间戳、MVID 和私有实现 GUID，已验证同源码连续构建 EXE SHA256 一致；
- `build.ps1` 生成 `SHA256SUMS.txt` 和 `VERSION.txt`；
- 安装前必须运行 `verify-checksums.ps1`。

详细操作见 `print-agent/使用说明.md`。禁止向技术支持发送 `agent.config.json`；日志中不记录密钥。

## 11. GitHub CI

`.github/workflows/ci.yml` 包含：

- 后端：Java 17 + Maven wrapper 全量测试；
- admin：固定 Node/npm，`npm ci` 冻结 lockfile，类型检查和 Vite build；
- Android：`testDebugUnitTest` + `assembleDebug` 始终必须成功并上传 debug APK；普通 CI **不再**检测签名 Secrets、不打 release、不跑 `apksigner`；
- 小程序：Node 逐个执行 `--check`；
- 打印代理：Windows 连续构建两次并逐文件比对 SHA256，通过后才上传产物；
- 运维模板：Bash/PM2 语法检查（含 `scripts/rider-publish.sh`），并断言迁移版本与业务表张数和 `versions.env` 一致；
- secret scan：检查 tracked runtime 文件、ZIP/TAR 成员和 Git 历史。

正式私钥只留在生产机仓库外目录，不进 GitHub Actions。

## 12. Runtime 文件与历史归档

组件内 `.gitignore` 已覆盖 PID、dump、token、keystore、打印配置和轮转日志。CI 还会阻止这些文件被强制加入 Git。

仓库已有 7 个 tracked ZIP，详见 `deploy/security/tracked-archive-report.md`。扫描未发现强特征密钥，但这些文件不能安全自动删除：

- 它们可能是客户交付物、设计源或供应商 SDK；
- 删除当前文件不等于清除 Git 历史；
- 真正发现密钥时必须先撤销，再由仓库管理员协调历史重写和重新克隆。

## 13. 共享文件待主控处理

A12 未越界修改以下 shared/business build 文件：

1. 根 `.gitignore`：建议主控合并 `*.dmp`、`*.dump`、`*.dumpstream`、`*.token`、`token.*`、`**/runtime/`；当前已有 PID、ZIP、Android keystore 忽略。
2. `art-lnb-master/package.json` / lockfiles：建议主控增加 `"packageManager": "npm@10.9.2"`，并决定移除重复的 `pnpm-lock.yaml` 与缺少 `packages` 字段、在现代 pnpm 下直接报错的 `pnpm-workspace.yaml`；A12 已在 CI/发布脚本统一使用 `package-lock.json`。
3. `rider-android/app/build.gradle.kts`：缺少签名材料时 `assembleRelease` 在配置阶段失败，不会产出未签名包。正式发布走本机 `scripts/rider-publish.sh`。
4. `server/src/main/resources/application.yml` / A1 启动检查：必须移除生产默认管理员密码回退或在 production profile 启动时拒绝；A12 只做部署前检查。

## 14. 骑手 APK 本机直发

正式骑手包在生产机上用一条命令发布，不再打 `rider-v*` 标签，普通 CI 也不再接触正式私钥。

```bash
bash scripts/rider-publish.sh --dry-run
bash scripts/rider-publish.sh --title "更新标题" --notes "更新日志"
```

流程：检查已跟踪文件是否干净 → 按 `Asia/Shanghai` 计算 `versionCode=YYMMDDNN` /
`versionName=YYYY.MM.DD.N` → Android 单测与 `verifyReleaseSignature` →
`aapt2` / `apksigner` / SHA-256 验包 → `POST http://127.0.0.1:8090/api/internal/rider-app/releases`
（operator=`server-local`）→ 核对公开 latest、下载、Range 和哈希。任一步失败都不更新已发布指针。

密钥与证书摘要在仓库外 `/root/.yulin/`（`0600`）。用
`scripts/rider-publish.sh --sync-pm2-env` 注入当前 PM2 并 `pm2 save`，不要写进
`deploy/pm2/ecosystem.config.cjs`。

高德 Android Key 必须绑定新证书 SHA-1（见 `/root/.yulin/AMAP-KEY-SETUP.txt`），用
`scripts/rider-configure-amap-key.sh` 写入环境文件后再发首包。

**新签名迁移**：2026-08 起使用新 keystore。旧签名包无法被新包覆盖，现有骑手须卸载旧版并手工安装一次；之后走 OTA。坏包可停用并切回同一新签名体系内的上一版，不能 OTA 回退到旧签名。

`--policy FORCE` 会阻断所有更旧客户端，只在安全修复等必须场景使用。

Windows `scripts/rider-ship.ps1` 只作应急出包，版本规则与本机脚本对齐，不登记 OTA。
`build-release.sh RIDER_APK=1` 同样不登记 OTA。

加密离线备份在 `/root/.yulin/backups/`，口令与 keystore 分开放。丢失任一样就无法再给已装机用户发覆盖更新。

上线逐项签字使用 `deploy/RELEASE_CHECKLIST.md`。
