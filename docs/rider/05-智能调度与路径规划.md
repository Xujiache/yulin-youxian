# 智能调度与路径规划

## 0. 设计哲学

美团技术团队在公开论文里说过一句关键的话：**他们没有从数据里学出派单的目标函数，而是人工写死了目标函数的结构，只用仿真和线上数据拟合参数。** 理由是标注数据不足、且不能假定调度员的决策是最优的。

美团那个体量都做不到，单门店更做不到。所以本项目的原则是：

1. **目标函数手写，权重可调。** 全部权重进 `delivery_config`，调度员在后台就能改，不用发版。
2. **每一层都有零依赖的兜底实现。** 没有高德 Key 也能跑完整流程，只是精度下降。
3. **可解释性优先于最优性。** 每次派单都要能回答「为什么派给他」，`dispatch_score` 的分项 breakdown 要能在后台看到。调度员不信任黑盒就会绕过系统打电话，那系统就白做了。
4. **规模很小，不要过度工程。** 10 个骑手 × 每人 8 单，暴力枚举 + 局部搜索在微秒级就能出结果。不需要 OR-Tools 的重型武器（但接口留好，未来能换）。

## 1. 调度主循环

`DispatchScheduler` 每 `dispatch.loop_interval_seconds`（默认 5 秒）跑一次：

```
1. 回收过期压单        —— hold_until_at 已过的 PENDING 任务进入候选池
2. 拉取候选任务        —— status=PENDING 且 hold_until_at 已过或为空
3. 若候选池为空 → 结束
4. 合单聚类            —— 把候选任务聚成若干「任务簇」
5. 对每个簇：
     a. 计算所有可用骑手的得分
     b. 选出最高分骑手（得分低于阈值则跳过，等下一轮）
     c. 创建或追加波次
     d. 触发路径规划
     e. 写任务/波次/事件，推送骑手
6. 在途风险扫描        —— 评估 DELIVERING 任务的超时风险，必要时触发改派
7. 运力预警            —— 积压/在岗数异常时写调度台告警
```

整个循环是单实例的 `@Scheduled`，与现有架构一致（现有系统本来就是单实例强绑定）。为防止循环重入，用 `ReentrantLock.tryLock()`，拿不到锁就跳过本轮。

## 2. 压单（Holding）

**为什么要压单**：任务一生成就立刻派出去，会错过 30 秒后到达的同小区订单，导致骑手跑两趟。多等一会儿，能显著提高合单率。

**为什么不能压太久**：顾客在等，压单直接吃掉承诺时间。

```java
holdUntil = pickedReadyAt + holdWindowSeconds
```

动态收缩规则（`HoldingWindowService`）：

| 条件 | 压单时长 |
| --- | --- |
| 默认 | `dispatch.hold_window_seconds`（120 秒） |
| 时间窗剩余 < 30 分钟 | 30 秒 |
| 时间窗剩余 < 15 分钟 或已超时 | 0（立即派） |
| 冷链等级 = FROZEN | 减半 |
| 当前无可用骑手 | 继续等待（不算压单，算积压） |
| 待派积压 ≥ 骑手数 × 2 | 0（运力紧张时不要再等了） |

压单期间任务在调度台的「待派积压」队列里可见，并显示倒计时。调度员可以手动点「立即派单」跳过压单。

## 3. 合单（Batching）

目标：把地理邻近、时间窗兼容、可以由同一个骑手一趟送完的任务打包。

### 聚类算法

用**基于楼栋 groupKey 的分层聚类**，而不是纯几何聚类。理由：现有 `DeliveryAddressIntelligence` 已经能把地址解析成 `area / building / unit / floor / room`，中文小区的地理邻近性在文本上比在坐标上更可靠（坐标常常是小区大门，几十户人家共享同一个点）。

```
第一层：完全同门牌（exactAddressKey 相同）
        —— 强制合并，绝不拆散。同一个门送两趟是最蠢的浪费
第二层：同楼栋（groupKey 相同）
        —— 强制合并
第三层：同小区（areaLabel 相同）
        —— 优先合并，受簇容量约束
第四层：地理邻近（簇质心距离 < batching_radius_meters，默认 500 m）
        —— 合并，受时间窗兼容性约束
```

### 簇的约束（任一超限则**不再加入新任务**，另起一簇）

| 约束 | 配置项 | 默认 |
| --- | --- | --- |
| 任务数 | `dispatch.max_tasks_per_wave` | 8 |
| 总重量 | 骑手 `capacity_weight_kg` | 30 kg |
| 预估总里程 | `dispatch.max_wave_distance_meters` | 8000 m |
| 预估总时长 | `dispatch.max_wave_duration_seconds` | 3600 s |
| 时间窗兼容 | 见下 | —— |

> **【关键规则】这些约束只用于决定「要不要往簇里再加一单」，绝不用于拒绝配送任何订单。**
>
> **单任务波次豁免全部里程与时长上限。** 一个 15 km 的远单，其单单波次里程 30 km，
> 远超 `max_wave_distance_meters`，但它**必须**被派出去，只是它自己独占一个波次。
>
> 实现上：`if (cluster.size() == 1) 跳过里程与时长校验`。
> 漏掉这一条会导致远单永远卡在待派队列里，这是本模块最容易写出的 bug。

### 时间窗兼容性

两个任务能合并，当且仅当存在一个配送顺序，使**两者都不超时**。简化判定：

```
兼容(A, B) ⟺ min(A.promisedAt, B.promisedAt)
             ≥ now + pickupSeconds + travel(store→近点) + handoff + travel(近点→远点) + handoff
```

冷链额外约束：**FROZEN 任务不能被安排在预计出箱时长超过 `40 分钟` 的位置**。这条在合单阶段做粗筛，在路径规划阶段做精算。

## 4. 派单评分（核心）

对簇 `C` 和骑手 `r`，计算综合得分。**得分越高越优先**，取值归一到 `[0, 1]`。

```
score(C, r) = w₁·f_顺路(C,r) + w₂·f_超时(C,r) + w₃·f_负载(r) + w₄·f_冷链(C,r) + w₅·f_等级(r)
```

权重全部来自 `delivery_config`，默认：

| 分项 | 权重键 | 默认 |
| --- | --- | --- |
| 顺路度 | `dispatch.weight_added_distance` | 0.35 |
| 超时风险 | `dispatch.weight_overtime_risk` | 0.30 |
| 负载均衡 | `dispatch.weight_load_balance` | 0.15 |
| 冷链适配 | `dispatch.weight_cold_chain` | 0.15 |
| 骑手等级 | `dispatch.weight_rider_level` | 0.05 |

### 4.1 顺路度 f_顺路

美团公开的定义就是**新增距离（marginal added distance）**：新增距离越小，顺路度越高。

```
addedDistance = optimalDistance(r.currentTasks ∪ C) − optimalDistance(r.currentTasks)

f_顺路 = 1 / (1 + addedDistance / 1000)      // 1 km 新增距离 → 0.5 分
```

骑手当前空闲时 `optimalDistance(∅) = 0`，此时 `addedDistance` 就是这一趟的完整里程，这是合理的——空闲骑手接一个远单确实成本高。

注意这里需要跑两次路径规划（加入前 / 加入后）。规模很小，代价可接受，且矩阵有缓存。

### 4.2 超时风险 f_超时

派给这个骑手后，**簇内新任务和骑手已有任务**的最小剩余富余时间。

```
for each task in (r.currentTasks ∪ C):
    slack(task) = task.promisedAt − predictedArrival(task)
minSlack = min over all tasks

f_超时 = clamp(minSlack / 1800, 0, 1)        // 30 分钟富余 → 满分
```

**任何一个任务的 `slack < 0`（即会导致超时）时，`f_超时 = 0`，并且整个候选被标记为 `blockers: ["WOULD_CAUSE_OVERTIME"]`。** 不是硬性排除（运力紧张时可能所有骑手都会超时，总得选一个），但会在调度台明确提示。

**「刻意留出富余时间」是美团公开算法里明确写的原则**，本项目照做。

### 4.3 负载均衡 f_负载

```
loadRatio = max(currentTaskCount / maxConcurrentTask,
                currentWeightKg  / capacityWeightKg)

f_负载 = 1 − loadRatio
```

`loadRatio ≥ 1` 时该骑手被**硬性排除**（返回 `1021`）。

### 4.4 冷链适配 f_冷链（本项目独有）

这是通用配送算法里没有、但生鲜必须有的一项。

每个任务有 `coldChainLevel`，对应一个**最大可接受出箱时长**：

| 等级 | 最大出箱时长 | 说明 |
| --- | --- | --- |
| `NORMAL` | 无限制 | 常温 |
| `CHILLED` | 60 分钟 | 冷藏（叶菜、鲜肉、乳品） |
| `FROZEN` | 40 分钟 | 冷冻（冻虾、汤圆、冰品） |

```
for each task in (r.currentTasks ∪ C) where coldChainLevel ≠ NORMAL:
    exposure(task) = predictedArrival(task) − now      // 出保温箱到送达的时长
    ratio(task)    = exposure(task) / maxExposure(task.coldChainLevel)

f_冷链 = 1 − clamp(max(ratio), 0, 1)
```

`ratio > 1`（即冻品可能化）时 `f_冷链 = 0` 且标记 `warnings: ["COLD_CHAIN_RISK"]`。

> **注意这是警告不是阻断。** 一个 12 km 外的冻品单，无论派给谁都会超出 40 分钟出箱时长，
> 但订单还是要送。系统的正确反应是：把它标为冷链风险、**强制排为该波次第一站**、
> 在调度台高亮提示（建议加冰袋/加保温箱），而不是拒绝派单。
>
> 冷链约束影响的是**顺序和提示**，不是**是否配送**。

**这一项还会反过来影响路径规划**：见 §5.4 的目标函数惩罚项。

### 4.5 骑手等级 f_等级

```
f_等级 = normalize(serviceScore, 60, 120)     // 服务分归一化
```

新手保护（`probation = true`）：
- `maxConcurrentTask` 强制降为 `dispatch.probation_max_tasks`（默认 3）
- 只参与**总里程 < 2 km** 的簇的竞争
- `f_等级` 不因新手而扣分（不能让新手永远接不到单）

### 4.6 硬性排除条件（**排除的是骑手，不是订单**）

先说清楚这一点：下表排除的是**候选骑手**，含义是「这一轮不派给他」。**任何情况下都不会因为这些条件而拒绝配送一个订单**——所有骑手都被排除时，任务留在 `PENDING` 队列等下一轮，同时触发运力预警，绝不丢弃。

| 条件 | 错误码 |
| --- | --- |
| `work_status ≠ ON_DUTY` | —— |
| `account_status ≠ ACTIVE` | `1002` |
| `dispatch_paused_until > now`（疲劳停派） | `1022` |
| `loadRatio ≥ 1` | `1021` |
| 位置数据陈旧超过 `liveness_timeout_seconds` | 掉线，不参与派单 |
| 骑手车型运力不足（如簇总重超 `capacity_weight_kg`） | —— |

**疲劳停派是硬门禁，`force=true` 的手动派单也不能绕过**，这是 GB/T 46862-2025 的合规要求。手动强派时后台必须弹窗二次确认并记录操作人。

### 4.6bis 三处「宁可派出去也不卡住」的规格细化（实现时确认）

以下三条都是同一个原则的推论：**任何约束都不能让订单永远派不出去**。

| 场景 | 处理 | 理由 |
| --- | --- | --- |
| 同门牌 9 单，超过单波次上限 | 强制合并**仍受**任务数与载重上限约束，超出部分拆成第二个同门牌簇 | 否则会形成一个所有骑手都装不下的簇，永远派不出去 |
| 单任务超重（如 40 kg > 30 kg 运力） | 对**空闲**骑手只记 `CAPACITY_OVERFLOW` 警告不硬排除；对已有在途任务的骑手仍硬排除 | 否则超重单无人可派 |
| 单骑手 `loadRatio > 0.9` | 记告警 + `f_负载 ≤ 0.1` 自然落选，**不硬排除** | 全员 0.9 时硬排除会导致订单集体滞留 |

另外调度循环的第 6、7 步（在途风险扫描、运力预警）**即使候选池为空也照常执行**——队列空的时候恰恰最该扫超时风险。

### 4.7 【核心原则】平台内所有订单都必须被配送

**本系统没有配送范围，不做距离筛选，不拒绝任何订单。**

现有平台本来就没有配送范围（`SettingsDto` 里没有该字段，后端也没有任何距离校验代码），顾客可以在任意地址下单。配送域必须与之保持一致：**只要订单进入「备货中」并完成拣货，就一定会生成配送任务并最终派出去。**

因此以下四类值全部是**软约束**，只影响「怎么派、派给谁、排第几站、给多少钱」，**绝不影响「派不派」**：

| 值 | 正确用法 | 错误用法（禁止） |
| --- | --- | --- |
| `dispatch.batching_radius_meters` | 决定能否与其他单合并 | ~~超出半径就不派~~ |
| `dispatch.max_wave_distance_meters` | 决定波次还能不能再加单 | ~~超出里程就不派~~ |
| `store.service_radius_meters` | 仅用于**远单标记**与 GPS 异常点识别 | ~~超出半径就拒单~~ |
| 冷链出箱时长 | 决定配送顺序与风险提示 | ~~超时就不派~~ |

**唯一的派单前置条件是「拣货完成」**，这不是筛选，只是时序——货没打包好，派了骑手也只能在店里干等。

### 4.8 远单（超出常规半径）的处理

远单不被拒绝，但需要区别对待，否则会拖垮整个波次。定义：单程距离 > `store.service_radius_meters`（默认 3000 m，纯粹作为「远」的判定阈值，不作为拒单阈值）。

| 处理 | 说明 |
| --- | --- |
| **独立成波次** | 远单不与近单合并（500 m 聚类半径天然保证了这一点）。绝不能让骑手为了一个 15 km 的单，把另外 7 个 2 km 的单一起拖过去 |
| **豁免波次里程/时长上限** | 见 §3 的关键规则 |
| **优先派给空闲骑手** | 远单会长时间占用一个骑手。评分时若所有骑手都在忙，`f_负载` 会自然把它推给最空的那个；若全部满载，进入等待并触发运力预警 |
| **ETA 按实际距离算** | 15 km ÷ 15 km/h ≈ 60 分钟 + 交付时长。如果算出来赶不上顾客选的配送时段，**不拒单**，而是把任务标为 `promiseAtRisk = true`，在调度台高亮，由调度员决定是否联系顾客说明 |
| **收入按里程线性递增** | `earning.distance_per_km_amount` 天然覆盖。建议客户为远单单独设一档更高费率 |
| **冷链远单强制首站** | 见 §4.4 |
| **调度台显式标记** | 远单在待派队列里带「远单 15.2 km」标签，让调度员心里有数 |

### 4.9 与配送时段（现有功能）的关系

现有平台的配送时段是真实存在且在用的：`DeliverySlotDto(id, label, maxOrders, available)`，label 形如「今日 09:00-11:00」，日期和时间窗靠正则从 label 解析。顾客下单时必须选一个。

配送域的用法：

- 顾客选的时段 → 任务的 `window_start_at` / `window_end_at` / `promised_at`
- 时间窗进入**评分**（`f_超时`）和**路径规划目标函数**（超时二次惩罚）
- 时间窗兼容性决定两个任务能否合单

**但时间窗同样不是拒单条件。** 即使一个远单注定赶不上顾客选的时段，系统也照常派单，只是标记超时风险。

另外提醒一个既有的坑：**`maxOrders`（每时段最大订单数）字段存在但从未被任何代码校验过**。也就是说时段容量目前是不限的，顾客可以无限往同一时段下单。这不是配送域引入的问题，但配送域会让它暴露出来（某个时段挤了 50 单，运力预警会一直响）。是否要真正启用时段容量限制，需要客户决策——这属于下单侧的改动，不在本项目范围内，但应该提出来。

## 5. 路径规划

### 5.1 问题定义

**单仓库、多配送点、带时间窗、带容量约束的 VRP（CVRPTW）**，但因为一次只为**一个骑手的一个波次**规划，实际退化成 **带时间窗的 TSP（TSPTW）**，规模 ≤ 8 个点。

这个规模有多小？8 个点的全排列是 40320 种，暴力枚举在 Java 里几毫秒就能跑完并得到**精确最优解**。所以：

**≤ 8 个站点时直接暴力枚举求精确解；> 8 个站点时用贪心 + 2-opt。** 这比引入任何求解器都简单可靠。

### 5.2 两阶段架构

```
阶段一：距离矩阵           阶段二：序列求解
DistanceMatrixProvider  →  RouteOptimizer
  ├ HaversineMatrix        ├ ExhaustiveOptimizer  (≤8 点，精确)
  ├ AmapMatrix             ├ GreedyTwoOptOptimizer (>8 点)
  └ TencentMatrix          ├ JspritOptimizer      (预留)
                           └ AmapSchedulingOptimizer (预留，付费)
```

两个接口都用 `@ConditionalOnProperty` + 工厂选择，配置项 `routing.matrix_provider` / `routing.optimizer`。

### 5.3 距离矩阵

```java
public interface DistanceMatrixProvider {
    String name();
    MatrixResult compute(GeoPoint origin, List<GeoPoint> destinations, TravelMode mode);
    MatrixResult computeFull(List<GeoPoint> points, TravelMode mode);
}
```

**HaversineMatrixProvider（默认，零依赖）**：

```
distance = haversine(a, b) × routing.detour_factor      // 默认 1.35
duration = distance / (eta.ebike_speed_kmh / 3.6)
```

1.35 的绕路系数是城市路网的经验值。对单门店 3 km 半径的场景，误差通常在 15% 以内，足以支撑正确的配送顺序决策——**顺序对不对，比里程数准不准重要得多**。

**AmapMatrixProvider**：调用高德距离测量 API，`type=4`（骑行）。批量最多 1 origin × 100 destination。

**缓存**（`distance_matrix_cache`）是关键：

```
cacheKey = provider + "|" + mode + "|" + quantize(origin) + "|" + quantize(dest)
quantize(p) = 坐标保留 4 位小数（约 11 m 网格）
```

不量化就永远不会命中。门店→客户点这条边在单门店场景高度重复，预期命中率 > 80%。缓存有效期 `routing.matrix_cache_hours`（默认 6 小时）。

### 5.4 目标函数

不是简单的「总里程最短」。完整目标：

```
minimize  Σ legDuration
        + λ_late  · Σ max(0, arrival(i) − promised(i))²      // 超时二次惩罚
        + λ_cold  · Σ max(0, exposure(i) − maxExposure(i))²  // 冷链二次惩罚
        + λ_early · Σ max(0, windowStart(i) − arrival(i))     // 过早到达（顾客不在家）
```

- 惩罚项用**平方**而不是线性：宁可两单各晚 5 分钟，也不要一单晚 10 分钟。这符合顾客感知（超时越久投诉概率超线性上升）。
- `λ_late` 默认 5.0，`λ_cold` 默认 8.0，`λ_early` 默认 0.5。**冷链惩罚比超时惩罚更重**，因为化了的冻品是不可逆损失，晚到 5 分钟顾客大多能接受。
- 这就是「冻品不排最后一站」的数学实现：把冻品排在末位会让 `exposure` 超限，二次惩罚会让这个解在搜索中被淘汰。

### 5.5 求解器

**ExhaustiveOptimizer**（≤ 8 站点）：全排列枚举，剪枝（当前部分解的目标值已超过已知最优则剪掉）。8 站点最坏 40320 次评估，实测 < 5 ms。

**GreedyTwoOptOptimizer**（> 8 站点）：

```
1. 构造初始解：最近邻贪心，从门店出发，每次选目标函数增量最小的下一站
2. 2-opt 局部优化：反复尝试反转任意子路段，接受改善解
3. Or-opt 补充：尝试把单个站点移动到其他位置
4. 直到无改善或超过 routing.solve_timeout_millis（默认 2000 ms）
```

**同门牌/同楼栋的站点强制相邻**，作为求解的硬约束（在邻域算子里禁止拆散它们）。这既符合常识，也大幅缩小搜索空间。

**JspritOptimizer**（预留）：jsprit 2.0 是纯 JVM、Apache 2.0、需要 Java 21。当前项目是 Java 17，**引入 jsprit 需要先升级 JDK**，因此一期只留接口不实现，用 `@ConditionalOnProperty` 挡住。这一点必须在评审时明确告知客户。

### 5.6 重规划触发

| 触发 | `trigger_reason` | 说明 |
| --- | --- | --- |
| 波次创建 | `INITIAL` | —— |
| 新任务加入已有波次 | `NEW_TASK` | 保留已完成站点，只重排剩余站点 |
| 改派 | `REASSIGN` | —— |
| 骑手偏离规划路线 > 500 m 持续 2 分钟 | `DEVIATION` | 骑手可能知道更好的路，重算 ETA 而非强行纠正 |
| 异常发生 | `EXCEPTION` | 挂起的任务移出当前序列 |
| 调度员手动 | `MANUAL` | —— |
| 骑手手动调整顺序 | —— | **不重规划**，尊重骑手判断，只重算 ETA，并记录 `adjusted_by_rider` 用于学习 |

每次重规划写一条 `route_plan`（`plan_version + 1`，旧版本 `is_active = 0`），便于复盘和 A/B 对比。

## 6. ETA 预估

### 6.1 主公式

对齐美团公开算法，且对骑手更友好：

```
ETA = max(模型估计, 保护时间₁, 保护时间₂, 保护时间₃) + Σ 场景补时
```

| 项 | 计算 |
| --- | --- |
| 模型估计 | `取货耗时 + Σ(段行驶时长) + Σ(前序站点交付时长) + 本站交付时长` |
| 保护时间₁（距离保底） | `直线距离 / 15 km/h × 1.5` |
| 保护时间₂（分段累加） | 每段按 `eta.ebike_speed_kmh` 上限计算的累加值 |
| 保护时间₃（绝对下限） | `eta.protection_floor_seconds`（默认 20 分钟） |

**`eta.ebike_speed_kmh` 默认 15，且不得调高。** 这是 GB/T 46862-2025 明确写入的电动车平均速度上限。配置项的 `max_value` 要设成 15，从代码上阻止调高。

### 6.2 楼栋交付时长学习（最大的精度红利）

单门店 + 复购顾客 = 同一批楼栋反复出现。`building_handoff_stat` 表几周内就会收敛。

**样本采集**：任务从 `ARRIVED` 到 `DELIVERED` 的时长即 `handoff_seconds`，写入 `delivery_task`，由 `BuildingHandoffLearner` 每晚聚合。

**分桶**：按 `group_key`（小区+楼栋）× `floor_bucket`（`1-3` / `4-6` / `7-12` / `13+`）。

**关键经验（来自美团公开数据）**：楼层与交付时长**不是线性关系**。低楼层走楼梯，高楼层坐电梯等电梯，中间楼层反而可能最慢。所以必须分桶统计，不能用 `基础时长 + 楼层 × 系数` 这种线性公式。

**取值**：用 `p70` 而不是均值（非对称偏好，宁可估长）。样本数 < 5 时回退到 `eta.default_handoff_seconds`（默认 180 秒）。

**门禁难度**：按 **90 天滚动窗口重算**（统计窗口内该 `group_key` 的 `ACCESS_DENIED` 异常次数，上限 5），而不是逐次累加。这样每晚重跑天然幂等、自带衰减，不会因任务重跑造成重复计数。交付时长按 `× (1 + access_difficulty × 0.1)` 放大。

### 6.3 场景补时

| 场景 | 补时 | 触发 |
| --- | --- | --- |
| 恶劣天气 | +20% | `WeatherConditionPort` 返回雨/雪/大风（兜底数据源是配置项 `eta.bad_weather_active`） |
| 门店拣货慢 | 实际延迟量 | `pickedReadyAt − 应完成时间` |
| 难进小区 | 见 6.2 | `access_difficulty` |
| 夜间 | +10% | **20:00–06:00**（凌晨配送同样需要缓冲，不只是晚上） |
| 高峰时段 | +15% | 11:00–13:00、17:00–19:00 |

### 6.4 级联补时（GB/T 46862 强制要求）

标准明确要求：**门店出货慢时，不仅要给该订单补时，还要给受其影响的其他订单补时。**

```
当任务 T 因门店拣货慢延迟了 Δ 秒：
    T.extraTime += Δ
    for each task S in 同一波次且 seqNo > T.seqNo:
        S.extraTime += Δ                 // 整个后续序列顺延
        S.extraTimeReason = "受前序订单门店出货延迟影响"
```

补时必须**对骑手可见且逐项列出**。美团的公开数据显示，骑手对逐项列明的补时信任度远高于一个黑盒数字。

### 6.5 顾客侧展示为区间

`eta.display_as_range = true` 时，顾客看到的是「预计 15:45–15:55 送达」而不是「15:50 送达」。

```
lowerAt = etaAt − range_span_minutes / 2
upperAt = etaAt + range_span_minutes / 2
```

美团公开数据显示，把点改成区间后**针对骑手的差评率下降了 50.7%**。这是投入产出比极高的一个改动。

### 6.6 非对称偏好

`eta.quantile = 0.70` 表示所有基于历史分布的估计都取 70 分位而不是中位数。

理由：低估比高估的代价高得多。低估 → 超时 → 顾客投诉 + 骑手扣分 + 客服成本；高估 → 顾客提前收到，是惊喜。美团在模型损失函数上用 1.8 : 1.2 的非对称斜率表达同一个偏好，本项目用分位数达到等效效果，但实现简单得多。

## 7. 自动改派

`ReassignmentService` 在调度循环第 6 步运行。

**风险评估**：

```
riskLevel(task):
    slack = task.promisedAt − predictedArrival(task)
    slack > 900s          → LOW
    300s < slack ≤ 900s   → MEDIUM
    0 < slack ≤ 300s      → HIGH
    slack ≤ 0             → OVERTIME
```

**改派条件（全部满足才改派）**：

1. 任务状态为 `ASSIGNED` 或 `ACCEPTED`（**已取货的不改派**，货在骑手身上）
2. `riskLevel ∈ {HIGH, OVERTIME}`
3. 存在另一骑手，其接手后 `riskLevel` 至少降低一级
4. `task.reassign_count < 2`（防止来回改派）
5. `dispatch.auto_reassign_enabled = true`

改派时：写 `delivery_task_event`（`event_type = REASSIGN`，记录 from/to 骑手和原因）、给原骑手发 `TASK_REASSIGNED` 消息、给新骑手发 `TASK_ASSIGNED` 消息、两个波次都触发重规划。

**改派不扣原骑手的分**，除非改派原因是骑手主动拒接或长时间不接单。

## 8. 运力预警

| 预警 | 条件 | 动作 |
| --- | --- | --- |
| 待派积压 | `pendingCount > onDutyRiderCount × 2` | 调度台高亮 + 给店长发消息 |
| 无可用运力 | `availableRiderCount = 0` 且有待派任务 | 同上，且暂停压单（立即派） |
| 骑手掉线 | 在岗但 `> liveness_timeout_seconds` 无位置 | 调度台标红 + 给该骑手发推送催上报 |
| 超时风险集中 | `overtimeRiskCount > 3` | 调度台告警 |
| 单骑手过载 | `loadRatio > 0.9` | 该骑手不再参与派单竞争 |

## 9. 服务分（积分制，绝不罚款）

**这是合规红线**：GB/T 46862-2025 写明「扣款原则上不应作为超时的处罚方式」，美团和饿了么已在 2025 年底全面取消超时扣款。**本系统的代码里不能有任何扣钱的逻辑。**

| 事件 | 分值 | 可恢复 |
| --- | --- | --- |
| 准时送达 | +1 | —— |
| 超时送达 | −2 | 是 |
| 异常上报成立 | +1 | —— |
| 异常上报不实 | −3 | 否 |
| 顾客好评 | +2 | —— |
| 顾客差评（未免责） | −3 | 是 |
| 完成培训 | +5 | —— |
| 安全骑行奖（月度无违规） | +10 | —— |

**恢复机制**：连续 20 单准时可恢复 5 分；完成一次培训可恢复 10 分。恢复时写 `rider_score_event`（`event_code = RESTORE`）并把被恢复的原事件标 `restored_at`。

**免责机制**：如果任务上存在成立的异常上报（`rider_exempt = true`），对应的超时扣分和差评扣分**自动免除**，不需要骑手申诉。这直接对标美团「30+ 异常场景前置上报，上报成立自动免除差评」的做法。

分数区间 `[0, score.max]`，默认上限 120，初始 100。

## 10. 收入规则引擎

```
单笔收入 = 基础费
        + 里程费   max(0, 实际里程 − 免计里程) / 1000 × 每公里费
        + 重量费   max(0, 总重 − 5kg) × 每公斤费
        + 楼层费   无电梯时 (楼层 − 1) × 每层费
        + 天气补贴 恶劣天气时
        + 夜间补贴 20:00 后
        + 节假日补贴 法定节假日
```

每一项都写一条 `delivery_settlement_item`，带 `calc_detail` 可读说明，例如：

> 里程费：实际 2.4 km，免计 1.0 km，(2400−1000)/1000 × 0.50 元 = 0.70 元

**骑手能看懂钱是怎么算出来的**，这比金额本身更重要。GB/T 46862 也要求「以通俗易懂的方式向配送员公布计价规则」。

节假日/天气补贴不是可选项，是标准要求的（7.2.7 条：法定节假日、恶劣天气、夜间配送必须有补贴）。

## 11. 可解释性

每次派单必须能回答「为什么派给他」。`delivery_task.dispatch_score` 存总分，`delivery_task_event.detail_json` 存完整 breakdown：

```json
{
  "candidates": [
    { "riderId": 1, "score": 0.8123,
      "breakdown": { "addedDistance": 0.31, "overtimeRisk": 0.28,
                     "loadBalance": 0.12, "coldChain": 0.14, "riderLevel": 0.04 },
      "addedDistanceMeters": 320, "blockers": [], "selected": true },
    { "riderId": 2, "score": 0.4210,
      "breakdown": { ... }, "blockers": ["FATIGUE_PAUSED"], "selected": false }
  ],
  "batchedWith": [9002],
  "batchReason": "SAME_BUILDING",
  "holdSeconds": 120
}
```

调度台在任务详情里直接渲染这个结构。这是让调度员信任系统、不绕过系统的关键。

## 12. 参数调优方法

一期不做在线学习，用**离线回放**调参：

1. 系统上线运行 2 周，积累真实的 `delivery_task` + `delivery_task_event` + `rider_location`。
2. 写一个回放工具（`DispatchReplayTool`，放在 `src/test`），用历史任务流重放调度循环。
3. 网格搜索权重组合，评估指标：准时率、总里程、骑手平均负载方差、冷链违规次数。
4. 把最优权重写回 `delivery_config`。

**这个工具本身就是一个交付物**，它让参数调整从拍脑袋变成可度量的实验。

## 13. 不做的事（明确划界）

| 不做 | 理由 |
| --- | --- |
| 机器学习 ETA 模型 | 单门店数据量不足以训练；启发式 + 楼栋学习表已能拿到大部分收益 |
| 深度学习派单 | 同上；且不可解释，调度员不会信 |
| 需求预测与运力提前调度 | 单门店排班靠人就够了 |
| 抢单大厅 | 自营骑手模式不需要 |
| 多门店联合调度 | 一期单门店 |
| 实时路况 | 高德企业 API 才有，且 3 km 半径内影响有限 |
| OR-Tools | 8 个点用暴力枚举就是精确最优，引入原生库得不偿失 |
