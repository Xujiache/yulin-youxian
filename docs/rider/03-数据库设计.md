# 数据库设计（冻结契约）

> **这是冻结契约。** 任何 Agent 都不得擅自增删字段或改名。确需变更必须先改本文档并通知主控 Agent，由主控统一广播。

## 0. 约定

| 项 | 约定 |
| --- | --- |
| 引擎/字符集 | `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci` |
| 主键 | `id BIGINT NOT NULL AUTO_INCREMENT` |
| 命名 | 表名/列名 `snake_case`，与 `docs/03-database-schema.md` 的既定规划一致 |
| 时间 | `DATETIME(6)`，业务时区 `Asia/Shanghai`；`created_at` 默认 `CURRENT_TIMESTAMP(6)`，`updated_at` 带 `ON UPDATE` |
| 金额 | `INT`，单位**分**（与现有系统一致） |
| 距离 | `INT`，单位**米** |
| 时长 | `INT`，单位**秒** |
| 重量 | `DECIMAL(10,3)`，单位**千克** |
| 坐标 | `DECIMAL(10,7)`，**GCJ-02**，`lat` 纬度 / `lng` 经度 |
| 状态 | `VARCHAR(24)`，存英文大写枚举常量 |
| 逻辑删除 | 仅 `rider` 表用 `deleted_at`；其余表用状态字段表达 |
| 外键 | **不建物理外键**。域内关系靠应用层保证；`order_id` 指向 JSON 快照里的订单，是软引用 |

### Flyway 迁移文件划分（严格按此，避免版本号冲突）

| 文件 | 内容 | 建表数 | 归属 Agent |
| --- | --- | --- | --- |
| `V1__create_application_state.sql` | application_state（既有系统的 JSON 快照表） | 1 | 既有 |
| `V2__create_rider_account.sql` | rider, rider_session, rider_device, rider_shift | 4 | A1 |
| `V3__create_delivery_task.sql` | delivery_task, delivery_task_event, delivery_wave, delivery_wave_stop | 4 | A1 |
| `V4__create_delivery_tracking.sql` | rider_location, rider_location_latest, delivery_geofence_event | 3 | A1 |
| `V5__create_delivery_exception.sql` | delivery_exception, delivery_evidence, delivery_weight_check | 3 | A1 |
| `V6__create_delivery_settlement.sql` | delivery_settlement, delivery_settlement_item, rider_score_event, rider_appeal | 4 | A1 |
| `V7__create_delivery_routing.sql` | route_plan, distance_matrix_cache, building_handoff_stat, geo_poi_cache | 4 | A1 |
| `V8__create_delivery_support.sql` | delivery_config, delivery_zone, rider_message, privacy_number_binding, delivery_rating<br>＋ 72 条 `delivery_config` 初始化数据 | 5 | A1 |
| `V9__add_amap_config.sql` | 无建表，仅补 2 条 `delivery_config`：`amap.js_key`、`amap.web_key` | 0 | A1 |

**共 9 个迁移文件，28 张业务表**（1 张 `application_state` + 27 张配送表），`delivery_config` 初始化 **74 条**。跑完之后库内实际有 29 张表——多出来的 `flyway_schema_history` 是 Flyway 自己的元数据表。

> 后续营销功能已新增 `V10__create_marketing_lottery.sql`：增加 7 张 `marketing_lottery_*`
> 表，并给 `delivery_task` 增加随机减免与赠品摘要字段。本文冻结的 27 张“配送域表”数量不变；
> `V11__harden_delivery_integrity.sql` 再新增 `auth_session`，并加固配送事件幂等、
> 结算明细唯一性与异常查询索引。当前完整数据库执行 V1–V11 后共 36 张业务表、
> 加 Flyway 记账表共 37 张，`delivery_config` 共 77 条。营销契约见
> `docs/09-random-discount-lottery.md`。

**所有 DDL 由 A1（后端核心）一个 Agent 编写**，其他 Agent 只读本文档、不写迁移文件。这是防冲突的关键规则。

> **V9 为什么要单独一个文件、而不是并进 V8**：`DeliveryConfigDao.updateValue` 只能改已存在的键。两个高德 Key 不预先落库的话，后台即使填了 Key 也没有可写入的行，地图会永远显示「未配置地图 Key」。V8 已经上过版本号，只能新增 V9。
>
> ⚠️ **`spring.flyway.*` 生效的前提是 `server/pom.xml` 里有 `spring-boot-starter-flyway`。** Spring Boot 4 把 `FlywayAutoConfiguration` 移出了 `spring-boot-autoconfigure`，只声明 `org.flywaydb:flyway-core` 会导致整套迁移**静默不执行**（无日志、无异常）。本项目曾长期处于这个状态，已修复。改动依赖或升级 Boot 版本后，务必按 12 文档 §3.2 复核一次 `flyway_schema_history`。

## 3. 位置与轨迹域

### rider_location · 历史轨迹（高频写）

```sql
CREATE TABLE rider_location (
    id              BIGINT       NOT NULL AUTO_INCREMENT,
    rider_id        BIGINT       NOT NULL,
    shift_id        BIGINT       NULL,
    wave_id         BIGINT       NULL,
    lat             DECIMAL(10,7) NOT NULL,
    lng             DECIMAL(10,7) NOT NULL,
    accuracy_meters INT          NULL,
    speed_mps       DECIMAL(6,2) NULL,
    bearing         DECIMAL(6,2) NULL,

    battery_level   INT          NULL,
    network_type    VARCHAR(16)  NULL,
    motion_state    VARCHAR(16)  NULL COMMENT 'STILL/WALKING/RIDING',
    is_cleaned      TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '是否已通过清洗',
    located_at      DATETIME(6)  NOT NULL COMMENT '设备定位时刻，非入库时刻',
    reported_at     DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    batch_key       VARCHAR(64)  NULL COMMENT '客户端批次幂等键',
    PRIMARY KEY (id),
    -- uk_location_dedup 同时承担 (rider_id, located_at) 的查询索引，不再另建重复索引
    UNIQUE KEY uk_location_dedup (rider_id, located_at),
    KEY idx_location_wave (wave_id, located_at),
    KEY idx_location_cleanup (located_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

> `uk_location_dedup` 让断网重传天然幂等：重复的点会撞唯一键，用 `INSERT IGNORE` 即可。
> `idx_location_cleanup` 支撑保留期清理任务（默认 90 天，见 `delivery_config`）。
>
> **已删除 `idx_location_rider_time (rider_id, located_at)`**：它与 `uk_location_dedup` 的列和顺序完全相同，是纯冗余——唯一键本身就是一棵可用于范围查询的 B+ 树，轨迹回放的 `WHERE rider_id = ? AND located_at BETWEEN ? AND ?` 直接走 `uk_location_dedup`，执行计划不变。
> 之所以值得专门删：`rider_location` 是全系统**写入最频繁**的表（每骑手每 10 秒一个点，一年约 3000 万行）。每一次 `INSERT` 都要维护一遍索引，留着这个重复索引等于把最热的写路径上的索引维护成本和磁盘占用白白翻一倍。
> 这类问题 H2 单元测试看不见——测试里的表是测试代码手写的 `CREATE TABLE`，根本不含这些索引定义。

## 10. 与既有系统的衔接

### 软引用一致性

`delivery_task.order_id` 指向 JSON 快照里的订单，无法建外键。约束靠三层：

1. 创建任务时校验订单存在且状态为 `备货中`。
2. `uk_task_order` 唯一键保证一单一任务。
3. 每日巡检任务：扫描所有非终态的 `delivery_task`，核对订单是否仍存在且状态合理，不一致则写入 `rider_message` 告警并记录日志。

### 备份体系扩展（Wave 0 强制任务）

现有 `BackupService` 只打包 `application_state` 的行 + `data/` 目录。必须扩展为：

- 备份时额外导出 27 张配送表（`SELECT * INTO OUTFILE` 不可用于远程，改用 JdbcTemplate 分页导出为 JSONL 放进同一个 ZIP）。
- 恢复时按依赖顺序 `TRUNCATE` + 批量插入。
- 恢复后调用配送域的 `reloadFromPersistence()`（如有内存缓存）。

**如果不做这一步，任何一次数据恢复都会造成订单域和配送域数据错位**，这是本项目最容易被忽略的高危点。
