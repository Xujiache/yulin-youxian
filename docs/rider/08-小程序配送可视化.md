# 小程序配送可视化（顾客侧）

## 0. 目标

让顾客在订单详情页看到骑手的实时位置和预计送达时间。这是本项目对**终端用户**唯一可见的改动，也是客户最直观感受到价值的部分。

现状：`client-wechat/pages/order-detail` 在「配送中」状态只有一句写死的文案「骑手正在火速配送，请保持电话畅通」，背后没有任何真实数据。

## 1. 现有客户端的关键事实

| 项 | 现状 |
| --- | --- |
| 框架 | **原生微信小程序**，无 Taro/uni-app，无 npm，无组件库 |
| 页面数 | 16 个，自定义 tabBar |
| 地图能力 | **目前完全没有用过 `<map>` 组件**，只用过 `wx.chooseLocation` 选收货地址 |
| 坐标 | `wx.chooseLocation` 返回 GCJ-02，与高德、`<map>` 组件一致，**无需转换** |
| 已有数据 | `GET /api/wx/orders/{id}` 返回的 `AddressDto` 里**已经包含 `latitude` / `longitude`**，只是从未渲染 |
| 请求封装 | `utils/request.js`，自动带 `Authorization: Bearer wx_xxx`，解包 `ApiResponse` |
| 订单状态 | 中文字符串，前端有一份状态 → 文案/样式的映射 |
| 订阅消息 | **完全没有使用过** |
| 轮询 | **没有任何轮询** |
| 设计系统 | 主色 `#006D37`，操作绿 `#27AE60`，背景 `#F8F9FB`，rpx 尺寸体系，可选的「液态玻璃」层 |

**好消息**：目的地坐标已经贯通了，不需要动地址链路。要做的只是加一个骑手位置源 + 一个地图卡片 + 轮询。

## 2. 交互设计

### 订单详情页的配送卡片

只在满足以下条件时展示：订单状态为 `配送中`，且 `deliveryTrackingAvailable = true`。

### 关键交互决策

**ETA 显示为区间，不是精确时刻。** 美团公开数据表明，把「15:50 送达」改成「15:45–15:55 送达」后，针对骑手的差评率下降了 50.7%。这是投入产出比极高的一个设计。由服务端 `eta.display_as_range` 控制。

**「骑手还有 N 单送达你」是一个高价值的小细节。** 顾客看到骑手在附近却不来，会焦虑并打电话。告诉他前面还有几单，焦虑立刻消失。数据来自 `stopsAhead`。

**骑手位置要平滑移动，不能跳。** 5 秒轮询一次，两点之间在客户端做线性插值，用 `<map>` 的 `translateMarker` 在 5 秒内平滑移动到新位置。这让 5 秒轮询在视觉上和实时推送没有区别。

**骑手未取货时不显示地图。** 骑手还在店里，显示他的位置既无意义又侵犯骑手隐私。此时只显示时间轴和「门店正在为您备货」。

## 3. 技术实现

### 3.1 为什么用轮询而不是 WebSocket

小程序 WebSocket 的现实约束：
- 最多 5 个并发连接
- **必须 `wss://`**，域名要备案且在小程序后台配置 socket 合法域名
- **切后台 5 秒内未完成的请求直接 `fail interrupted`**，网络 API 在回到前台前都不可用
- 空闲连接会被客户端主动关闭，需要应用层心跳
- 多连接时 `wx.onSocketOpen` 只对第一个生效，必须用 `SocketTask`

而单门店同时在看配送的顾客可能只有几十个，5 秒轮询的服务端压力是 20 QPS 量级，查的还是 10 行的 `rider_location_latest` 热表。

**结论：轮询是这里的正确工程答案，WebSocket 是过早优化。** 配合客户端插值，用户完全感知不到差别。

### 3.2 轮询生命周期（必须严格管理）

```js
// pages/order-detail/index.js
onShow()   → 若订单为「配送中」则 startTracking()
onHide()   → stopTracking()          // 切后台必须停，否则报 fail interrupted
onUnload() → stopTracking()

startTracking() {
  this.fetchTracking()                                    // 立即拉一次
  this._timer = setInterval(() => this.fetchTracking(), 5000)
}

fetchTracking() {
  request.get(`/api/wx/delivery/orders/${orderId}/tracking`)
    .then(res => {
      if (!res.hasDelivery) return this.stopTracking()
      if (res.polling.stopWhenDone && isTerminal(res.taskStatus)) {
        this.setData({ tracking: res })
        return this.stopTracking()                        // 终态立即停止
      }
      this.animateRider(res.rider)                        // 平滑移动
      this.setData({ tracking: res })
    })
    .catch(() => { /* 静默失败，下次继续，不打扰用户 */ })
}
```

**连续失败 3 次后把间隔退避到 15 秒**，避免网络不好时疯狂请求。

### 3.3 地图组件

```xml
<map
  id="deliveryMap"
  class="delivery-map"
  latitude="{{mapCenter.lat}}"
  longitude="{{mapCenter.lng}}"
  scale="{{mapScale}}"
  markers="{{markers}}"
  polyline="{{polyline}}"
  show-location="{{false}}"
  enable-rotate="{{false}}"
  enable-3D="{{false}}"
  bindmarkertap="onMarkerTap"
/>
```

要点：
- `<map>` 是**原生组件**，层级最高，会盖住普通元素。弹窗、遮罩必须用 `cover-view` / `cover-image`，或者在弹窗打开时把地图 `hidden`。这是小程序地图最常见的坑。
- 坐标一律 GCJ-02，`wx.getLocation` 也要 `type: 'gcj02'`。
- `polyline.points` 超过约 1000 点会明显掉帧，服务端返回的骑手轨迹必须**降采样**（本项目顾客侧根本不返回历史轨迹，所以只画「骑手→目的地」的直线或规划线，点数很少）。
- 骑手图标用 `rotate` 属性配合 `bearing` 表现朝向。
- 自动调整视野：用 `mapCtx.includePoints({ points: [rider, destination], padding: [60,60,60,60] })` 让骑手和目的地都在视野内。

**平滑移动**：

```js
animateRider(rider) {
  const ctx = wx.createMapContext('deliveryMap', this)
  ctx.translateMarker({
    markerId: MARKER_RIDER,
    destination: { latitude: rider.location.lat, longitude: rider.location.lng },
    autoRotate: false,
    rotate: rider.bearing || 0,
    duration: 4800,          // 略小于轮询间隔，避免动画未完成就被下一次打断
  })
}
```

### 3.4 隐私号拨打

```js
onCallRider() {
  const { callNumber, degraded } = this.data.tracking.rider
  if (degraded) {
    wx.showModal({ title: '提示', content: '本次为直接拨号，请勿保存骑手号码', showCancel: false })
  }
  wx.makePhoneCall({ phoneNumber: callNumber })
}
```

### 3.5 订阅消息

小程序订阅消息的规则约束：
- **一次性订阅**：用户授权一次 = 你可以发一条。没有时间限制，但一条就是一条。
- **长期订阅**只对政务民生、医疗、交通、金融、教育开放，**生鲜配送不符合条件**，不要指望。

实用做法：

| 时机 | 申请的模板 |
| --- | --- |
| 下单支付成功后 | 「订单已接单」+「骑手已出发」 |
| 每次打开订单详情页（配送中） | 「即将送达」 |

`wx.requestSubscribeMessage` 必须由用户点击触发，不能自动调用。授权结果通过 `POST /api/wx/delivery/orders/{id}/subscribe` 回传服务端记录。

用户勾选「总是保持以上选择」后弹窗不再出现，直接复用之前的选择——所以**每次进详情页都可以再申请一次**，这是通行做法，不违规。

### 3.6 评价

送达后在订单详情页展示评价入口：5 星 + 标签多选（准时/礼貌/包装完好/态度好/其他）+ 可选文字。调 `POST /api/wx/delivery/orders/{id}/rating`。

已评价的显示结果，不可重复评价（`uk_rating_task` 唯一约束）。

## 5. 隐私与合规

| 要求 | 实现 |
| --- | --- |
| 顾客只能看当前位置，不能看历史轨迹 | 服务端 tracking 接口根本不返回轨迹数组 |
| 订单完成后立即失效 | 终态时 `rider = null`，客户端停止轮询 |
| 只有订单本人可查 | 服务端用 `CurrentUserContext` 校验，越权返回 404（沿用现有模式） |
| 骑手姓名脱敏 | 只返回「张师傅」，不返回全名和工号 |
| 骑手手机号不暴露 | 只给隐私号 |
| 骑手未取货前不给位置 | 服务端在 `PICKED_UP` 之前不返回 `rider.location` |
| 小程序隐私协议 | 需在小程序后台声明收集「位置信息」（用于展示配送位置）；若只展示骑手位置而不获取顾客位置，可不申请 `scope.userLocation` |

**建议不申请顾客定位权限**：目的地坐标已经在收货地址里了，没必要再要一次 `wx.getLocation`，少一个授权弹窗就少一层流失。

## 6. 降级与边界

| 情况 | 表现 |
| --- | --- |
| 地址无经纬度（老订单） | 不显示地图，只显示时间轴和 ETA 文字 |
| 骑手定位陈旧（> 2 分钟） | 地图上骑手图标变灰 + 文案「骑手位置更新中」 |
| tracking 接口失败 | 静默保留上一次数据，不弹错误 |
| 无配送任务（未启用配送域） | `hasDelivery = false`，退回原有的静态文案 |
| 骑手坐标明显是 GPS 漂移（超 200 km） | 不渲染，按定位陈旧处理。注意远单是正常的，不要按距离误判 |
| 低端机型 | 地图卡片可折叠，默认折叠状态由用户上次选择记忆 |

## 7. 验收标准

1. 配送中订单能看到骑手位置，图标平滑移动不跳变。
2. 切后台再回来，轮询正确恢复且不报 `fail interrupted`。
3. 订单送达后 5 秒内地图消失、轮询停止。
4. 用他人账号访问该订单的 tracking 接口返回 404。
5. 弹窗/遮罩不被地图盖住。
6. 页面来回切换 20 次无内存泄漏、无残留定时器。
7. 老订单（无经纬度）不白屏、不报错。
