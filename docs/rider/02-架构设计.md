# 架构设计

## 1. 现状架构（必须先理解）

```
┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐
│ 微信小程序        │   │ Vue 管理后台      │   │ C# 打印代理       │
│ client-wechat    │   │ art-lnb-master   │   │ print-agent      │
│ 原生 MP          │   │ Vue3+EP+Vite     │   │ HTTP 轮询租约     │
└────────┬─────────┘   └────────┬─────────┘   └────────┬─────────┘
         │ /api/wx/**           │ /api/admin/**        │ /api/printing/agent/**
         └──────────────────────┼──────────────────────┘
                                ▼
                  ┌───────────────────────────┐
                  │  Spring Boot 4.1 / Java17 │
                  │  PM2 托管，无 Docker/CI    │
                  │  ┌─────────────────────┐  │
                  │  │ StorefrontService   │  │  ← 3217 行的领域单体
                  │  │ 全量内存 Map        │  │     所有方法 synchronized
                  │  │ persist() 全量写回  │  │     每次改动重写整个快照
                  │  └──────────┬──────────┘  │
                  └─────────────┼─────────────┘
                                ▼
                  ┌───────────────────────────┐
                  │ MySQL 8: application_state│
                  │  state_key | payload      │
                  │  storefront    (JSON 大对象)│
                  │  user-profiles (JSON)     │
                  │  printing      (JSON)     │
                  └───────────────────────────┘
```

**这是一个 JSON 文档存储伪装成的 MySQL。** 没有 ORM、没有业务表、没有外键、没有索引、没有事务粒度。它对现有场景（低频的商品/订单写入 + 全量备份可恢复）工作得很好，但它对骑手域是致命的。

### 为什么骑手域不能进快照

一次 `persist()` 的实际代价：

1. 复制 8 个集合 + 5 个 Map（含全部商品、全部订单、全部退款）
2. Jackson 全量序列化成 JSON 字符串
3. 计算 SHA-256
4. `UPDATE application_state SET payload=?` 写入 LONGTEXT
5. 回读并再次校验 SHA-256
6. 影子写一份 JSON 文件到磁盘
7. 发布 `StateChangedEvent` → 触发防抖 1.5 秒的**全量 ZIP 备份**

而且整个 `StorefrontService` 是 `synchronized` 的（94 处），意味着这期间所有下单、加购、支付回调全部阻塞。

10 个骑手每 10 秒上报一次 = 每秒 1 次全量重写。订单量增长后单次快照可达几十 MB。**这条路走不通，没有商量余地。**

这是典型的 **Strangler Fig（绞杀榕）模式**：不重构遗留的 JSON 快照，而是在旁边长出一个正常的关系型模块，用单向依赖连接。配送域是这个系统里第一个「正常」的模块，未来订单域迁移关系型时可以照这个样子做。

## 3. 架构决策记录（ADR）

### ADR-001：配送域使用关系表，不进 JSON 快照

**状态**：已决定，不可推翻。

**背景**：见 §1.1 的写放大分析。

**决策**：新增 Flyway 迁移 `V2__` 起，为配送域建立 25 张真正的关系表，用 `JdbcTemplate` 访问。`application_state` 表和 `StorefrontService` 保持原样。

**后果**：
- 好：骑手 GPS 上报是普通的行插入，代价可忽略；可以加索引、分区、按需清理。
- 好：配送域可以有正常的事务边界，不需要 `synchronized` 全局锁。
- 坏：系统里同时存在两种持久化范式，新人会困惑 → 用本文档消解。
- 坏：`delivery_task.order_id` 无法建外键（指向 JSON 里的订单 id）→ 定义为**软引用**，应用层校验，并提供一致性巡检任务。
- 坏：现有的 `BackupService` 只备份 `application_state` 和 JSON 文件，**不备份新表** → 必须扩展备份逻辑，这是 Wave 0 的任务。

### ADR-002：不引入 JPA / MyBatis，坚持 JdbcTemplate

**决策**：用 `spring-boot-starter-jdbc`（项目已有）+ `JdbcTemplate` + `RowMapper` 手写 SQL。

**理由**：项目已依赖它；引入 JPA 会带来懒加载、一级缓存、N+1 等一整套需要团队理解的心智负担，而配送域的查询模式简单且明确；手写 SQL 对高频写入的性能控制更直接。25 张表的 Repository 手写量可接受，且非常适合并行分工。

### ADR-003：配送域状态用英文枚举，订单状态保持中文字符串

**决策**：`delivery_task.status` 用 `PENDING`/`ASSIGNED`/... 英文常量（Java `enum` + 数据库 `VARCHAR(24)`）。现有 `orders[].status` 的中文字符串**一个字都不改**。

**理由**：现有的中文字面量散布在几十处 `String.equals` 里，是已知的技术债，不该扩散到新模块；但改造它风险大且不在本项目范围内。用一个明确的边界隔开，比混着写好。

**后果**：需要一个 `OrderStatusBridge` 单向适配器，把配送任务事件翻译成订单状态动作（映射表见 01-PRD §5）。展示层需要 `DeliveryTaskStatus.displayName()` 提供中文名。

### ADR-004：骑手会话必须持久化，不能沿用内存 Session

**背景**：现有 `wx_`/`admin_` 令牌存在 `ConcurrentHashMap` 里，服务重启即全部失效。管理员重新登录没问题，但骑手在送货途中被登出是不可接受的。

**决策**：新建 `rider_session` 表，存 access token（30 天滑动过期）+ refresh token（90 天）。密码用 BCrypt。

**为什么不用 JWT**：需要支持服务端强制下线（骑手离职、设备丢失）、需要单设备登录约束、需要记录设备信息。有状态会话在这个场景更合适，而且表查询代价可忽略。

### ADR-005：实时通信分三条链路，各用最合适的方案

| 链路 | 方案 | 理由 |
| --- | --- | --- |
| 骑手 → 服务端（位置） | **HTTP 批量 POST**，每 15–30 秒提交一批点 | 最抗弱网；带客户端时间戳 + 幂等键，断网重传天然正确；和打印代理的既有范式一致 |
| 服务端 → 骑手（派单） | **厂商推送 + 应用内轮询兜底** | 国产 ROM 上任何长连接都不可靠，必须有推送唤醒；轮询保证推送失败时不丢单 |
| 服务端 → 小程序（骑手位置） | **HTTP 轮询 5 秒** | 小程序 WebSocket 有 5 连接上限、切后台 5 秒即断、需要 wss 域名备案。单门店并发观看者极少，轮询在视觉上和推送无差别，且零基础设施成本。客户端做插值让图标平滑移动 |
| 服务端 → 调度台 | **SSE（Server-Sent Events）** | 单向推送足够；比 WebSocket 简单；浏览器原生支持自动重连 |

**明确不做**：不引入 MQTT broker，不引入 Redis（当前规模不需要），不引入消息队列。

### ADR-006：外部服务全部可插拔，且必须有零依赖的兜底实现

**决策**：距离矩阵、路径求解、推送、隐私号、天气，每一个都定义接口 + 至少两个实现（真实实现 + Noop/本地实现），通过 `@ConditionalOnProperty` 切换。

**理由**：这是本项目最重要的工程约束。高德企业认证、极光付费版、隐私号服务都需要客户采购和资质审核，周期不可控。**开发和演示绝对不能被密钥阻塞。**

具体降级矩阵：

| 能力 | 有密钥 | 无密钥（默认） |
| --- | --- | --- |
| 距离矩阵 | 高德距离测量 API | Haversine 直线距离 × 1.35 绕路系数 |
| 路径求解 | jsprit VRPTW | 贪心最近邻 + 2-opt 局部优化 |
| 推送 | 极光全厂商通道 | 应用内轮询（3 秒） |
| 隐私号 | 阿里云 AXB | 明文号码 + 后台记录降级事件 |
| 天气 | 高德天气 API | 固定「晴」，补时系数为 1 |
| 地图渲染（App） | 高德地图 SDK（必需） | 无兜底，这一项必须有 Key |

只有 Android 端的高德地图 SDK 是硬依赖（个人认证 Key 即可，免费）。

### ADR-007：路径规划在服务端，不在手机上

**决策**：所有距离矩阵获取和路径求解在 Spring Boot 端完成，手机只展示结果并把每一段交给高德导航 SDK。

**理由**：Web API 密钥不能进 APK（无 SHA1 绑定，泄露即被盗刷）；跨骑手的合单需要全局视野；手机算路会耗掉 GPS 需要的电量；服务端换算法不需要发版。

**性能预算**：30 个点的矩阵调用 200–800 ms（可缓存），求解 < 100 ms，端到端 < 2 秒。足够支持「每来一单就重新规划」。

### ADR-008：Android 用 Kotlin + Compose，最低 API 26

**决策**：`minSdk 26` / `targetSdk 36`，Kotlin 2.3.21，Jetpack Compose + Material 3，Hilt + Room + DataStore + WorkManager + Retrofit/OkHttp，高德定位/地图/导航 SDK。

`minSdk 26` 的理由：通知渠道（自定义派单提示音必需）从 API 26 才有，而这是骑手端的核心体验；低于 26 的设备在 2026 年占比可忽略。

地图是 View 不是 Composable，用 `AndroidView` 包装，必须手动转发 `onCreate/onResume/onPause/onDestroy/onSaveInstanceState`，这是最常见的内存泄漏源。

### ADR-009：定位管道不放在 ViewModel

**决策**：定位采集在前台 `Service` 里，Service 持有 Repository，Repository 写 Room，另一个协程把 Room 里的点批量上传。UI 层观察同一个 Repository。

**理由**：Activity 会被销毁，Service 不会。骑手锁屏骑车时 UI 早就没了，采集必须继续。

### ADR-010：分层保活策略

Android 平台规则只是及格线，国产 ROM 才是真正的战场。分四层：

1. **平台层**：`foregroundServiceType="location"` + 高优先级常驻通知。`location` 类型没有运行时长上限（`dataSync` 才有 6 小时限制），可以跑完整个班次。
2. **权限层**：上班动作必须在**应用可见时**由骑手主动点击触发，这样永远不会撞上「后台无法启动 while-in-use 服务」的限制。绝不从推送或开机广播启动定位。
3. **ROM 层**：内置保活设置向导，按 `Build.MANUFACTURER` 深链到各厂商的自启动/后台耗电/省电策略页面，配图引导。**这不是锦上添花，这是决定 App 能不能用的功能。**
4. **可观测层**：服务端监测在岗骑手的上报心跳，超过 2 分钟无数据就在调度台告警。国产 ROM 上不可能做到 100% 存活，那就让失败可见。

### ADR-011：坐标系统一 GCJ-02，不做转换

高德 SDK 输出 GCJ-02，微信小程序 `<map>` 要求 GCJ-02，现有地址表里的经纬度来自 `wx.chooseLocation`（也是 GCJ-02）。全链路一致，不需要任何坐标转换。

**这也是选高德而不是百度的关键理由之一**（百度用 BD-09，会在每个边界上引入转换层和精度损失）。

数据库存 `DECIMAL(10,7)`，7 位小数约 1.1 cm 精度，远超需求。

### ADR-012：新表必须纳入现有备份体系

现有 `BackupService` 会把 `application_state` 的行和 `data/` 目录打包成 ZIP，支持一键恢复。新增的 25 张表如果不纳入，一次误恢复就会造成配送域和订单域数据错位。

**决策**：扩展 `BackupService`，备份时导出配送域表为 SQL/JSON，恢复时一并还原。这是 Wave 0 的强制任务，不能留到最后。

## 6. 性能与容量预算

按 10 骑手 / 日均 300 单 / 峰值 60 单每小时设计。

| 项 | 预算 | 依据 |
| --- | --- | --- |
| 位置写入 | 峰值 1 行/秒，日增约 30 万行 | 10 骑手 × 10 秒间隔 × 8 小时；批量提交后实际请求数约 0.05 QPS |
| `rider_location` 表增长 | 约 25 MB/月 | 单行约 80 字节；保留 90 天后清理 |
| `rider_location_latest` | 恒定 10 行 | 顾客与调度台的高频查询都打这张表 |
| 顾客位置轮询 | 峰值 20 QPS | 假设同时 100 个顾客在看，5 秒轮询 |
| 派单计算 | < 2 秒 | 矩阵 800 ms（可缓存）+ 求解 100 ms |
| 派单频率 | 每 5 秒一次调度循环 | `@Scheduled` |
| 矩阵缓存命中率 | 预期 > 80% | 门店→客户点的边高度重复 |

现有单机 PM2 部署可以轻松扛住。**不需要 Redis，不需要集群。** 但要注意：现有架构是单实例强绑定的（内存会话、内存快照、`synchronized`），所以配送域也按单实例设计，用 `@Scheduled` 而不是分布式调度。如果未来要多实例，整个系统都要改，不是配送域单独的问题。

## 7. 关键风险与对策
