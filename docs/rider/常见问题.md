## 1. APP 收不到新单

### 先按这个顺序排查（90% 的情况在前三条）

#### ① 有没有点「上班」？

**这是最常见的原因。**

系统只给"在岗"的人派单。没点上班 = 系统当你不存在 = 一个单都收不到。

**怎么确认**：APP 首页最上面的开关，是不是在"上班"状态。
**怎么解决**：点「上班」。

**店主这边怎么看**：后台「配送调度台」第四列「在岗骑手」里，有没有这个人。没有就是没上班。

#### ② 店主有没有点「拣货完成」？

**第二常见的原因，而且是店主这边的问题。**

不点「拣货完成」，系统根本不会生成配送任务，自然也不会派给任何人。

**怎么确认**：后台「配送调度台」第一列「待派积压」是不是 0。如果是 0，且订单管理里明明有备货中的订单，那就是没点。
**怎么解决**：去「订单管理」，把打包好的订单点「拣货完成」（绿色按钮，在每一行最右边）。

> **如果订单页上根本找不到「拣货完成」，显示的还是原来的「配送」**：不是按钮没做，是调度台右上角的「自动派单」被关掉了——这个开关关掉之后按钮会一起消失。去调度台把它打开，按钮就回来了。详见《日常使用手册》1.7 节。

#### ③ 保活向导做了没有？

手机把 APP 冻结了，它就问不到服务器"有没有新单"。

**典型现象**：手机放兜里半天没动静，**一掏出来点亮屏幕，单子立刻全跳出来了**。这就是被冻结的铁证。

**怎么解决**：
1. APP →「我的 → 设置 → 保活向导」
2. **每一项都点进去实际设置一遍**，不是看一遍
3. 特别注意这几项（按品牌）：

| 品牌 | 最关键的设置 |
| --- | --- |
| 华为 / 荣耀 | 手机管家 → 应用启动管理 → **关掉"自动管理"** → 三项全开 |
| 小米 / 红米 | 省电策略 → 改成「**无限制**」 |
| OPPO / vivo | 最近任务界面 → 下拉本 APP 的卡片 → **点小锁图标** |
| 三星 | 电池 → 后台使用限制 → 「永不休眠的应用」里加上本 APP |

#### ④ 通知权限开了没有？

**怎么确认**：手机设置 → 应用 → 禹邻优鲜骑手 → 通知，看总开关是不是开的。
**还要看**：「新派单」「紧急提醒」「配送服务」三个分类是不是都开着，并且「新派单」设成了"重要通知/横幅提醒"并允许响铃。

#### ⑤ 是不是开了省电模式？

下拉通知栏看一眼。**电量低于 20% 时手机会自动开启省电模式**，这时候后台全被限制。

**解决**：关掉省电模式，充电。

#### ⑥ 网络通不通？

用手机浏览器随便打开一个网页试试。

#### ⑦ 手上的单是不是已经满了？

系统给每个人设了"最多同时接几单"（默认 3 单）。手上满了就不会再派新的。

**怎么看**：后台「配送调度台」第四列，骑手卡片上有个 `3/3` 这样的数字。
**解决**：送完几单自然就有位置了。急的话店主可以在后台「骑手管理」里把这个人的"最多同时接几单"调大。

### 关于新单提醒的原理（知道了好排查）

APP 每 **3 秒**问一次服务器"有没有新单"。有的话就响铃 + 语音播报。

- 手机没被冻结的时候，从店主点「拣货完成」到手机响，**最多几分钟**（其中 0～2 分钟是压单等待，3 秒是轮询间隔）
- 手机被冻结的时候，这个"每 3 秒问一次"就停了，所以收不到

> 目前**没有接第三方推送服务**（极光推送因为版本兼容问题暂缓了）。所以保活做没做好，直接决定收不收得到单。

## 2. 手机定位不动了

### 现象

- 后台「配送调度台」第四列，这个人的卡片上出现红色的「**定位陈旧**」
- 顾客小程序上看到骑手图标卡在一个地方不动
- 送货的人自己没感觉，还在正常骑车

### 可能原因和解决办法

| # | 可能原因 | 怎么确认 | 怎么解决 |
| --- | --- | --- | --- |
| 1 | **手机把 APP 冻结了**（最常见） | 让他点亮屏幕打开 APP，位置立刻恢复 | **重做保活向导**。这次一定要每一项都真的点进去改 |
| 2 | 开了省电模式 | 下拉通知栏看 | 关掉，充电 |
| 3 | 系统定位总开关被关了 | 下拉通知栏看"位置"图标是不是灰的 | 打开 |
| 4 | 后台定位权限不是"始终允许" | 手机设置 → 应用 → 禹邻优鲜骑手 → 权限 → 位置信息 | 改成「始终允许」 |
| 5 | 通知栏那条常驻通知被划掉了 | 下拉通知栏看还在不在 | 重新点一次「下班」再「上班」 |
| 6 | 手机没信号（地下车库、电梯） | 问他在哪 | 正常现象。**位置点会存在手机里，出来有信号后自动补传**，不会丢 |
| 7 | 定位精度太差被系统丢弃了 | 室内、高楼之间容易发生 | 正常现象，走到开阔地就恢复 |
| 8 | 手机被重启了（系统更新、没电关机） | 问他 | 重新打开 APP 点「上班」。**手机重启后不会自动开始定位**，这是合规要求，必须人工点一次 |

### 店主这边的处理流程

1. 看到红色的「定位陈旧」→ **打电话让他把 APP 打开看一眼**
2. 打开就恢复 → 记下来，当天回店后重做保活向导
3. 打开也不恢复 → 让他检查 3、4 两条
4. 都不行 → 让他「下班」再「上班」一次

### 为什么系统能发现"定位陈旧"

系统会盯着每一个在岗的人。**超过 2 分钟没收到位置上报，就在调度台标红。**

国产手机上没有任何办法保证 100% 不被杀，所以做法是：尽力保活 + **一旦失败立刻让你看见**。

## 3. 后台看不到骑手位置

分两种情况，先分清是哪一种。

### 情况 A：地图区域是一片空白，中间写着"未配置地图 Key"

**这不是故障，这是正常的。**

因为还没申请高德地图 Key，所以后台画不出地图底图。

**重要：这完全不影响派单。**四列队列、派单、改派、异常处理全都正常工作。调度台的设计本来就是"队列为主、地图为辅"，页面上那句话写得很清楚：「不用地图也能完成全部派单」。

**想要地图**：申请一个高德 Key（个人认证免费，实名认证大概 1 天）。拿到之后，**光是让后台这块地图显示出来，你自己就能搞定**——后台「调度参数 → 地图」里把「JS API Key」填进去保存就行，不用找技术人员。要让距离也按真实道路算、要让骑手 APP 里的地图也出来，那几步才需要技术人员，见《交付说明》第六节。

### 情况 B：地图能看到，但某个人的图标不在上面 / 位置不更新

按第 2 条排查。

### 情况 C：整个页面的数据都不刷新

右上角是不是显示「实时连接已断开，正在 5 秒轮询」？

| 显示 | 说明 | 怎么办 |
| --- | --- | --- |
| 实时连接正常 | 正常 | —— |
| 实时连接已断开，正在 5 秒轮询 | 数据还在更新，只是慢 5 秒 | 点「立即重连」；不行就刷新页面 |
| 一直断开，重连也没用 | 服务器的 Nginx 配置里缺了几行 | 找技术人员，见《安装部署手册》5.3 节的 `proxy_buffering off` |

## 4. 订单派不出去，"待派积压"一直有单

按顺序查：

### ① 🔴 自动派单开关是不是关着？（**先查这一条**）

看调度台页面右上角的「自动派单」开关，或者「调度参数 → 派单」里的同一个开关。

**这一条排在第一位，是因为它的后果最大、最容易被误解。**关掉它不是"改成手动派单"——**整套配送会直接停摆**：

- 系统不再自动派单，「待派积压」里已有的单就一直堆在那儿
- **订单页上的「拣货完成」按钮也会跟着消失**，变回原来的「配送」按钮，新的配送任务一个都建不出来
- 页面上不会有任何提示告诉你为什么

**解决**：打开它。**没有"只手动派单"这个模式**，所以别把它当成手动模式的开关长期关着。

**急着派某一单**：在「待派积压」列点那一单的「立即派单」。**想让系统马上跑一轮**：点右上角「手动触发调度」。**这两个按钮都不受这个开关影响**，能达到你想要的效果，又不会把系统关停。详见《日常使用手册》1.7 节。

### ② 有没有人在岗？

看第四列「在岗骑手」。空的就是没人上班。

**解决**：让送货的人在手机上点「上班」。

### ③ 还在压单等待期？

新生成的任务会等 **0～2 分钟**，看看有没有顺路的单可以合并。卡片右上角有倒计时。

**这是正常的，不是故障。**急的话点「立即派单」跳过等待。

### ④ 在岗的人手上单满了？

骑手卡片上的 `3/3` 就是满了。

**解决**：等他送完，或者去「骑手管理」把"最多同时接几单"调大。

### ⑤ 顶部出现黄色"运力预警"横幅？

意思是：待派的单已经超出在岗人手能承受的量了。

**解决**：加人，或者主动联系顾客商量延后。

### ⑥ 点「查看建议」看系统怎么说

在待派的卡片上点「**查看建议**」，会弹出一个框，列出每个候选人的得分和**阻断原因**。

常见的阻断原因：

| 阻断原因 | 意思 | 解决 |
| --- | --- | --- |
| 已达并发上限 | 手上单满了 | 等或调大上限 |
| 不在岗 | 没点上班 | 点上班 |
| 定位陈旧 | 超过 2 分钟没上报位置 | 见第 2 条 |
| 试用期限制 | 新人只能接 2 公里内的单 | 「骑手管理」里取消"试用期"勾选 |
| 载重超限 | 这一趟太重了 | 拆开派，或调大"最大载重" |

### ⑦ 一直卡着，手动也派不出去

点「手动触发调度」（页面右上角）强制跑一次派单。

还不行就看后端日志：`pm2 logs yulin-youxian-server --lines 100`，找 ERROR。

## 5. 地图是空白的

| 哪里的地图 | 现象 | 原因 | 怎么办 |
| --- | --- | --- | --- |
| **后台调度台** | 显示"未配置地图 Key"的提示页 | 还没申请高德地图 Key | **不影响使用**，队列派单全正常。想要地图就申请 Key，见《交付说明》第六节 |
| **骑手 APP 的"路线"页** | 底图出不来 | 同上，Android 端的 Key 没配 | **不影响送货**。点"导航"会跳到手机上装的高德/百度地图，照样能导航 |
| **顾客小程序** | 地图空白或不显示 | ⚠️ **这个不该空白**。小程序的地图是微信自带的，不需要高德 Key | 见下面 |

### 顾客小程序地图不显示，排查这几条

| 可能原因 | 说明 |
| --- | --- |
| 订单还没到"配送中" | **正常**。东西还没打包好、骑手还没取货的时候，本来就不显示地图 |
| 订单已经送达了 | **正常**。送达后地图会消失，只留进度条 |
| 骑手还没上报过位置 | 系统拿不到位置就不画地图。看后台这个人是不是在岗、位置是不是新的 |
| 顾客把地图收起来了 | 页面上有个「展开地图」，让顾客点一下 |
| 门店坐标没配对 | 见《日常使用手册》1.6 节 |
| 顾客手机上开了别的弹窗 | 小程序的地图是原生组件，弹窗打开时会临时隐藏，关掉弹窗就回来了 |

## 6. 照片传不上去

### 先明确一件事：**照片传不上去不影响你送货**

拍完照 → 照片先存在手机里 → 滑动确认送达 → 送达这个动作**立刻生效**（哪怕没网）→ 照片在后台慢慢传。

所以看到"上传中"不用等，接着送下一单就行。

### 一直传不上去，排查

| # | 可能原因 | 怎么确认 | 怎么解决 |
| --- | --- | --- | --- |
| 1 | 没网 / 信号差 | 用浏览器打开个网页试试 | 走到有信号的地方，会自动重传 |
| 2 | 相机权限没给 | 拍照时黑屏或直接闪退 | 手机设置 → 应用 → 禹邻优鲜骑手 → 权限 → 相机，打开 |
| 3 | 手机存储满了 | 手机设置里看剩余空间 | 清理一下，至少留 1 GB |
| 4 | **服务器磁盘满了** | 后台传所有图片都失败 | 🔴 **店主处理**：让技术人员 `df -h` 看磁盘，清理一年以上的旧照片 |
| 5 | 上传的图片超过大小限制 | 少见（APP 会自动压缩） | 找技术支持 |
| 6 | APP 提示"同步异常" | APP 里会显示有几条没传上去 | 点手动重试。多次失败告诉店主 |

### 店主怎么确认照片到底传上去没有

后台「配送任务」→ 搜任务号或订单号 → 点「详情」→ 切到「凭证」标签页，能看到这一单所有的照片。

照片上会有时间和地点水印。

## 7. 换手机了怎么办

### 好消息：不需要店主做任何操作

账号是绑手机号的，不绑设备。换手机只要重新装 APP、重新登录就行。

### 步骤

1. **在旧手机上先点「下班」**（如果旧手机还能用）
2. 把 `禹邻优鲜骑手.apk` 装到新手机上（找店主要，或者从旧手机上把安装包传过去）
3. 安装时会遇到"未知来源"拦截，见《安装部署手册》6.4 节
4. 用**手机号 + 现在的密码**登录（不是初始密码，是改过之后的）
5. 🔴 **重新做一遍三步授权**
6. 🔴 **重新做一遍保活向导**（新手机的设置是全新的，一定要重做）
7. 点「上班」，让店主在后台确认能看到你

### 常见问题

| 问题 | 答 |
| --- | --- |
| 旧手机上没送完的单会丢吗 | 不会。单子存在服务器上，新手机登录后就能看到 |
| 旧手机上还有没传上去的操作怎么办 | ⚠️ **会丢**。所以换手机前，先让旧手机连上网，等 APP 里的"待同步"清零 |
| 密码忘了 | 找店主在「骑手管理」里点「重置密码」，会生成一个新的初始密码 |
| 两台手机能同时登吗 | 不建议。一个账号在新设备登录后，旧设备可能被登出 |
| 换的是苹果手机 | ❌ **用不了**。这个 APP 只有安卓版。需要准备一台安卓手机 |

## 8. 要加送货的人，怎么加

完整步骤见《日常使用手册》1.5 节。这里是精简版：

### 三步走

| 步骤 | 在哪做 | 做什么 |
| --- | --- | --- |
| 1️⃣ 建账号 | 电脑后台「骑手管理 → 新增骑手」 | 填姓名、手机号、车辆类型 → 保存 → **立刻抄下弹出来的初始密码** |
| 2️⃣ 装 APP | 他的安卓手机 | 发 apk 过去 → 安装（要处理"未知来源"） |
| 3️⃣ 首次设置 | 他的手机，**你陪着做** | 登录 → 改密码 → 三步授权 → **保活向导** → 点一次「上班」验证 |

### 🔴 三个最容易出错的地方

1. **初始密码只显示一次**，关掉窗口就没了。忘了只能重置。
2. **保活向导必须现场陪着做完**，不能让他自己回家做。这一步不做，后面天天出问题。
3. **必须是安卓手机。**苹果手机装不了。

### 建议给新人勾上"试用期"

勾了之后系统只派**近的（2 公里内）、少的（最多 3 单）**给他。熟练了再去「骑手管理」把这个勾去掉。

### 加了人之后系统会自动做什么

- 派单时会在几个人里挑最合适的（看谁顺路、谁手上活少、谁不会超时）
- 每个人的单量会自动均衡，不会全压在一个人身上
- 每个人的位置在调度台上分开显示

## 9. 以后要雇外人送货，需要改什么

自家人送货和雇外人送货，管理方式差别很大。下面这些是**建议**打开的（现在都关着）。

### 必须重新考虑的四件事

| # | 事项 | 为什么 | 怎么做 |
| --- | --- | --- | --- |

## 10. 其他常见小问题

### Q：点了「拣货完成」，但订单没变成"配送中"

**正常。**「拣货完成」只是生成配送任务，订单还是"备货中"。

订单要等**送货人在手机上完成取货核对**之后，才会变成"配送中"。

> ⚠️ **确认框上那句话写得不太准，别被它带偏。**「拣货完成」的弹窗里写着"确认拣货完成后订单进入配送中"，但实际上这一步**只生成配送任务，不改订单状态**。以下面这张表为准。

完整对应关系：

| 谁做了什么 | 订单状态变成 |
| --- | --- |
| 店主点「拣货完成」 | 还是「备货中」（多了一个配送任务） |
| 送货人完成取货核对 | 「配送中」 |
| 送货人确认送达 | 「已完成」 |
| 异常处理选了"退回门店" | 保持「配送中」，等你人工处理 |
| 取消了配送任务 | 退回「备货中」，可以重新派 |

### Q：一趟送好几单，顺序能自己改吗

能。两个地方：

- **送货人**：在 APP 的路线页可以手动调整顺序
- **店主**：后台「配送波次 → 点开某个波次」，站点列表可以拖拽重排

系统会记录你改了多少，用来慢慢学习你的偏好。

### Q：为什么系统把某一单排在最后，那家明明最近？

派单和排顺序看的不只是距离，还有：

- **冷链**：带冻品的单会被往前排，避免化掉（冷链的权重比超时还高——化掉的冻品不可逆，晚几分钟顾客大多能接受）
- **承诺时间**：约了 15:00 的单不会排在 14:00 之前送（太早顾客可能不在家）
- **楼栋难度**：系统学过每栋楼平均要爬多久，会把耗时的往前排

在待派卡片上点「查看建议」能看到系统的计算依据。

### Q：什么是"远单"？会不会因为太远就不派？

**不会。远单只是一个提示标签，绝对不会拒单。**

系统里所有跟距离有关的设置都是**软约束**——只影响"怎么派、排第几站"，不影响"派不派"。

超过 3 公里（可改，「调度参数 → 门店 → 远单标记半径」）的单会打上"远单"标签，让你知道这单要多花点时间。就这样，没别的。

一个 15 公里的单会自己独占一趟（不跟别的单合并），照送。

### Q：一趟最多能带几单？

默认 **8 单 / 8 公里 / 60 分钟 / 30 公斤**，任何一项超了就拆成两趟。

在「调度参数 → 派单」里可以改。**保温箱装不下的话，把"单波次最大单量"改小。**

> 例外：一个单如果自己就超过 8 公里，会豁免里程和时长限制，单独一趟送。

### Q：后台的「骑手结算」页面要管吗？

**不用管。**你自己送货，钱是自己的，左手倒右手没意义。

系统每天凌晨 1:00 会生成一张结算单，但你可以完全不看。不会有任何影响。

以后雇人了再看第 9 条。

### Q：位置记录会一直存着吗？

不会。**90 天后系统自动删除**（每天凌晨 3:30 清理）。

这是个人信息保护的合规要求，不建议改长。

### Q：下班之后还会记录位置吗？

**不会。**点「下班」是真的停止采集，不是隐藏起来。这也是合规要求。

所以收工一定要记得点下班，既省电也合规。

### Q：数据会不会丢？

系统有两层保护：

1. **实时备份**：数据一变就打包备份（停下来 1.5 秒后触发）
2. **定时备份**：每 5 分钟固定再存一份

后台「数据备份」页面能看到最近一次备份的时间，也能一键恢复。

#### ⚠️ 挑恢复点时注意：**这次升级之前的旧备份，文件名上的时间比实际早 8 小时**

备份文件的名字里带着时间，形如 `backup-20260812-143005-123-auto.zip`。

**这次升级把文件名里的时间改成了北京时间**（改之前用的是国际标准时间，比北京时间早 8 小时）。所以：

| 备份是什么时候生成的 | 文件名上的时间 |
| --- | --- |
| 这次升级**之后** | ✅ 北京时间，和你看表的时间一致 |
| 这次升级**之前**（老备份） | ⚠️ 比实际时间**早 8 小时**。比如实际是下午 14:30 存的，名字上会写成 06:30 |

**新旧备份混在一个目录里的那几天，如果你按文件名去排先后，顺序会排错。**举个例子：升级前上午 10:00 存的那份老备份，名字上写的是 `02:00`；升级后上午 09:00 存的新备份，名字上写的是 `09:00`。按文件名排，`02:00` 那份排在前面、看着更早，**其实它比 `09:00` 那份还要新**。

> ✅ **但页面上的列表不受影响。**「数据备份」页面是**按文件实际的生成时间排序**的，不看文件名，所以列表里最上面的永远是最新的一份。系统清理超出 30 份的旧备份时，用的也是实际时间，不会误删。
>
> **所以：挑恢复点就看页面列表的顺序，别自己去读文件名上的数字。**等这批老备份被新的顶掉（忙的时候两三个小时，闲的时候几天），这个问题就自动消失了。

#### 🔴 但是：**只保留最近 30 份**，能退回去的时间比你以为的短

这两层备份合起来，**总共只留最近 30 份，超过就把最老的顶掉**。

忙起来的时候，30 个位置**两三个小时就轮完一圈**。也就是说：

- 上午出的问题，下午才发现 → **很可能已经找不到出问题之前的那个备份点了**
- 越忙，这个窗口越短

**所以：**

| 什么时候 | 做什么 |
| --- | --- |
| 要做大动作之前（批量改价、批量改商品、清理数据） | **先在「数据备份」页面手动备份一次** |
| 发现数据不对劲 | **当场就去看备份页面**，别等收工再说 |
| 上线后一周内 | 做一次"备份 + 恢复"演练——真出事的时候才知道能不能救回来 |

### Q：服务器重启之后要做什么？

| 谁 | 要做什么 |
| --- | --- |
| 服务器 | PM2 一般配置了开机自启，会自动起来。用 `pm2 status` 确认 |
| 店主 | 刷新一下后台页面 |
| 送货人 | **重新点一次「上班」**（保险起见），并确认通知栏那条常驻通知还在 |

> 好消息：送货人的登录状态**不会**因为服务器重启而失效（登录信息存在数据库里，30 天有效）。
>
> 管理后台不一样：它的登录状态只存在内存里，**服务器一重启就要重新登录**。反过来说，**它也没有设过期时间**——只要服务器不重启，你登录一次就一直有效，不会自己掉线，也不会因为放了几天没动就要求重登。所以如果电脑是店里公用的，用完记得点右上角退出登录，别只是关掉浏览器。

### Q：不小心重复点了「拣货完成」会怎样？

不会重复生成任务。一个订单最多只能有一个配送任务，数据库层面就限制死了。

- 如果之前那个任务**还在进行中** → 系统会提示"已存在进行中的配送任务 XXX"，什么都不会发生
- 如果之前那个任务**已经结束了**（比如被取消、被退回） → 系统会用原来的任务号重新派一次，这正是你想要的

### Q：APP 有更新怎么办？

目前没有做自动更新。新版本出来的时候，技术人员会给一个新的 apk，重新装一遍即可（**直接覆盖安装，数据不会丢**）。

⚠️ 前提是新包的签名和旧包一致。**只要技术人员一直用交付时那个签名文件（`rider-release.jks`）加那张密码单上的口令打包，签名就是一致的**，覆盖安装没问题。换了签名文件、或者文件和口令丢了任意一样、只能另建一把，就必须先卸载再装——登录状态和手机里没传上去的操作都会丢。所以**文件和口令都要备份好，而且分开放**，见《安装部署手册》6.1 节。

### Q：能不能在电脑上看送货人现在在哪？

能。两个地方：

- **实时位置**：后台「配送调度台」，右边的地图辅助面板
- **历史轨迹**：后台「骑手管理 → 点开某个人 → 轨迹回放」，能看到某一天走过的完整路线。可以播放、暂停、拖进度条、调快慢（最方便的是调到 2 倍速看一遍）。播到哪个点，下面就显示那一刻的**坐标、速度（多少公里每小时）和状态（静止 / 步行 / 骑行）**
- **一趟的规划路线和实际走法对比**：后台「配送波次 → 点开某个波次」，右边地图上会把两条线叠在一起——**绿色实线是系统排的路线，蓝色虚线是实际走过的轨迹**，一眼能看出哪一段绕了路。这个页面下面也有一个轨迹回放播放器

> ⚠️ 这三个地方**都要有高德地图 Key 才能看到地图底图**（现在还没申请，见《交付说明》第六节）。没有 Key 时地图区域是空的，轨迹画不出来。<br>播放器上的时间、速度、状态这些文字信息不依赖地图，没有 Key 也照样能看。

## 11. 后端启动报 `Table 'xxx' doesn't exist` / 表没有自动创建

> 这一条给技术人员看。店主遇到这个问题，直接把这一整节转给技术支持就行。

### 现象

- 后端日志里出现 `Table 'yulin_fresh.delivery_task' doesn't exist`、`Table 'yulin_fresh.application_state' doesn't exist` 这类报错（意思是"这张表不存在"）
- 或者：程序看上去启动成功了、`/api/ping` 也通，但一打开后台的配送页面就是 500 错误
- 数据库里 `SHOW TABLES` 一看，那 27 张配送表一张都没有

**一句话原因：本该在启动时自动建出来的表，根本没建。**

### 为什么会这样（这个项目真实发生过，值得一读）

程序里负责"启动时自动建表"的部件叫 **Flyway**。它要能干活，前提是打包时把它的**启动器**一起装进去。

这个项目早期漏装了这个启动器。后果是：Flyway 从来没被启用过，配置文件里那一整段建表相关的设置全被忽略，**迁移一次都没执行过**。最坑的地方在于它是**完全静默**的——不报错、不警告、日志里一个字都不写，看起来和"没有表需要建"一模一样。

**为什么以前没发现**：日常跑的那四百多个自动化测试（都是后端的，**具体多少条以实际执行 `mvn test` 的输出为准**）全部用的是内存里的临时数据库，而且里面的表是**测试代码自己手工建的**，压根不走这套自动建表机制（测试配置里甚至明确把它关掉了）。所以 Flyway 装没装、能不能工作，对测试结果没有任何影响——测试全绿也照样发现不了。

**这类问题的盲区就在这儿：测试全过，只能说明业务逻辑对，不能说明程序启动时该装的东西都装上了。**

问题**已经修好了**（在 `server/pom.xml` 里补了 `spring-boot-starter-flyway`）。但如果你上传的是修复之前打的 jar 包，问题会原样重现。

### 三步确认

```bash
# 第一步：日志里到底有没有 Flyway
pm2 logs yulin-youxian-server --lines 500 --nostream | grep -i flyway

# 第二步：记账表在不在，内容对不对
mysql -u yulin_fresh -p yulin_fresh -e \
  "SELECT installed_rank, version, type, success FROM flyway_schema_history ORDER BY installed_rank;"

# 第三步：数表
mysql -u yulin_fresh -p yulin_fresh -e "SHOW TABLES;"
```

正常情况：第一步能搜到内容；第二步是 10 行（第 1 行可能是 `type=BASELINE`，后续为 `type=SQL`），
`success` 全是 1；第三步能看到 36 张表，其中 27 张配送表、7 张 `marketing_lottery_*` 随机减免表。

### 按查到的情况对号入座

| 查到的情况 | 说明 | 怎么办 |
| --- | --- | --- |
| 日志里一行 Flyway 都没有，记账表也不存在 | **最常见**。上传的是修复之前打的 jar | 用最新源码重新 `mvn -DskipTests clean package`，替换 jar，重启。上传前可以先验一下包：`unzip -l fresh-delivery-server-*.jar \| grep spring-boot-flyway`，能搜到才是对的包 |
| 记账表在，但有 `success=0` 的行 | 建表跑到一半失败了 | **不要反复重启碰运气。**去日志里找那条失败的 SQL 和它的报错。最常见的是数据库账号缺 `CREATE` / `ALTER` / `INDEX` 权限，见《安装部署手册》2.1 节 |
| 记账表在，10 行全 `success=1`，但还是报某张表不存在 | 多半是连错库了 | 核对 `MYSQL_URL` 里的库名，和 `SHOW TABLES` 的实际结果对一遍 |
| 只有 `application_state` 不存在（全新空库） | 同第一行，旧 jar | 同第一行 |

### 🔴 两件千万不要做的事

1. **不要手工 `CREATE TABLE` 去"补"缺的表。** 手工建的表在索引、注释、字符集上很难和迁移脚本完全一致，当时看着能用，以后每次升级都会出岔子，而且这种不一致极难排查。正确做法永远是让程序自己建。
2. **不要为了让程序起来就删库重建。** 老数据（订单、用户、商品）都在 `application_state` 这张表里，删了就没了。

## 12. 中文显示成问号

> 这一条给技术人员看。

### 先分清是哪一种，处理方式完全不同

| | 情况 A：只是显示不对 | 情况 B：数据真的被写坏了 |
| --- | --- | --- |
| 表现 | 换个工具看又正常了 | 换什么工具看都是 `?` |
| 本质 | 数据是好的，看的方式不对 | **原字已经彻底没了** |
| 能不能修 | 能，换个看法就行 | ❌ **不能还原**，只能找原文重填 |

### 情况 A：只是显示的问题（常见，好修）

| 原因 | 解决 |
| --- | --- |
| 命令行查数据库时没指定字符集 | 加上 `--default-character-set=utf8mb4` 再查 |
| Windows 上用 PowerShell 的 `>` 把结果重定向到文件 | PowerShell 会把文件存成另一种编码，中文就花了。改成 `cmd /c "mysql.exe ... > 结果.txt"` |
| 数据库连接串里少了字符集参数 | `MYSQL_URL` 里要有 `useUnicode=true&characterEncoding=UTF-8&connectionCollation=utf8mb4_unicode_ci` |
| 终端窗口本身不是 UTF-8 | 换个终端，或者用图形化的数据库客户端看 |

### 情况 B：数据真的被写坏了

**一旦中文在写入的时候就被转成了 `?`，那些字的信息已经彻底消失了。** `?` 这个字符不携带任何关于原字的线索，所以没有任何工具能"解码"回去——这不是"打开方式不对"，是原件被销毁了。

这个项目真实遇到过一次：`server/data/storefront-state.json` 里 3 条 banner 的标题和副标题，**共 52 个字**被毁成了字面的 `?`。

#### 🔴 系统有一道保护会拒绝启动，**不要绕过它**

后端在读写这份数据时会检查内容里有没有"连续问号"，发现了就直接报错并拒绝启动：

```
状态数据包含连续问号，疑似历史乱码，已拒绝导入或读取: storefront
```

**看到这句话，第一反应不应该是"怎么让它别拦我"，而应该是"文件真的坏了"。** 上面那次就是——保护机制没有误判，文件是真坏的。

这道保护的意义在于：如果放行，坏掉的内容会被原样写进数据库，覆盖掉可能还完好的版本，那时候才是真的没救了。它拦的这一下，恰恰是在保住你最后的恢复机会。

**绝对不要做的事**：

- ❌ 找个开关把这个检查关掉
- ❌ 把 `?` 批量替换成空格或者删掉，让它"通过检查"
- ❌ 觉得"就几个字，先上线，回头再说"

这三种做法都是把损坏**固化**下来，并且从此再也看不出哪里坏过。

#### 正确的处理步骤

1. **先把坏掉的文件原样备份一份留档**，不要直接改。上一次留的是 `server/data/storefront-state.json.mojibake-backup-20260811`。
2. **去找原文。** 优先级：① 代码里的初始化数据（上一次的原文就在 `StorefrontService.seedBanners()` 里，banner 的初始文案都在那）；② 最近一次可用的备份；③ 都没有的话，只能人工重新录入。
3. **恢复，并且核对字数。** 恢复后每一条的字符数，要和坏掉的位置数量**精确吻合**（上一次是 52 个字，逐条对上了）。**字数对不上，说明你认错原文了**，别将就。
4. **重启验证。** 保护机制不再报错，就说明这份数据干净了。
5. 顺手再跑一次 `mysql -u yulin_fresh -p yulin_fresh < server/scripts/verify-mysql-migration.sql`，确认字符数和校验值都对得上。

### 怎么预防

| 做法 | 说明 |
| --- | --- |
| 数据库、表、连接**三处**都用 utf8mb4 | 见《安装部署手册》2.0 和 2.1 节。三处只要有一处不是，就会在那个环节丢字 |
| 命令行一律带 `--default-character-set=utf8mb4` | 少了它，查询和写入都可能出问题 |
| Windows 上别用 PowerShell 的 `>` 处理 SQL 文件 | 会写成 UTF-16。改用 `cmd /c "... < 文件"` / `cmd /c "... > 文件"` |
| **任何导入、导出、迁移数据之前，先备份** | 乱码几乎都是在这些环节产生的，而且**不可逆** |

## 还是解决不了？

联系技术支持时，请提供：

1. **具体现象**（"收不到单"太笼统，"店主 10:05 点了拣货完成，到 10:20 手机还没响"就很有用）
2. **发生时间**（精确到分钟）
3. **订单号或任务号**
4. **手机品牌和型号**（比如"红米 Note 12，MIUI 14"）
5. **你已经试过哪几步**
6. 如果能截图更好

技术人员那边可以查的东西：

```bash
pm2 logs yulin-youxian-server --lines 200    # 后端日志
```

后台「配送任务 → 详情 → 事件时间轴」里，能看到这一单每一步是几点几分谁做的，非常适合还原现场。
