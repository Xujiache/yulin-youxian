## 一、服务器需要什么

### 1.1 硬件与系统

| 项 | 最低要求 | 建议 | 为什么 |
| --- | --- | --- | --- |
| 操作系统 | Linux（CentOS / Ubuntu 均可） | —— | 现有系统就跑在 Linux 上 |
| 内存 | 2 GB | 4 GB | Java 服务 + MySQL 一起跑 |
| CPU | 2 核 | 2 核 | 派单计算量很小 |
| **磁盘剩余空间** | **50 GB** | **100 GB 以上** | ⚠️ 送达照片是最大的空间消耗，每单约 2 张、每张 150～250 KB。一年下来可能几十 GB |
| 带宽 | 1 Mbps | 3 Mbps | 位置上报很省流量，照片上传是主要占用 |

### 1.2 软件

| 软件 | 版本要求 | 检查命令 | 说明 |
| --- | --- | --- | --- |
| Java | **17 或更高** | `java -version` | 后端是 Spring Boot 4.1，低于 17 起不来 |
| MySQL | **8.0** | `mysql --version` | 必须是 8.0，字符集必须 utf8mb4 |
| Nginx | 任意较新版本 | `nginx -v` | 对外提供 HTTPS，转发给后端 |
| PM2 | 任意 | `pm2 -v` | 用来守护后端进程，现有系统就是用它 |
| Node.js | **22.14.0（建议）或 20.19.0 以上** | `node -v` | 只在**构建管理后台**时需要，可以在自己电脑上构建好再上传 |

### 1.3 端口

| 端口 | 用途 | 是否对外 |
| --- | --- | --- |
| 443 | HTTPS（Nginx） | ✅ 对外 |
| 80 | HTTP 跳转 HTTPS | ✅ 对外 |
| 8080 | 后端服务 | ❌ **只允许本机访问**，不要开放到公网 |
| 3306 | MySQL | ❌ **只允许本机访问** |

#### ⚠️ 8080 可能已经被别的程序占着

一台服务器上同一个端口只能给一个程序用。8080 是个非常常见的默认端口，**很可能有别的程序先占了**——开发这套系统的机器上就是这样，8080 被一个完全不相干的程序（`ayd-server.jar`）占着，所以本地测试全程跑在 8081。

**怎么知道被占了**：后端起不来，日志里出现下面这类话：

```
Web server failed to start. Port 8080 was already in use.
```

**怎么查是谁占的**：

```bash
# Linux（两条哪条能用用哪条）
ss -lntp | grep 8080
lsof -i:8080

# Windows：先查出占用者的编号（最后一列），再查这个编号是什么程序
netstat -ano | findstr :8080
tasklist | findstr 上一步查到的编号
```

**两种处理方式，二选一**：

| 方式 | 怎么做 | 什么时候用 |
| --- | --- | --- |
| 停掉占端口的程序 | 确认那个程序确实没用了，再停 | 只有在你**确切知道**那是个废弃程序时才这么干。停错了会搞坏别的业务 |
| **给本系统换个端口**（推荐） | 见下 | 不确定占用者是干什么的时候，一律选这个 |

**换端口要改两个地方，必须一起改**：

1. PM2 配置文件里加一行环境变量：`SERVER_PORT=8081`
2. Nginx 配置里**两处** `proxy_pass http://127.0.0.1:8080` 全部改成 `8081`（一处是 `/api/`，一处是 `/uploads/`，见 5.3 节）

改完 `pm2 restart yulin-youxian-server` 加 `nginx -t && nginx -s reload`。

🔴 **只改一边会出现 502 错误页**：后端在 8081 上听着，Nginx 还往 8080 送，谁也接不上。这是换端口时最常见的失误。

换完之后，本文档后面所有出现 `8080` 的命令（比如 `curl http://127.0.0.1:8080/api/ping`）都要相应改成你的新端口。

## 二、数据库

### 2.0 服务器上还没装 MySQL 的话，先装 MySQL

先确认一下到底有没有：

```bash
mysql --version
```

**能打印出 `8.0.xx` 就说明已经装好了，整节跳过，直接看 2.1。**（正常情况下应该是已经装好的——现有的禹邻优鲜系统就在用它。）

#### 从哪里下载：官网下不动，用阿里云镜像

这一条是 2026-08-11 实测的结果，能省你半天时间：

| 下载源 | 实测结果 |
| --- | --- |
| `dev.mysql.com`（MySQL 官网） | ❌ 直接被拒绝访问（403） |
| `cdn.mysql.com`（官网的下载服务器） | ❌ 找不到文件（404） |
| 清华 / 中科大 / 华为 / 网易 / 腾讯 这几个常用的国内镜像站 | ❌ 站点本身能开，但**根本没有 MySQL 这个目录** |
| **阿里云镜像** | ✅ **唯一能下下来的** |

阿里云上能拿到的最高版本是 8.0.28，够用：

```
https://mirrors.aliyun.com/mysql/MySQL-8.0/mysql-8.0.28-winx64.zip
```

（这是 Windows 免安装版，约 212 MB。**服务器是 Linux 的话不用下这个**，直接用系统自带的安装命令更省事：CentOS 用 `yum install mysql-server`，Ubuntu 用 `apt install mysql-server`。）

#### 🔴 一个能坑你半天的配置项：不要写 `skip-name-resolve`

MySQL 的配置文件（Windows 上叫 `my.ini`，Linux 上一般叫 `my.cnf`）里有一行可选配置叫 `skip-name-resolve`。网上很多教程都让加，**这套系统里千万别加**。

**它会造成什么**：这一行的作用大致是"别去查连接过来的那台机器叫什么名字"。加上之后，程序用 `127.0.0.1` 这个地址连数据库时，数据库就不再认为"这是本机来的"，于是把它当外人挡在门外，报这么一句：

```
ERROR 1130 Host '127.0.0.1' is not allowed to connect to this MySQL server
```

（意思是"不允许这台机器连接"。）

**为什么难查**：现象特别有迷惑性——账号建了、密码是对的、MySQL 服务也活着，就是连不上，而且报错完全不提密码的事。很容易让人反复去改密码、重建账号，白折腾。

**怎么解决**：把配置文件里 `skip-name-resolve` 这一行**删掉或者注释掉**（行首加 `#`），然后重启 MySQL 服务。

#### 配置文件里必须有的几行

关键是**字符集必须是 `utf8mb4`**，否则中文会存成一堆问号，而且是存进去就坏了、事后救不回来的那种坏。

```ini
[mysqld]
port=3306
bind-address=127.0.0.1
character-set-server=utf8mb4
collation-server=utf8mb4_unicode_ci
default-time-zone='+08:00'
max_connections=300
# 注意：这里绝对不要出现 skip-name-resolve

[client]
default-character-set=utf8mb4

[mysql]
default-character-set=utf8mb4
```

> 本地开发环境的完整安装命令（下载、解压、初始化、注册成 Windows 服务）记在 `server/scripts/local-mysql-runbook.md` 里，一步步照抄就能跑起来。

### 2.1 如果是全新服务器：先建库建用户

用 MySQL 管理员账号执行：

```sql
CREATE DATABASE IF NOT EXISTS yulin_fresh
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_unicode_ci;

CREATE USER IF NOT EXISTS 'yulin_fresh'@'127.0.0.1'
    IDENTIFIED BY '换成一个高强度随机密码';

GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, REFERENCES
    ON yulin_fresh.* TO 'yulin_fresh'@'127.0.0.1';

FLUSH PRIVILEGES;
```

> **权限说明**：`CREATE / ALTER / INDEX` 是必须的，因为程序启动时要自动建表。现有系统的授权就是这一套，够用，不需要改。

### 2.2 🔴 如果服务器上已经有系统在跑：**必须先备份，这次尤其不能省**

**这次上线和以往任何一次升级都不一样，先花两分钟读完下面这段。**

这套程序里有一个"启动时自动建表"的机制：程序一起来，先看看数据库里缺哪些表，缺的就建上，不用人手工执行任何 SQL。

**但是：这个机制到今天为止，在你的正式数据库上一次都没有真正运行过。**

原因是打包程序的时候漏装了一个必需的零件，导致这个机制整个被跳过了。最要命的是，它跳过的时候**一声不吭**——不报错、不警告、日志里连一个字都不写，看上去和"一切正常"一模一样。所以这个问题一直没人发现。数据库里现有的那张老表，当初是用别的办法建起来的（要么是手工建的，要么是更早的程序版本建的）。

这个漏掉的零件**已经补上了**。所以：

> **这次重启，是"自动建表"这个机制第一次真的在你的正式数据库上动手。**

它这一次会做三件事，按顺序：

| 顺序 | 做什么 | 会不会动你的老数据 |
| --- | --- | --- |
| 1 | 在数据库里建一张"记账表"，把现有状态登记为"第 1 版"，意思是"老表已经有了，不用再建" | 不动。只是多一张记账用的小表 |
| 2 | 按顺序建 27 张新表 | 不动。全是新建，不改老表 |
| 3 | 往其中一张表里写入 77 条默认配置 | 不动 |

**全程只有"新增"，没有"修改"，没有"删除"。** 已经用两种数据库排练过：一个全新的空库、一个只有那张老表的库（和你的正式库起始状态一样），两次都一次通过，没有重复建表、中文也没有乱码。

**但排练用的库里没有你的真实订单。这仍然是正式库第一次执行建表操作。** 所以：

🔴 **先备份，再重启。这不是走流程，这是这次上线唯一的后悔药。**

```bash
# 1. 停服务
pm2 stop yulin-youxian-server

# 2. 备份数据库
mkdir -p backup
mysqldump -u yulin_fresh -p yulin_fresh > backup/pre-delivery-$(date +%Y%m%d%H%M).sql

# 3. 备份数据目录（里面有上传的图片和 JSON 快照）
tar czf backup/pre-delivery-data-$(date +%Y%m%d%H%M).tar.gz server/data/

# 4. 记录校验值，防止备份文件本身损坏
sha256sum backup/pre-delivery-* > backup/SHA256SUMS

# 5. 看一眼备份文件不是 0 字节（0 字节的备份等于没备份）
ls -lh backup/pre-delivery-*.sql

# 6. 记下现在有哪些表，事后好对照
mysql -u yulin_fresh -p yulin_fresh -e "SHOW TABLES;" > backup/tables-before.txt
```

> **更稳一步（建议做）**：把刚导出的备份文件，往一个临时数据库里真的导一次，确认它能导进去。备份文件本身坏掉、或者导出到一半断了，都是真实发生过的事，而且只有在真需要它的时候才会发现。
>
> ```bash
> mysql -u root -p -e "CREATE DATABASE restore_drill CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
> mysql -u root -p restore_drill < backup/pre-delivery-刚才那个文件名.sql && echo "备份可用"
> mysql -u root -p -e "DROP DATABASE restore_drill;"
> ```

### 2.3 建表怎么跑（这个过程只发生一次）

**不需要手动执行任何 SQL。**后端启动时会自己检查数据库缺哪张表，缺的就建上。

> 这个负责自动建表的部件叫 **Flyway**。你会在两个地方看到这个词：启动日志里的 `Flyway ...` 开头的行，以及数据库里那张叫 `flyway_schema_history` 的记账表。下面提到"记账表"指的就是它。

本次会新增 **35 张表**（27 张配送表 + 7 张随机减免表 + 1 张统一会话表），另外写入 **77 条**默认配置，分 10 批执行：

| 批次 | 建了什么 | 张数 |
| --- | --- | --- |
| V2 | 骑手账号、登录会话、设备、班次 | 4 |
| V3 | 配送任务、任务事件流水、波次、波次站点 | 4 |
| V4 | 位置轨迹、最新位置、围栏事件 | 3 |
| V5 | 异常、凭证照片、称重核对 | 3 |
| V6 | 结算单、结算明细、服务分、申诉 | 4 |
| V7 | 路线计划、距离缓存、楼栋耗时统计、地点缓存 | 4 |
| V8 | 配置项、区域、消息、隐私号绑定、评价（同时写入 72 条默认配置） | 5 |
| V9 | 不建表，只补 2 条高德地图 Key 的配置 | 0 |
| V10 | 随机减免活动、阶梯、奖项、分享挑战、抽奖、赠品、订单决策；同时给配送任务增加减免和赠品快照列 | 7 |
| V11 | 统一会话表；同时加固任务事件幂等、结算明细唯一性、异常索引和高德配置 | 1 |

⏱ **建表这件事只会发生一次。** 建完之后，程序会在数据库里记账，以后每次重启都只是核对一下"这 10 批都做过了"，然后跳过，不会重复建、也不会把你的数据清掉。所以你只需要在**这一次**上线时格外小心。

V2–V9 只新增表和配置；V10 增加营销表和任务快照列；V11 会回填旧任务事件幂等字段、清理重复结算明细后建立唯一索引。

### 2.4 怎么确认建表成功（三项都要查）

启动后端之后（第三节），依次执行下面三组命令。**三项全对才算成功。**

**① 看记账表：应该正好 11 行**

```bash
mysql -u yulin_fresh -p yulin_fresh -e \
  "SELECT installed_rank, version, description, type, success
   FROM flyway_schema_history ORDER BY installed_rank;"
```

**期望**：一共 **11 行**，**每一行的 `success` 都必须是 1**。

- 老服务器（数据库里原来就有东西）：第 1 行 `type=BASELINE`（就是 2.2 节说的"把现有状态登记为第 1 版"），后面 9 行 `type=SQL`。
- 全新空数据库：11 行全是 `type=SQL`，没有 BASELINE 那一行。

两种都对，**看的是"一共 11 行、全部成功"**。

❌ **如果报错说 `Table 'yulin_fresh.flyway_schema_history' doesn't exist`（这张表根本不存在）**：说明自动建表机制**又被跳过了**，一张新表都没建。这不是数据库的问题，是程序包的问题——多半是上传的 jar 还是修好之前的旧包。**换成新打的 jar 重新上传、重启**，还不行就找技术支持，别自己反复重启。

❌ **如果有哪一行的 `success` 是 0**：建表中途失败了。**立刻停下来，不要重启碰运气**，把 `pm2 logs yulin-youxian-server --lines 200` 的报错发给技术支持。

**② 数表：配送表 27 张、随机减免表 7 张、统一会话表 1 张、全库 37 张**

```bash
mysql -u yulin_fresh -p yulin_fresh -e \
  "SELECT COUNT(*) AS delivery_tables FROM information_schema.tables
   WHERE table_schema='yulin_fresh'
     AND table_name NOT IN ('application_state','flyway_schema_history')
     AND table_name NOT LIKE 'marketing_lottery_%';"

mysql -u yulin_fresh -p yulin_fresh -e \
  "SELECT COUNT(*) AS lottery_tables FROM information_schema.tables
   WHERE table_schema='yulin_fresh'
     AND table_name LIKE 'marketing_lottery_%';"

mysql -u yulin_fresh -p yulin_fresh -e \
  "SELECT COUNT(*) AS all_tables FROM information_schema.tables
   WHERE table_schema='yulin_fresh';"
```

**期望**：`delivery_tables` = **27**，`lottery_tables` = **7**，`all_tables` = **36**。

**③ 数配置条数：应该是 74，而且中文不能是问号**

```bash
mysql -u yulin_fresh -p yulin_fresh -e \
  "SELECT COUNT(*) AS configs FROM delivery_config;"

mysql -u yulin_fresh -p yulin_fresh --default-character-set=utf8mb4 -e \
  "SELECT config_key, display_name FROM delivery_config WHERE config_key IN ('store.lat','amap.js_key');"
```

**期望**：`configs` = **74**。第二条应该显示出「门店纬度」和「高德 JS API Key（管理后台地图）」这样的中文。

❌ **如果中文显示成 `??` 或者一堆乱码**：先别急着改数据——大概率只是你当前这个命令行窗口的字符集不对（命令里的 `--default-character-set=utf8mb4` 就是干这个的）。换个工具再看一眼。确认数据库里存的真的坏了，见《常见问题》第 12 条。

**最后再确认老数据没被弄坏：**

```bash
mysql -u yulin_fresh -p yulin_fresh < server/scripts/verify-mysql-migration.sql
```

期望：`storefront` 和 `user-profiles` 两行都在，`checksum_ok` 都是 1。

> 这个脚本**只检查老数据完不完整**，不检查上面那 27 张新表建没建。所以①②③ 三项还是得单独查一遍，不能拿它代替。

## 三、后端

### 3.0 🔴 先把服务器时间调成中国时间（这一步千万别跳过）

**先做一件事**，在服务器上敲：

```bash
date
```

看输出末尾是不是 `CST` 和 `+0800`。是的话这一节可以跳过；**不是的话，按下面改**：

```bash
sudo timedatectl set-timezone Asia/Shanghai
date        # 再看一遍，确认变成了 CST +0800
```

改完要**重启后端**（`pm2 restart yulin-youxian-server`）才生效。

**如果这台服务器还跑着别人的东西，不方便改整机时区**，那就单独告诉后端"按中国时间跑"——在 PM2 配置里给 java 加一个启动参数：

```
-Duser.timezone=Asia/Shanghai
```

#### 为什么非改不可

后端算业务时间的时候，一律按**北京时间**算——这是写死在程序里的，不会变。但往数据库里写的那一刻，用的是**这台服务器自己的时间设置**。两边不一致，存进去的时间就是错的，差多少取决于差几个时区。

开发这套系统的机器就踩过这个坑：机器设的是东京时间（比北京快 1 小时），结果**接口返回和小票上写着「23:08 送达」，打开数据库一看却是「22:08」，整整差 1 小时**。

具体会碰到这些麻烦：

- **自己查数据库会被误导**。想核对某一单几点送到的，直接查表看到的时间是错的，跟骑手手机上、跟顾客小程序上显示的都对不上。
- **找问题的时候会找错方向**。看到时间对不上，第一反应是"程序把时间写错了"或者"骑手手机时间不准"，其实是服务器时区没设对，白折腾半天。
- **卡在半夜的单会被算到隔壁一天**。「今日已完成」「今天送了几单」「今天准时率多少」都是按送达时间落在哪一天来算的。时区差 1 小时，晚上 11 点多送的单就可能被算成前一天或第二天的。
- **夜间补贴可能给错**。晚上 8 点到早上 6 点这段有夜间补贴，时间错了就可能该给的没给、不该给的给了，跟骑手对账说不清。

#### 怎么确认改对了

服务器时间和数据库时间都看一眼：

```bash
date
mysql -u yulin_fresh -p -e "SELECT NOW();"
```

两个都应该是当前的北京时间。再让骑手实际送一单，对比 APP 上显示的送达时间和数据库里 `delivery_task` 表 `delivered_at` 这一列的值——**必须一模一样**，差一秒都行，差一小时就是时区还没弄对。

### 3.1 构建

在有 Java 17 和 Maven 的机器上（可以是自己电脑）：

```bash
cd server
mvn -DskipTests clean package
```

产物：`server/target/fresh-delivery-server-0.0.1-SNAPSHOT.jar`

把这个 jar 上传到服务器，替换原来的那个。

### 3.2 需要配哪些环境变量

环境变量写在 **PM2 的配置文件**里（通常叫 `ecosystem.config.js`，在服务器上，不在代码仓库里）。

#### 原来就有的（不要动）

`MYSQL_URL`、`MYSQL_USERNAME`、`MYSQL_PASSWORD`、`ADMIN_USERNAME`、`ADMIN_PASSWORD`、`WECHAT_*` 这一堆微信支付和小程序的配置——**保持原样**。

#### 这次新增的

```bash
# ── 配送功能总开关 ──
DELIVERY_ENABLED=true

# ── 门店坐标（给天气服务用；派单和路线用的是后台「调度参数」里的那份，两边填一样的值） ──

AMAP_JS_KEY=
```

### 3.3 启动

```bash
pm2 start yulin-youxian-server
pm2 logs yulin-youxian-server --lines 200
```

**日志里要看到什么**：
- 一批带 `Flyway` 字样的行，包括 `Successfully baselined schema with version: 1`，然后逐条 `Migrating schema ... to version "2" / "3" ... "9"`，最后 `Successfully applied 8 migrations`
  （如果是全新的空数据库，这里会是 9 个而不是 8 个——空库里连那张老表也要新建）
- `Started FreshDeliveryServerApplication in xx seconds`
- 没有 `ERROR` 开头的行

方便一点的查法：

```bash
pm2 logs yulin-youxian-server --lines 500 --nostream | grep -i flyway
```

🔴 **如果这条命令一行都搜不出来**，说明"自动建表"根本没启动——这正是 2.2 节讲的那个老毛病。**注意：这种情况下程序看上去是正常启动的，接口也能通，但配送的表一张都没建**，等你打开配送页面才会报错。所以别看到"启动成功"就放心，一定要按 2.4 节查一遍。

**日志里如果看到这些，说明有问题**：
- 一行 `Flyway` 都没有 → 上传的 jar 多半还是旧包，见 2.4 节 ①
- `Flyway ... failed` / `Migration ... failed` → 建表中途失败，看 2.4 节 ①
- `Table 'yulin_fresh.xxx' doesn't exist` → 表没建成，同上
- `Access denied for user` → 数据库账号密码不对
- `Communications link failure` → MySQL 没起来或地址不对
- `Port 8080 was already in use` → 端口被占，见 1.3 节

### 3.4 检查服务活着

```bash
curl http://127.0.0.1:8080/api/ping
```

返回内容里应该有 `"code":0`。

> 如果按 1.3 节换过端口，这里的 `8080` 要换成你实际用的端口。

## 四、配置门店坐标（必做）

装完之后**第一件事**就是把门店坐标改对，否则所有距离和时间都是错的。

1. 手机打开**高德地图 APP**
2. 搜到或找到「兴泾镇市场西北门 中国黄金对面」，把地图放大到能看清店门
3. **长按**店门口的位置，屏幕上会出现一个红色图钉，底部弹出的卡片里会显示一串数字，形如 `38.383423, 106.096144`

⚠️ **别填反了。**宁夏银川这边：纬度是 38 开头，经度是 106 开头。如果填反了，系统会以为门店在南极洲附近，所有单都会被标成"超远单"。

### 5.2 部署

把 `dist/` 整个目录上传到服务器上 Nginx 指向的静态目录（覆盖原来的）。

### 5.3 Nginx 配置要点

现有配置应该已经是这样了，检查一下：

```nginx
server {
    listen 443 ssl;
    server_name hqhjxt.vip;

    # 证书配置（保持原样）

    # 管理后台静态文件
    root /你的路径/dist;
    index index.html;
    location / {
        try_files $uri $uri/ /index.html;   # 单页应用必须有这行，否则刷新页面会 404
    }

    # 接口转发给后端
    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # ↓↓↓ 配送调度台新增要求：实时推送需要关闭缓冲，否则看板不刷新 ↓↓↓
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;
    }

    # 上传的图片（送达照片、异常照片）
    location /uploads/ {
        proxy_pass http://127.0.0.1:8080;
    }

    client_max_body_size 10m;   # 照片上传，别小于 10m
}
```

⚠️ **`proxy_buffering off` 这三行很关键。**调度台用的是"服务器主动推消息给浏览器"的技术，如果 Nginx 开着缓冲，消息会被卡住，看板上的数字就不会自动变，只能靠手动刷新。

改完执行：

```bash
nginx -t && nginx -s reload
```

## 六、骑手 APP（安卓）

### 6.1 打包前必须知道的三件事

⚠️ **签名已经配好了，别再造第二把；但签名文件和口令都不在代码仓库里，换台机器打包要先补上。打错版本会得到一个连不上服务器的包。先看完这一节。**

#### 第一件：签名已经配好，**不要再生成新的签名文件**

正式签名在这次交付里已经做完了：

| 项 | 实际值 |
| --- | --- |
| 签名文件（keystore） | 默认保存在当前用户目录的 `.yulin/rider-release.jks`。⚠️ **它必须在代码工作区外**，随交付单独给出 |
| 别名（alias） | `yulin-rider` |
| 口令（keystore 和 key 是同一个） | **见随交付一并给出的密码单。**为了不让口令散落在文档和代码里，这里不写明文 |
| 口令填在哪 | 默认放在当前用户目录的 `.yulin/rider-signing.properties`，也可由 CI 环境变量注入。**禁止写入仓库内的 `gradle.properties`** |
| 签名方案 | v2 + v3 双签名（v1 已关闭：minSdk 是 26，没有设备需要 v1） |

🔴 **千万不要再执行 `keytool -genkeypair` 另建一把签名。** 安卓是认签名的：换一把签名打出来的新包，在系统看来和手机上已经装着的旧包是"两个不相干的应用"，**覆盖安装会直接失败**，只能先把旧的卸载再装——卸载就意味着骑手手机上还没传上去的操作、登录状态全部丢掉。已经配好的签名再造一把，纯属给自己挖坑。

##### 🔴 `rider-release.jks` 和密码单必须单独备份，这件事比打包本身还重要

这个文件是这个 APP 唯一的"身份证"。**丢了就再也发不了更新**——以后修任何一个 bug、加任何一个功能，打出来的新包都装不到老用户手机上，只能让每个人**卸载重装，手机本地的数据全部清空**。而且**口令丢了和文件丢了后果一样**：没有口令就用不了这个签名文件。

所以现在就做，别等以后：

- **拷到至少两个互不相干的地方**：一个 U 盘 + 一个网盘（或者两个 U 盘分开放）。跟代码放在同一台电脑上不算备份
- **密码单单独存一份**，别和 .jks 放在同一个目录里（两样东西一起丢，等于一样都没备）
- **两样都交一份给店主自己收着**，并且告诉他这是什么、丢了会怎样
- 以后换电脑、换技术人员，第一件要交接的就是这个文件加这张密码单

> 以后如果确实需要换口令，用 `keytool -storepasswd` 改就行——那只换开锁的钥匙，签名本身不变，已经发出去的包不受影响。改完记得同步更新密码单和工作区外的 `rider-signing.properties`。

#### 第二件：换台机器打包，先补上两个不进版本库的文件

`rider-release.jks`（签名文件）和 `rider-signing.properties`（签名配置）都必须放在**代码工作区之外**。这是有意为之，避免私钥或口令跟着代码、压缩包和备份到处传播。代价是：**新机器 clone 代码后不能直接打正式包**，必须先从安全备份恢复这两个文件。

**换机器后做这两步：**

**第 1 步：在用户目录创建私有签名目录**

Windows 默认位置是 `%USERPROFILE%\.yulin`，Linux/macOS 默认位置是 `~/.yulin`。创建目录后，把安全备份中的 `rider-release.jks` 放进去：

```bash
mkdir -p ~/.yulin
chmod 700 ~/.yulin
# 然后把备份里的 rider-release.jks 拷到 ~/.yulin/
```

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\.yulin"
# 然后把备份里的 rider-release.jks 拷到这个目录
```

**第 2 步：创建工作区外的签名配置**

用文本编辑器创建 `.yulin/rider-signing.properties`，内容如下。路径必须是 keystore 的绝对路径：

```properties
RIDER_KEYSTORE_PATH=<工作区外的 rider-release.jks 绝对路径>
RIDER_KEYSTORE_PASSWORD=<密码单上的 keystore 口令>
RIDER_KEY_ALIAS=yulin-rider
RIDER_KEY_PASSWORD=<密码单上的 key 口令>
```

Linux/macOS 再执行 `chmod 600 ~/.yulin/rider-signing.properties ~/.yulin/rider-release.jks`。CI 可直接注入上述四个同名环境变量；环境变量优先。若外部文件放在其他位置，用环境变量 `RIDER_SIGNING_PROPERTIES_FILE` 指定。

⚠️ **不要把这四项写进仓库内的 `rider-android/gradle.properties`、文档、脚本或聊天记录。**

##### 🔴 缺少签名材料时，release 构建会立即失败

构建脚本采用 fail-closed：缺少 keystore、路径、别名或任一口令时，`assembleRelease` 会明确报错，不会悄悄生成未签名 APK。打包和验签使用同一条命令：

```bash
./gradlew :app:verifyReleaseSignature
```

看到 `[rider] release APK 签名校验通过` 才能交付。

#### 第三件：调试包连的是开发机地址

代码里两个版本连的服务器地址不一样：

| 版本 | 连的地址 | 能不能给店里用 |
| --- | --- | --- |
| debug（调试包） | `http://10.0.2.2:8080` | ❌ 这是模拟器专用的本机地址，装到真手机上什么都连不上 |
| release（正式包） | `https://hqhjxt.vip` | ✅ 就是它 |

所以**必须打 release 包**，也就是下面 6.2 的命令。

### 6.2 打包命令

**确认 6.1 第二件的两个工作区外文件都到位，并设置好 `ANDROID_SDK_ROOT` 或 `ANDROID_HOME`，再执行下面的命令。**

```bash
cd rider-android

# 现在没有高德 Key，直接打
./gradlew :app:verifyReleaseSignature

# 以后申请到高德 Key 了（把 xxx 换成 Android 端的 Key）
./gradlew :app:verifyReleaseSignature -PAMAP_KEY=xxx
```

产物：`rider-android/app/build/outputs/apk/release/app-release.apk`。

建议改个名字再发出去，比如 `禹邻优鲜骑手-v0.1.0.apk`。

> **没填 Key 会怎样**：APP 能正常装、正常用，只是地图页面显示不出底图。点"导航"会自动跳到手机上装的高德/百度地图 APP，照样能导航。

#### 安装包有点大：两种打法，按手机新旧二选一

这个 APP 里装着高德地图的导航库，它比较占地方，而且**每一种手机芯片都要单独带一份**。带几份，包就有多大：

| 打法 | 包多大 | 能装在什么手机上 | 命令 |
| --- | --- | --- | --- |
| **默认（推荐先用这个）** | **99.2 MB** | ✅ **所有安卓手机**，新的旧的都能装 | `./gradlew :app:verifyReleaseSignature` |
| **小包** | **70.5 MB**（省 29 MB） | ⚠️ 只能装 **64 位手机**。2015 年以后出的安卓手机基本都是 64 位的 | `./gradlew :app:verifyReleaseSignature -PRIDER_ABI=arm64` |

**怎么选：**

- **拿不准就用默认的 99.2 MB 那个。**多出来的 29 MB 换的是"绝对不会因为手机太旧装不上"，对只装一两台手机的场景，这个保险很划算。
- 如果你要**用微信把安装包发给家里人装**，99.2 MB 已经很贴近微信单个文件的大小上限，传起来慢，网络差的时候还容易传到一半失败。这种情况下，**确认家里人的手机都是近几年买的（2015 年以后基本都满足）**，就可以用小包，微信传起来会明显轻快一些。
- 另外两个避开微信的办法：**用数据线直接拷**（最稳，也最快，见 6.3 节），或者传网盘让手机下载。用这两种方式就不用为了大小纠结，直接打默认包。

🔴 **小包装不上的时候是什么样**：如果误把小包装到一台老的 32 位手机上，安装会失败，提示大多是"应用与你的手机不兼容""解析包时出现问题"。**遇到这个提示，重新用默认命令打一个 99.2 MB 的包给他装就行**，不用改任何代码，也不是包坏了。

> 提示：`-PRIDER_ABI=arm64` 只影响 release 正式包。调试包不受影响（它必须多带一份电脑模拟器用的芯片版本，否则装不进模拟器）。

#### 🔴 打完包的第一件事：装一台真安卓手机跑一遍

**这一步不能省，也不能用模拟器代替。**

开发期间的验证全部是在电脑上的模拟器里做的，而模拟器用的是电脑的 x86_64 芯片架构，**安装包里高德地图那部分的库文件只提供了手机用的 arm 架构版本**。也就是说：**地图、导航、高德定位这一整层，在模拟器上一次都没有被真正执行过。** 这不是"还没在真机上复核一遍"，是"压根没跑起来过"。

拿到 APK 后请在真手机上重点确认这几项：

| 确认什么 | 正常应该是 |
| --- | --- |
| APP 能装上、点开不闪退 | 能进到登录页 |
| 登录、上班 | 后台「配送调度台」第四列能看到这个人 |
| 上班后位置上报 | 后台看得到位置时间在刷新，不出现「定位陈旧」红标 |
| 地图页面 | 没有高德 Key 时**本来就是空的，这是正常的**（见上面那条「没填 Key 会怎样」）。**关键是不能闪退** |
| 点「导航」 | 能跳到手机上装的高德 / 百度地图 |

任何一项出问题都要先解决再交给店主，不要拿"模拟器上是好的"当验证结论。

### 6.3 把安装包发到手机上

三种方式，随便挑：

| 方式 | 怎么做 | 注意 |
| --- | --- | --- |
| 微信 | 把 apk 发到微信文件传输助手，手机上点开 | 微信可能提示"文件格式不支持"，需要点右上角「···」→「用其他应用打开」 |
| 数据线 | 手机连电脑，把 apk 拷到手机存储里，用文件管理器点开 | 最稳 |
| 网盘 | 上传到网盘，手机下载 | 有些网盘会限速 |

### 6.4 🔴 允许安装未知来源应用（关键步骤，一定要看）

**安卓 8.0 以后，"允许安装未知来源"不再是一个总开关了。**

以前（安卓 7 及更早）：设置里有一个"未知来源"开关，打开一次，以后装什么都行。

现在（安卓 8 及以后）：**是按"你从哪个 APP 点开的安装包"分别授权的**。也就是说：
- 你从**微信**点开 apk → 要授权给**微信**
- 你从**文件管理器**点开 apk → 要授权给**文件管理器**
- 你从**浏览器**下载后点开 → 要授权给**浏览器**

给微信授权了，不代表用文件管理器装的时候也能装。**这是最容易卡住的地方**，很多人以为自己已经开过了。

#### 操作步骤（推荐用"文件管理器"这条路，最稳）

**第 1 步**：把 apk 传到手机上（6.3 节任选一种）

**第 2 步**：打开手机自带的「文件管理」APP，找到那个 apk 文件，点它

**第 3 步**：会弹出一个提示，大意是"为了安全，你的手机不允许安装来自此来源的未知应用"，旁边有一个「设置」或「去设置」按钮 —— **点它**

> 如果没弹出提示，直接开始安装了，说明这个来源以前已经授权过，跳到第 6 步。

**第 4 步**：跳转到一个叫「安装未知应用」的页面，上面写着当前这个 APP（比如"文件管理"）的名字，下面有一个开关叫**「允许来自此来源」**或**「允许安装应用」**

**第 5 步**：把这个开关**打开**，然后按手机的返回键回到刚才的安装界面

**第 6 步**：点「安装」，等几秒钟

**第 7 步**：⚠️ **这里国产手机会再拦一道**。可能出现的情况：

| --- | --- | --- |

| 华为 / 荣耀 | 提示"该应用未经过安全检测" | 点「继续安装」/「仍要安装」 |

| 三星 | 提示 Play Protect 拦截 | 点「仍然安装」 |

**第 8 步**：安装完成，桌面上出现「禹邻优鲜骑手」图标

#### 各品牌"安装未知应用"设置的位置（找不到时对着查）

### 6.5 装好之后必须做的三件事

装上不等于能用。**在把手机交给送货的人之前，当面陪着做完这三步**：

| 步骤 | 做什么 | 不做的后果 |
| --- | --- | --- |
| 1️⃣ 登录 + 改密码 | 用后台建账号时给的手机号和初始密码登录，系统会强制要求改一个新密码 | 登不进去 |
| 2️⃣ 三步授权 | 跟着 APP 的引导页走完：①定位+通知权限 ②位置信息授权同意书 ③后台定位选「始终允许」 | 少任何一步都不能上班接单 |
| 3️⃣ **保活向导** | 「我的 → 设置 → 保活向导」，每一项都点进去实际设置一遍 | **锁屏后位置停止上报、收不到新单。这是最常见的故障** |

🔴 **第 3 步必须现场陪同做完，不能让送货的人自己回家做。**向导里的每一项都要点开、跳到系统设置里真的改一次、回来看到状态变成"已完成"才算数。这一步大约 15 分钟，一台手机只需要做一次。

## 九、出问题了怎么退回去

按影响从小到大，能用上面的就别用下面的。

| 级别 | 什么情况用 | 怎么做 | 影响 |
| --- | --- | --- | --- |
| **一级** | 派单派得明显不对，想让**新单先别再进配送流程** | 后台「配送调度台」右上角把「自动派单」关掉 | 秒级生效。🔴 **这不是"改成手动派单"，是"新单不再进配送"**：关掉之后订单页的「拣货完成」按钮会变回原来的「配送」按钮，**建不出新的配送任务**，「待派积压」自然也不会有新单可派。已经在跑的任务不受影响，仍可在调度台上处理完 |
| **二级** | 配送功能整体有问题，想先回到老流程 | PM2 配置里把 `DELIVERY_ENABLED` 改成 `false`，**必须重启后端**才生效 | 配送功能整体停用，订单回到"后台手动点已完成"的老模式。数据都还在。**具体停什么、留什么见下面的表**，不是全站关停 |
| **三级** | 新版程序有 bug | 把 jar 换回上一个版本，重启 | ✅ **安全**。新建的 27 张表留着不删，老版本程序不认识它们，但也不会报错 |
| **四级** | 数据被弄坏了 | 用第 2.2 节的备份恢复数据库 | ⚠️ **最后手段**。会丢失备份时间点之后的所有数据（订单、支付记录都会丢） |

💡 **只是想"这一单我自己挑人派"，不要动一级回退。** 在调度台「待派积压」里点那一单的「立即派单」或「指派给…」就行，这两个按钮不受「自动派单」开关影响。一级回退针对的是"系统整体派得不对，先全停下来"这种情况。

🔴 **系统里没有"只手动派单"这个模式，别去找。**「自动派单」这个开关同时管着"自动派"和"订单页能不能建配送任务"两件事，代码里是耦合的（评估过，只有一个人送货时"自动派给唯一的人"和"手动派"结果完全一样，交付前不值得为拆开这个耦合去动前端）。所以关掉它得到的不是手动模式，而是整套配送停摆。

⚠️ **永远不要手动 `DROP TABLE` 删配送表。**留着不占多少空间，删了以后想恢复就麻烦了。

### 9.1 二级回退（`DELIVERY_ENABLED=false`）到底停了什么

这是**整个配送域的总闸**，和一级回退的「自动派单」开关不是一回事：一级只管派单这一环，总闸管的是整个配送功能。关掉之后并不是"整站关停"，界限如下。

#### 🔴 关闸后会停的

| 停什么 | 具体表现 |
| --- | --- |
| 自动派单 | 每 5 秒跑一次的派单循环直接空转，不再派任何单。后台的「手动触发调度」也会被拒绝并给出明确提示 |
| 新建配送任务 | 订单页点「拣货完成」会被**拒绝**并提示配送功能已停用，「批量拣货完成」也是整批一次性拒掉（不会让你一单一单看同一条错） |
| 骑手端**所有写操作** | 上报位置、上班下班、接单、取货核对、送达、上报异常……全部被拒绝，返回错误码 `1000` |

#### ✅ 关闸后仍然可用的

| 留什么 | 为什么留着 |
| --- | --- |
| 骑手**登录、登出、改密码、定位授权** | 🔴 **这是有意保留的。**如果连登出都关掉，骑手手机上就会留着一个再也退不掉的会话，后台还在跑定位——人退不出去、定位停不下来，比停用本身更麻烦。所以这几个接口不受总闸约束 |
| 骑手端的**查看类操作** | 手上已有的任务、历史记录还能看，不至于关闸后 APP 变成一片空白 |
| 管理端**查看和取消在途任务** | 关闸时路上可能还有没送完的单，得让你能看到、能收尾 |
| 管理端**改配置** | 「调度参数」照常能改，不然你连恢复前的准备工作都做不了 |

#### 关闸后订单页会自动变回老样子

关闸之后，订单页上的「拣货完成」会**自动退回成原来的「配送」按钮**，你按老流程操作即可——这是特意做的：如果按钮还留在那儿，点下去才被拒绝，等于每单白点一次。

> 这里有个容易看错的地方：关闸后你去看「调度参数 → 派单」，会发现「自动派单」显示成关闭状态。**这只是总闸压着它显示成关闭，数据库里你原来的设置一个字都没改**。总闸合上（改回 `true` 并重启）之后，你之前设的值原样恢复，不需要重新设置一遍。

#### 怎么恢复

把 `DELIVERY_ENABLED` 改回 `true`，**再重启一次后端**（`pm2 restart yulin-youxian-server`）。这个开关是环境变量，**改完不重启不生效**，改前改后都一样——这一点和后台「调度参数」里那些改完立即生效的设置不同，别混了。

恢复之后建议按 5.4 节和第八节的方式确认一遍：订单页显示的是绿色的「拣货完成」，调度台右上角「实时连接正常」。

## 十、日常维护

### 10.1 常用命令

```bash
pm2 status                              # 看服务是不是活着
pm2 logs yulin-youxian-server --lines 100   # 看最近 100 行日志
pm2 restart yulin-youxian-server        # 重启
df -h                                   # 看磁盘还剩多少
du -sh server/data/uploads/             # 看照片占了多大
```

### 10.2 需要定期看一眼的

| 频率 | 看什么 | 正常是什么样 |
| --- | --- | --- |
| 每天 | 后台「配送调度台」有没有红色告警 | 没有红色 |
| 每周 | 磁盘剩余空间 `df -h` | 剩余 20% 以上 |
| 每周 | 后台「数据备份」页面，最近一次备份时间 | 是最近几分钟内的 |
| 每月 | 照片目录大小 | 增长符合预期（大约每 100 单 40 MB） |

> ⚠️ **备份文件名的时区，这次改了。**「数据备份」生成的文件形如 `backup-20260812-143005-123-auto.zip`，名字里的时间**现在是北京时间**，改之前用的是 UTC。所以**本次升级之前生成的旧备份，文件名上的时间比实际早 8 小时**，新旧混在一个目录里时，按文件名排序会错位。
>
> 页面列表和"只留 30 份"的清理逻辑**都是按文件的实际修改时间来的，不看文件名**，所以列表顺序是对的，也不会误删新备份。要挑恢复点，以页面列表为准；只有在服务器上直接 `ls` 翻文件时才需要注意这 8 小时的差。等旧备份被轮换掉，这个差异就不存在了。

### 10.3 系统自己会做的事（不用管）

| 时间 | 做什么 |
| --- | --- |
| 每 5 秒 | 检查有没有单要派 |
| 每 60 秒 | 检查有没有送货人掉线、有没有单快超时 |
| 每 10 分钟 | 释放过期的隐私号绑定（没开隐私号时空跑） |
| 每小时 | 清理过期的距离缓存 |
| 每天 01:00 | 生成前一天的结算单（你不用结算，可以不管） |
| 每天 02:00 | 重新统计每栋楼的平均交付耗时，让预计送达时间越来越准 |
| 每天 03:30 | 删除 90 天前的位置轨迹 |
| 每天 04:00 | 清理过期的登录会话 |
| 每天 05:00 | 检查配送任务和订单有没有对不上的，有就告警 |

### 10.4 照片满了怎么办

一年以上的送达照片可以删（**记录会保留，只是点开看不到图**）：

```bash
# 先看看有多少
du -sh server/data/uploads/delivery/*

# 确认无误后删除指定月份（例：删 2025 年 8 月的）
rm -rf server/data/uploads/delivery/202508
```

⚠️ 删之前建议先打包备份到别的地方。涉及纠纷的订单照片千万别删。
