# 管理后台调度台设计

## 0. 最重要的一条设计原则

调度中心的实践经验里有一条反直觉但极其重要的结论：

> 值班人员只需要盯四件事：**待派积压、在途超时风险、未关闭异常、在岗运力不足**。这四件事都必须能以**列表**形式筛选。地图是辅助，不是主界面。只有热力图而没有状态筛选的调度中心，不会减少一个电话。

失败模式非常具体：做了一个漂亮的地图，但没人能从上面派单，最后调度还是靠打电话。

所以本模块的主界面是**四列队列看板**，地图是右侧/下方的辅助面板。培训时也要**先教筛选，再教地图**。

## 1. 技术栈与集成方式

| 项 | 说明 |
| --- | --- |
| 宿主 | `art-lnb-master/`（Art Design Pro 模板，Vue 3.5 + Vite 7 + Element Plus 2.11 + TS） |
| 新增路由 | 在 `src/router/modules/fresh.ts` 的 `freshRoutes.children` 下追加（**由 Wave 0 主控修改，其他 Agent 不碰这个文件**） |
| 新增视图 | `src/views/fresh/delivery/**`（全新目录，无冲突） |
| 新增 API | **`src/api/delivery.ts`（新文件）**，不要动 `src/api/admin.ts`（那是高冲突文件） |
| HTTP 封装 | 复用 `src/utils/http`，令牌自动注入，响应包 `{code,msg,data}` 自动解包 |
| 样式 | 复用 `src/views/fresh/style.scss`（`.fresh-page` / `.fresh-card` / `.fresh-toolbar` / `.metric-grid`） |
| 地图 | 高德 JS API 2.0（`@amap/amap-jsapi-loader`），**Key 从后端 `/api/admin/delivery/configs` 下发，不硬编码** |
| 主题 | 绿色系（`#00843D` / `#60C041`），金额用 `#00843D` 加粗 |

**必须遵守的模板约定**（照抄现有 fresh 视图的写法）：
- SFC 里 `defineOptions({ name: 'XxxName' })` 必须与路由 `name` 一致，否则 `keepAlive` 失效
- 列表页 `meta.keepAlive: true`，详情/编辑页 `meta.isHide: true`
- 图标用 iconify 的 `ri:*`
- 每个改动型操作都要 `ElMessageBox.confirm` 二次确认
- 图片 URL 一律走 `resolveFreshAssetUrl()`
- 金额后端给分，前端 `/100` 展示

### 数据获取

- 首屏 `GET /api/admin/delivery/board` 拉全量
- 之后接 `GET /api/admin/delivery/board/stream`（SSE）增量更新
- SSE 断开时降级为 5 秒轮询 `board`，并在右上角提示「实时连接已断开，正在轮询」
- 地图位置单独用 `GET /api/admin/delivery/map` 每 5 秒刷（比 `board` 轻得多）
- 页面 `onDeactivated` / `onUnmounted` 必须关闭 SSE 和定时器

### 各队列的卡片与动作

**待派积压**（按 `holdUntilAt` 升序）

```
┌────────────────────────────────────────────┐
│ PS20260811000123    🧊冷冻   待派 02:15 ⏱  │  ← 压单倒计时
│ 阳光小区 3号楼 2单元 1201                   │
│ 8件 6.5kg · 承诺 16:00 · 剩余 20:00        │
│ 💡 建议派给 张三（顺路度高，得分 0.81）      │  ← 系统建议，一键采纳
│ [立即派单] [指派给…] [查看建议] [取消]      │
└────────────────────────────────────────────┘
```

- 「立即派单」跳过压单，走系统推荐
- 「指派给…」弹出骑手选择器，**每个骑手旁边显示得分和 blockers**，不是让调度员盲选
- 「查看建议」展开 `dispatch/suggest` 的完整 breakdown（顺路度/超时/负载/冷链/等级各占多少分）

**在途超时风险**（按剩余时间升序）

卡片显示骑手、当前站点、剩余时间倒计时（< 5 分钟标红闪烁）、超时后自动置顶。动作：`[改派] [联系骑手] [联系顾客] [补时]`。

**未关闭异常**（按 severity 降序）

卡片显示异常类型、任务、骑手、上报时间、照片缩略图、挂起倒计时。动作：`[处理] [查看照片] [联系顾客]`。处理弹窗里选择 `resolutionType`（继续配送/退回门店/改派/发起退款/取消/忽略）+ 是否免除骑手责任（**默认勾选免除**）。

**在岗骑手**（按 `loadRatio` 升序，空闲的在最上）

```
┌────────────────────────────────────────────┐
│ 👤张三 QS000001  🟢在线 4h  🔋68%           │
│ 负载 ███░░░░░ 3/8  12.5/30kg               │
│ 当前波次 BC0012 · 第2/5站 · 预计17:05返店   │
│ 今日 20单 准时95% 服务分98                  │
│ ⚠️ 疲劳提醒中，12:20 前不派单                │  ← 疲劳状态显式展示
│ [派单] [查看轨迹] [发消息] [强制下班]        │
└────────────────────────────────────────────┘
```

位置陈旧（> 120 秒无上报）时整卡标红 + 「定位异常」角标。

### 拖拽派单

任务卡片可拖拽到骑手卡片上完成指派（`vuedraggable` 或原生 HTML5 DnD）。放下时：
1. 前端先本地校验（`loadRatio ≥ 1` 或疲劳停派 → 直接拒绝并提示）
2. 弹 `ElMessageBox.confirm`，展示「派给张三，预计新增里程 320 m，其他订单不会超时」
3. 调 `POST /tasks/{id}/assign`
4. 失败回滚 UI

**强制指派**（`force = true`）必须二次确认并要求填写原因，因为它会绕过并发上限。疲劳停派**不可绕过**，前端连按钮都不要给。

## 4. 其他页面要点

### 配送任务页

复用现有订单管理页的交互语言（`ElSegmented` 状态筛选 + 表格 + 详情弹窗）。列：任务号、订单号、状态、骑手、地址、时间窗、ETA、超时、异常数。筛选：状态、日期、骑手、区域、超时与否。

任务详情弹窗要有三个 Tab：**基本信息** / **事件时间轴**（`delivery_task_event` 全量，含改派留痕）/ **凭证照片**。

### 波次详情页

左侧站点列表（可拖拽重排），右侧地图（规划路线 + 实际轨迹叠加对比）。顶部展示 `optimizerName` / `matrixProvider` / `objectiveValue` / `solveMillis`，方便评估算法效果。支持「重新规划」和轨迹回放（时间轴拖拽 + 倍速播放）。

### 骑手管理页

列表 + 详情。详情页含：基本资料、装备、健康证（到期高亮）、今日/本周统计、班次历史、服务分流水、结算记录、历史轨迹回放。

新建骑手时返回的初始密码**只显示一次**，照抄现有「打印代理密钥」页面的一次性展示 + 复制按钮交互。

### 调度参数页

**不要硬编码表单字段。** `GET /api/admin/delivery/configs` 返回每一项的 `displayName` / `description` / `valueType` / `minValue` / `maxValue` / `editable`，前端按 `category` 分组动态渲染。这样后端加配置项时前端零改动。

分组：门店 / 派单 / 路径 / ETA / 轨迹 / 围栏 / 疲劳 / 收入 / 配送 / 公平秤 / 隐私 / 推送 / 服务分。

`eta.ebike_speed_kmh` 的 `maxValue` 是 15，前端要显示合规说明：「依据 GB/T 46862-2025，电动车平均速度不得高于 15 km/h」。

### 配送分析页

用 echarts 6（模板已有）。图表：日单量与准时率双轴折线、平均配送时长趋势、骑手人效对比柱状、异常类型分布饼图、**楼栋难度榜**（交付时长 top 20，直接指导运营）、时段单量热力图。

## 5. 与既有订单页的集成

在 `src/views/fresh/orders/index.vue` 增加（**这个文件由管理后台 Agent 修改，但改动要小而集中**）：

1. 新增列「配送」：数据来自 `GET /api/admin/delivery/tasks/by-orders?orderIds=`（对当前页可见订单批量查询后前端合并，**不改既有订单接口**），显示任务状态 + 骑手名 + ETA，点击跳配送任务详情
2. 「配送」按钮语义变更：配送域启用时改为「拣货完成」，弹出拣货确认框（件数、总重、冷链等级、拣货备注**四项，最终未做电子秤照片上传**），调 `POST /api/admin/delivery/orders/{id}/pick-ready`
3. 批量「配送」同理改为批量拣货完成
4. 保留旧行为作为开关兜底（`dispatch.enabled = false` 时按原逻辑走）

**这是唯一需要改既有文件的地方，改动必须小、必须有开关、必须可回退。**

## 7. 验收标准

1. 四个队列都能独立筛选，不依赖地图就能完成派单。
2. 超时订单有可搜索标记，且有处理入口。
3. 异常原因能追溯回原始订单。
4. 骑手 App 与后台显示的是**同一个任务号**。
5. 改派有留痕且可回查。
6. 自动/手动派单切换后，状态模型保持一致（同一个事实来源）。
7. SSE 断开时自动降级轮询，用户无感。
8. 页面切走后所有定时器和 SSE 都已释放（切 10 次不涨内存）。
