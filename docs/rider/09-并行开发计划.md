# 并行开发计划（10 Agent）

## 0. 并行开发能否成功，只取决于两件事

1. **契约先冻结。** 所有 Agent 依赖同一份数据库设计（03）和 API 契约（04）。契约不冻结，并行就是灾难。
2. **文件归属互斥。** 两个 Agent 改同一个文件 = 冲突 = 返工。所以本文档的核心是一张**文件归属表**，它比任何任务描述都重要。

共享文件（`pom.xml`、`WebConfig.java`、`application.yml`、`fresh.ts` 路由、`app.json` 等）**全部由 Wave 0 主控一次性改完**，之后对所有 Agent 只读。这是让并行成立的关键手段。

## 1. 波次划分

```
Wave 0（串行，1 个主控 Agent，约占总工作量 8%）
   契约冻结 + 全部共享文件改动 + 项目骨架
        ↓  必须 100% 完成并通过编译才能进入 Wave 1
Wave 1（并行，10 个 Agent，约占总工作量 75%）
   A1 A2 A3 A4 A5 A6 A7 A8 A9 A10 同时开工
        ↓  各自单元测试通过
Wave 2（半并行，3–4 个 Agent，约占总工作量 17%）
   联调 + 端到端 + 性能 + 合规核查 + 文档收尾
```

## 4. 各 Agent 任务详情

### A1 · 后端核心与账号

**交付物**
1. Flyway `V2`–`V8` 七个迁移文件，严格照 03 文档的 DDL，**一个字段都不能差**
2. `V8` 里插入 `delivery_config` 的全部默认配置项（03 文档 §7 的表格）
3. 27 张表的 Repository（`JdbcTemplate` + `RowMapper`），统一的分页/条件构造工具
4. `RiderAccountService`：骑手 CRUD、初始密码生成、BCrypt、停用/启用/强制下班
5. `RiderAuthService`：登录、令牌签发、刷新、撤销、`rider_session` 管理
6. `RiderAuthInterceptor` + `CurrentRiderContext`（实现类，注册由 Wave 0 完成）
7. `RiderShiftService`：上下班、上班检查校验、疲劳计算（4h/8h/12h）、休息
8. `DeliveryConfigService`：带内存缓存的配置读取，变更时失效
9. 04 文档 §1.1 §1.2 和 §2.4 §2.7（configs 部分）的全部接口
10. 每日巡检任务：软引用一致性检查

**关键约束**
- BCrypt 需要 `spring-security-crypto`。**若 `pom.xml` 未引入，不要自己加**，报给主控。可先用 JDK 自带的 `PBKDF2WithHmacSHA256` 实现 `PasswordHasher` 接口，后续替换。
- 疲劳规则是合规硬要求，必须有单元测试覆盖 4h/8h/12h 三个阈值。
- `location_consent_at` 为空时任何位置写入都要拒绝——这个校验方法由 A1 提供，A5 调用。

**测试**：Repository 用 H2（参考现有 `MysqlStateStoreTests` 的建法）；疲劳计算、令牌过期、密码策略要有单测。

### A2 · 后端任务生命周期

**交付物**
1. `DeliveryTaskStateMachine`：10 个状态、全部合法流转、非法流转抛 `1011`
2. `DeliveryTaskService`：创建（`pick-ready`）、查询、状态流转、幂等（`clientEventId`）
3. `DeliveryTaskEventRecorder`：每次流转写 `delivery_task_event`
4. `OrderStatusBridge`：**全系统唯一允许调用 `StorefrontService` 的类**，实现 01 文档 §5 的同步表
5. `DeliveryWaveService`：波次创建、追加任务、站点顺序、完成
6. 04 文档 §1.3、§2.2（pick-ready 部分）、§2.3 的接口

**关键约束**
- 幂等是核心：同一个 `clientEventId` 重复提交必须返回上次结果且无副作用。建议用一张轻量的 `client_event_id → result` 内存 LRU + 事件表查询兜底。
- `OrderStatusBridge` 调用 `StorefrontService` 时要注意那边是 `synchronized` 的，**不要在持有数据库事务时长时间调用**，先提交本地事务再同步订单。
- 状态机必须是纯函数（`canTransit(from, to)`），便于测试。

**测试**：状态机全流转矩阵（合法/非法各一条）；幂等重放；订单状态同步。

**交付物**（严格照 05 文档 §1–§4、§7、§8）
1. `HoldingWindowService`：压单窗口动态收缩
2. `BatchingService`：四层分层聚类 + 簇约束
3. `RiderScoringService`：五项加权评分 + 硬性排除 + breakdown 输出
4. `DispatchEngine`：主流程编排
5. `ReassignmentService`：风险评估 + 自动改派
6. `CapacityAlertService`：运力预警
7. `DispatchScheduler`：`@Scheduled` 循环 + `tryLock` 防重入
8. `DispatchReplayTool`（放 `src/test`）：历史回放调参工具
9. 04 文档 §2.2 的 `assign` / `reassign` / `suggest` / `run-now`

**关键约束**
- 所有权重从 `DeliveryConfigService` 读，**不许硬编码**。
- 疲劳停派是硬门禁，`force=true` 也不能绕过。
- 每次派单必须输出完整 breakdown 写入 `detail_json`，这是可解释性的载体。
- 依赖 A4 的 `RouteOptimizer` 计算 `addedDistance`。**并行开发时先按接口写，A4 未完成时用一个返回 Haversine 的临时桩**，联调时替换。

**测试**：给定固定骑手/任务集合，评分结果可预期；疲劳骑手被排除；冻品违规被标记；改派条件矩阵。

### A4 · 后端路径与 ETA

**交付物**（严格照 05 文档 §5、§6）
1. `DistanceMatrixProvider` 接口 + `HaversineMatrixProvider`（默认）+ `AmapMatrixProvider`
2. `MatrixCacheService`：坐标网格量化 + `distance_matrix_cache` 读写
3. `RouteOptimizer` 接口 + `ExhaustiveOptimizer`（≤8 点精确）+ `GreedyTwoOptOptimizer`（>8 点）
4. 目标函数：时长 + 超时二次惩罚 + 冷链二次惩罚 + 过早惩罚
5. 同门牌/同楼栋强制相邻的硬约束
6. `RoutePlanService`：规划、写 `route_plan`、重规划触发
7. `EtaEngine`：`max(模型, 三个保护时间)` + 场景补时 + **级联补时**
8. `BuildingHandoffLearner`：每晚聚合 `building_handoff_stat`，p70 取值，分桶
9. `GeoUtils`：Haversine、网格量化、折线编码
10. 04 文档 §1.3（`waves/{id}/route`）、§2.3（replan）

**关键约束**
- `eta.ebike_speed_kmh` 上限 15，代码里要有断言。
- 无高德 Key 时全链路必须能跑通，这是硬要求。
- 求解要有超时保护（`routing.solve_timeout_millis`）。
- `JspritOptimizer` 只留接口不实现（需要 JDK 21），用 `@ConditionalOnProperty` 挡住并抛明确异常。

**测试**：8 点暴力枚举结果 = 已知最优解（构造一个人工可验证的算例）；2-opt 不会让目标函数变差；冻品排最后会被惩罚淘汰；缓存命中；楼栋分桶统计正确；级联补时正确传播。

### A5 · 后端轨迹与实时

**交付物**
1. `LocationIngestService`：批量接收、`INSERT IGNORE` 幂等、更新 `rider_location_latest`、动态下发采样间隔与 commands
2. 拒收校验：未上班、未同意定位（调 A1 提供的方法）、精度过差、GPS 漂移异常点
   （超 `store.gps_sanity_radius_meters` 200 km，这是数据清洗不是业务范围限制）
3. `TrackCleaner`：异常点剔除 + 卡尔曼平滑
4. `LocationQueryService`：最新位置、历史轨迹（降采样至 ≤1000 点）
5. `GeofenceService`：到达围栏识别（80 m + 停留 30 s）→ 自动 `MARK_ARRIVED`
6. `LivenessMonitor`：在岗无上报告警
7. `DeliveryEventStream`：SSE 广播（`task-changed` / `rider-moved` / `exception-raised` / `summary-updated` / `heartbeat`）
8. `DeliveryBoardService`：四列队列聚合
9. `TrackingRetentionJob`：按保留期分批删除（`LIMIT 5000` 循环，不要一次删几十万行）
10. 04 文档 §1.4、§2.1、§三（小程序 tracking，含全部脱敏规则）

**关键约束**
- `/locations/batch` 是全系统最高频接口，要极致简洁：不查复杂关联、不触发级联计算、不写日志。
- 小程序 tracking 的脱敏规则是合规红线，必须逐条实现并有测试。
- SSE 连接要有上限和超时清理，防止连接泄漏。
- 位置写入**绝对不能**触碰 `StorefrontService`。

**测试**：重复批次幂等；未上班拒收；未同意定位拒收；精度过差拒收；终态后 tracking 返回 `rider=null`；越权访问返回 404；围栏触发。

## 5. 跨 Agent 依赖与解耦

| 依赖 | 处理方式 |
| --- | --- |
| A2/A3/A4/A5/A6 → A1 的 Repository | Wave 0 已定稿 `domain` record；各 Agent **按接口写，用内存桩自测**；联调时替换 |
| A3 → A4 的 `RouteOptimizer` | A3 先用「返回 Haversine 直线距离」的桩，A4 完成后替换 |
| A5 → A1 的定位同意校验 | A1 优先交付 `RiderAccountService.isLocationConsentGranted(riderId)` 这一个方法 |
| A8/A9 → A7 的 core 模块 | **A7 必须优先交付 `designsystem` 和 `network` 的接口签名**（哪怕是空实现），A8/A9 才能开工 |
| A10 → 后端接口 | 前端**先用 mock 数据开发**（按 04 文档手写 JSON fixture），后端就绪后切真实接口 |

**降低耦合的关键做法：每个 Agent 都先写「接口 + 空实现 + 测试」，再填实现。** 这样其他 Agent 随时能编译通过。

## 6. 防冲突的硬规则

1. **只改自己独占目录里的文件。** 需要改别人的？停下来报主控。
2. **不创建新的 Flyway 迁移。** 只有 A1 能写迁移文件。
3. **不改 `pom.xml` / `libs.versions.toml` / `package.json`。** 需要新依赖？报主控。
4. **不改 `StorefrontService`。** 一个字都不要动。
5. **不改契约。** 03/04 文档是冻结的，发现问题报主控，主控改文档并广播。
6. 每个 Agent 在**独立分支**开发：`feature/rider-a1-core`、`feature/rider-a2-task`……
7. 提交信息带 Agent 标识：`feat(rider-a3): 实现顺路度评分`
8. 每完成一个可编译的里程碑就提交一次，不要憋大提交。
