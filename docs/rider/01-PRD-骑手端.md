# 骑手端（商家自配送）产品需求文档

## 1. 背景与定位

现有系统是禹邻优鲜的单门店生鲜同城配送：微信小程序下单 → 微信支付 → 管理后台接单备货 → **商家自行配送** → 后台手动点「已完成」。

「商家自行配送」这一段目前是完全的黑盒：谁去送、送到哪一步、什么时候到，系统一无所知，顾客也看不到。本项目就是把这一段补上。

**产品对标不是美团众包，而是盒马 / 朴朴 / 叮咚买菜的前置仓自营配送模式。**这个判断决定了很多设计：

| 维度 | 众包模式（美团/蜂鸟） | 自营模式（盒马/朴朴）← 本项目 |
| --- | --- | --- |
| 接单方式 | 抢单大厅 + 派单 | **系统统一派单，不抢单** |
| 取货点 | 成千上万家商户 | **单一固定门店** |
| 配送范围 | 平台按商圈限制 | **无限制 —— 平台内所有订单都要送** |
| 一趟单量 | 骑手自行控制 | **系统合单，一趟 5–8 单** |
| 骑手关系 | 众包/兼职 | **门店雇员** |
| 超时处罚 | 历史上罚款 | **不罚款，用服务分** |
| 装备 | 骑手自备 | **门店配发生鲜保温箱** |

因为取货点唯一，路径规划问题被极大简化：这是一个**单仓库、多配送点、带时间窗、带容量约束的 VRP**，而不是通用的取送货问题。5–30 个点的规模，服务端毫秒级即可求解。

## 2. 角色

| 角色 | 使用端 | 新增/已有 | 说明 |
| --- | --- | --- | --- |
| 顾客 | 微信小程序 | 已有，需扩展 | 新增：查看骑手实时位置、ETA、联系骑手（隐私号）、配送评价 |
| 骑手 | **Android 骑手端（新建）** | 新增 | 上下班、接收派单、导航、取货、送达、异常上报、查收入 |
| 调度员/店长 | Vue 管理后台 | 已有，需扩展 | 新增：调度看板、手动改派、骑手管理、异常处理、结算 |
| 系统 | —— | 新增 | 自动派单、自动合单、自动规划路线、自动 ETA、自动预警 |

骑手权限分两级：`RIDER`（普通骑手）与 `RIDER_CAPTAIN`（骑手组长，可在 App 内查看全组任务、代为改派）。

## 3. 核心业务流程

### 3.1 主流程（拣货完成即派单）

```
顾客下单支付
   ↓
订单进入「备货中」（现有流程不变）
   ↓
门店拣货、称重、打包 ────► 拍摄电子秤照片（公平秤）
   ↓
后台点击「拣货完成」  ★新增★  ← 这是派单触发点，不是下单时刻
   ↓
系统生成配送任务 delivery_task（PENDING）
   ↓
【智能调度引擎】
   ├─ 压单窗口：等待 0–180 秒，观察是否有可合并的新单
   ├─ 合单：把地理邻近 + 时间窗兼容的任务打包成波次 delivery_wave
   ├─ 评分派单：对每个在岗骑手计算综合得分，选最优
   └─ 路径规划：为波次生成最优配送顺序 + 每段路线 + 每站 ETA
   ↓
推送到骑手 App（JPush 厂商通道 + 应用内轮询兜底 + 语音播报）
   ↓
骑手「接单」（ACCEPTED）→ 到店取货，核对件数（PICKED_UP）
   ↓                              ↓
   ↓                      订单状态同步为「配送中」
   ↓
骑手按规划顺序配送（DELIVERING）
   ├─ App 前台服务持续上报 GPS（10–30 秒自适应）
   ├─ 顾客小程序实时看到骑手位置 + ETA
   └─ 到达围栏自动识别（ARRIVED）
   ↓
逐单送达：核销送达码 / 滑动确认 + 拍照留证（DELIVERED）
   ↓
订单状态同步为「已完成」，生成收入明细
   ↓
波次全部完成 → 骑手返店，接收下一波
```

### 3.2 异常分支

任何环节骑手都可发起**异常上报**，上报后系统自动免责并进入调度员异常队列：

| 异常类型 | 骑手操作 | 系统处理 |
| --- | --- | --- |
| 顾客联系不上 | 上报 + 拨打记录 | 挂起 30 分钟，期间可先送其他单，超时可退回门店 |
| 地址错误/超区 | 上报 + 定位对比 | 通知调度员，调度员联系顾客改址或退回 |
| 顾客拒收 | 上报 + 拍照 | 生成退回任务，商品回店，不计骑手责任 |
| 商品破损/漏液 | 上报 + 拍照 | 进入售后队列，可直接触发退款流程 |
| 缺斤少两争议 | 调取拣货电子秤照片 | 差额超阈值自动退差价，边界值转人工 |
| 门禁进不去 | 上报 | 计入该楼栋交付难度，ETA 自动补时 |
| 车辆故障/身体不适 | 上报 | 该骑手剩余任务自动触发改派 |
| 天气恶劣 | 系统自动识别 | 全局 ETA 补时 + 补贴规则生效 |

### 4.2 服务端调度中枢

#### 任务与生命周期
- `P0` 配送任务 CRUD 与状态机（10 个状态，见 §5）
- `P0` 任务事件流水表（谁在什么时间把任务从什么状态改成什么状态，全量审计）
- `P0` 与现有订单状态的双向同步规则
- `P0` 波次（一趟多单）建模

#### 智能派单
- `P0` **压单策略**：任务生成后进入 0–180 秒可配置的观察窗口，等待可合并单
- `P0` **合单策略**：按地理网格 + 楼栋 groupKey + 时间窗兼容度聚类
- `P0` **评分派单**：多目标加权评分（见 05 文档），选出最优骑手
- `P0` **冷链权重**（本项目独有）：冻品/冷藏品出保温箱时长进入目标函数，拒绝把冻品排在长路线的最后一站
- `P0` 新手保护：试用期骑手降低并发上限、优先派近单
- `P0` 疲劳约束硬门禁：4 小时连续后 20 分钟内不派单
- `P1` **自动改派**：持续评估在途任务超时风险，风险高时评估是否存在更优骑手
- `P1` 运力预警：待派积压 / 在岗骑手不足时告警
- `P2` 第三方运力溢出（预留接口）

#### 路径规划
- `P0` 三层可插拔的距离矩阵提供者：Haversine（零依赖兜底）→ 高德距离测量 → 腾讯距离矩阵
- `P0` 三层可插拔的求解器：贪心 + 2-opt（零依赖兜底）→ jsprit VRPTW → 高德排线调度（付费，预留）
- `P0` **零外部依赖也能跑**：没有高德 Key 时用 Haversine + 2-opt，功能完整只是精度下降。这是硬要求，保证开发和演示不被密钥阻塞
- `P0` 矩阵缓存（门店→客户点的边高度重复，缓存命中率会很高）
- `P0` 重规划：新单加入、骑手偏离、异常发生时重新规划

#### ETA 预估
- `P0` `ETA = max(模型估计, 保护时间A, 保护时间B, 保护时间C)`（对齐美团公开算法，且对骑手更友好）
- `P0` 电动车平均速度上限 **15 km/h**（GB/T 46862-2025 明确要求，不得更快）
- `P0` **楼栋交付时长表**：从真实轨迹学习每个楼栋/楼层的「入客到离客」时长，这是单门店场景最大的精度红利

- `P0` **级联补时**：门店拣货慢时，不仅补该单，还要补受其影响的同波次其他单（GB/T 46862 要求）

## 5. 配送任务状态机（冻结）

**注意**：现有订单状态是中文字符串，保持不变。配送任务是新的关系表，使用英文枚举。两者通过同步规则关联。

| 状态 | 中文名 | 含义 | 触发方 |
| --- | --- | --- | --- |
| `PENDING` | 待分配 | 拣货完成，已生成任务，等待派单 | 后台/系统 |
| `ASSIGNED` | 已派单 | 已分配给骑手，等待骑手接受 | 系统/调度员 |
| `ACCEPTED` | 已接单 | 骑手已确认接受 | 骑手 |
| `PICKED_UP` | 已取货 | 骑手在门店完成取货核对 | 骑手 |
| `DELIVERING` | 配送中 | 骑手已出发 | 骑手/系统 |
| `ARRIVED` | 已到达 | 到达顾客点（围栏自动或手动） | 系统/骑手 |
| `DELIVERED` | 已送达 | 交付完成 | 骑手 |
| `EXCEPTION` | 异常中 | 异常挂起，等待处理 | 骑手/调度员 |
| `RETURNED` | 已退回 | 商品退回门店 | 骑手/调度员 |
| `CANCELLED` | 已取消 | 任务作废 | 调度员/系统 |

### 合法流转

```
PENDING ──► ASSIGNED ──► ACCEPTED ──► PICKED_UP ──► DELIVERING ──► ARRIVED ──► DELIVERED
   ▲            │             │            │              │             │
   │            ▼             ▼            ▼              ▼             ▼
   └──────── (拒接/改派) ────────────────► EXCEPTION ◄──────────────────┘
                │                              │
                ▼                              ├──► DELIVERING  (异常解除，继续送)
            CANCELLED                          ├──► RETURNED    (退回门店)
                                               └──► CANCELLED
```

规则：
- `PENDING → ASSIGNED` 可由系统自动或调度员手动触发。
- 骑手拒接或调度员改派 → 回到 `PENDING`，并在任务上累加 `reassign_count`。
- `EXCEPTION` 是可恢复的挂起态，必须记录 `exception_id` 指向具体异常记录。
- `DELIVERED` / `RETURNED` / `CANCELLED` 是终态。
- 任何流转都必须写入 `delivery_task_event`。

### 与订单状态的同步规则（冻结）

| 配送任务事件 | 订单状态动作 |
| --- | --- |
| 任务创建（PENDING） | 订单必须已是 `备货中`，否则拒绝创建 |
| 任务 → `PICKED_UP` | 订单 → `配送中` |
| 任务 → `DELIVERED` | 订单 → `已完成` |
| 任务 → `RETURNED` | 订单保持 `配送中`，进入人工处理（可能转退款） |
| 任务 → `CANCELLED` | 订单回到 `备货中`，可重新派单 |
| 订单被后台取消 | 关联任务 → `CANCELLED` |

同步方向是**单向的**：配送域调用订单域。订单域不感知配送域，`StorefrontService` 不新增对配送模块的依赖，避免循环依赖和快照写放大。

## 6. 关键业务规则

0. **【最高优先级】平台内所有订单都必须被配送，系统不做任何距离筛选。**
   现有平台本来就没有配送范围（`SettingsDto` 里没有该字段，后端也没有任何距离校验代码），
   顾客可以在任意地址下单。配送域必须与之一致：**只要订单进入「备货中」并完成拣货，
   就一定生成配送任务并最终派出去**，不管它有多远。
   所有涉及距离的配置项都是**软约束**，只影响「怎么派、派给谁、排第几站、给多少钱」，
   绝不影响「派不派」。详见 05 文档 §4.7 与 §4.8。
1. **派单触发点是「拣货完成」，不是「下单」。** 门店拣货慢会导致骑手在店干等，这是自营配送最常见的效率损失。以拣货完成为触发点，实测可以显著降低骑手等待。这是**时序**要求，不是筛选条件。
2. **一个波次最多 8 单、最多 8 km 总里程、最多 60 分钟**（可配置）。超出就**拆波次**，不是拒单。
   **单任务波次豁免里程与时长上限**——一个 15 km 的远单自己独占一个波次，照送。
3. **冻品/冷藏品不排在波次末位。** 任务携带 `cold_chain_level`，路径规划的目标函数里有冷链惩罚项。
4. **同一门牌多单必须合并到同一骑手同一波次。** 现有 `DeliveryAddressIntelligence.sameAddressOrderCount` 已能识别。
5. **超时不罚款。** 只扣服务分，且可通过准时单和培训恢复。这既是 GB/T 46862-2025 的要求，也是自营团队留人的关键。
6. **骑手看不到顾客真实手机号。** 全链路走隐私号；隐私号服务不可用时降级为明文并在后台记录降级事件。
7. **下班即停止定位采集。** 不是隐藏，是真的停止。这是 PIPL 最小必要原则的可审计要求。
8. **顾客只能看到骑手当前位置，看不到历史轨迹**，且订单完成后位置接口立即失效。
