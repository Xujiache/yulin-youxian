# 合规与安全

> 这一份不是「锦上添花」。里面有两项是**上线时间的关键路径**（APP 备案 + 软著），有三项是**代码级红线**（不许扣款、定位单独同意、下班停采集）。请在项目启动第一天就开始处理。

## 1. 关键路径：立即启动的事项

| 事项 | 周期 | 说明 |
| --- | --- | --- |
| **确定 App 中文名** | 立即 | **应用名称、软著名称、APP 备案名称三者必须完全一致。** 定了就不能改，改名要重做软著和备案 |
| **软件著作权登记** | 数周至两个月 | 各大应用商店明确要求先有软著才能上架，不能先上架后补 |
| **APP 备案（移动互联网应用程序备案）** | **20 个工作日** | 依据工信部信管〔2023〕105 号。通过网络接入服务商（阿里云/腾讯云）向省通信管理局提交 |
| **小程序备案** | 同上 | **小程序需要单独备案**，不能因为已有 ICP 备案就跳过 |
| 各厂商推送消息分类审批 | 数天至数周 | 华为/小米/OPPO/vivo 的「服务与通讯」分类，不批就没有响铃权限 |
| 高德企业开发者认证 | 数天 | 个人认证配额 15 万次/月，企业认证 300 万次/月 |

**没有备案号的后果**：责令限期改正 → 责令关闭；未在应用内显著展示备案号可处 **5000–50000 元罚款**。备案号必须在 App 的「关于」页显著展示，且**可点击跳转**至工信部备案系统。

## 2. GB/T 46862-2025《外卖平台服务管理基本要求》

2025-12-02 发布并实施，中国第一部外卖平台服务管理国家标准。虽然是推荐性标准（GB/T）且面向「平台」，但美团和淘宝闪购（饿了么）都已公开宣布采纳，它已成为事实上的行业基准。**一旦发生纠纷，这就是监管和法院会拿来对照的尺子。**

单门店自配送在字面上不是「外卖平台」，但我们自建了派单算法和时限计算——正是该标准规范的行为。**建议按标准设计，合规成本极低，不合规的代价不对称。**

### 已在系统设计中落实的条款

| 条款 | 要求 | 落实位置 |
| --- | --- | --- |
| 7.4.1 a) | 每日接单时长原则上不超过 8 小时；到点提示是否继续；骑手自行确认后可合理延长 | `rider_shift.fatigue_8h_confirmed_at` + App 模态弹窗，确认动作留证 |
| 7.4.1 b) | 连续 4 小时疲劳提示；**20 分钟内停止派单** | `rider_shift.dispatch_paused_until` + 派单引擎硬门禁 |
| 算法 | 时限计算按**电动自行车平均速度 ≤ 15 km/h** | `delivery_config.eta.ebike_speed_kmh = 15`，`max_value` 锁 15 |
| 算法 | 考虑路况、天气、**爬楼时间** | 场景补时 + `building_handoff_stat` 楼栋交付时长学习 |

| 7.2.7 | 法定节假日、恶劣天气、夜间配送**必须有补贴** | 收入规则引擎的三项补贴，非可选 |
| 7.2.2 | 计价规则以通俗易懂的方式向骑手公布 | 每条收入明细带 `calc_detail` 可读说明 |

| 8.4 | 个人信息保护 | 见 §3 |
| —— | 公开派单算法并听取骑手意见 | 派单 breakdown 可解释 + 后台可查 |
| —— | 不得强制购买指定装备或增值服务 | 系统内无任何强制购买 |

### 代码级红线

**系统里不能出现任何对骑手扣钱的逻辑。** 超时、差评、异常，全部只影响服务分，且服务分可恢复。代码评审时会专门 grep 检查。

## 3. 个人信息保护法（PIPL）

### 骑手位置属于敏感个人信息

《个人信息保护法》第 29 条：处理敏感个人信息应取得**单独同意**。第 6 条：处理目的明确合理、与目的直接相关、采取**对个人权益影响最小**的方式、限于**最小范围**。

「单独同意」在实践中的含义很明确：**不能捆绑在隐私政策或劳动合同的一个勾选框里**，必须是一次独立的、显著的、专门针对位置信息的授权交互。

### 系统落实

| 要求 | 落实 |
| --- | --- |
| 单独同意 | **独立的授权页面**（`location_consent` 路由），不与隐私政策合并；调 `POST /api/rider/auth/location-consent` |
| 同意留证 | `rider.location_consent_at` + `location_consent_version`，可审计 |
| **未同意即禁止采集** | `LocationIngestService` 硬校验，`location_consent_at` 为空直接拒收（错误码 `1004`） |
| **最小时段** | 采集**严格限于上班期间**。「下班」是真的停止采集，不是隐藏。休息日、非工作时段零采集 |
| 最小频率 | 自适应采样：静止 60 s / 步行 20 s / 骑行 10 s。静止时降频既省电又是最小必要的合规论据 |
| 最小精度 | 只采集业务必需的坐标，不采集通讯录、相册、应用列表等无关信息 |
| 保留期 | `tracking.retention_days` 默认 90 天，到期自动分批删除 |
| 撤回权 | 授权页可随时关闭，关闭后服务端清空 `location_consent_at` 并停止接收 |
| 加密与访问控制 | HTTPS 传输；只有管理后台登录用户可查历史轨迹；顾客侧只能看当前点 |

### 顾客地址与手机号的最小化

| 要求 | 落实 |
| --- | --- |
| 骑手看不到真实手机号 | 全链路隐私号（阿里云 AXB）；服务不可用时降级为明文并记录 `DEGRADED` 状态供审计 |
| 渐进式披露 | 取货前只显示小区/楼栋，取货后才显示完整门牌 |
| 送达后隐藏 | 任务终态后 App 端不再展示顾客联系方式和详细地址 |
| 顾客侧最小化 | tracking 接口只返回骑手**当前**位置，不返回任何历史轨迹；订单终态后 `rider` 字段整体为 `null` |
| 骑手身份脱敏 | 顾客只看到「张师傅」，不看到全名、工号、手机号 |

### 隐私政策与告知

App 首次启动必须展示隐私政策，明确列出：收集哪些信息、为什么收集、保留多久、如何撤回、如何投诉。这是 GB/T 41391-2022《App 收集个人信息基本要求》的要求。

## 4. 骑手劳动权益与保险

### 现状（2026 年 8 月）

**新就业形态人员职业伤害保障已于 2026-07-01 全国推开**（人社部发〔2025〕24 号，覆盖 31 省 + 兵团），按日参保、按单计费、月度缴费，**平台全额缴纳，骑手不缴**。即时配送的基准费率约 0.07 或 0.25 元/单。2026 年 7 月新纳入的平台包括小象超市、盒马鲜生——**即时零售已明确在范围内**。

**但这个制度覆盖的是「以平台企业名义接单」的人员。** 单门店自有骑手基本不可能被认定为覆盖对象。

### 单门店自配送的正确做法

1. **把劳动关系做清楚。** 签正式劳动合同，依法缴纳社保**含工伤保险**。这是最干净的路径，能规避「劳动关系不清导致保险拒赔」这个最大的坑。
2. **在此基础上加买雇主责任险。**
3. **另外买非机动车第三者责任险**（骑手撞伤路人时直接赔付第三方）。
4. **绝不能用意外险替代工伤保险。**

第 4 点尤其重要。北京四中院法官厉莉的公开分析指出：**雇主责任险是财产（责任）保险，标的是雇主自身的赔偿责任；意外伤害险是人身保险，标的是劳动者的生命健康。二者性质完全不同。** 企业常见的错误是「我买了意外险，所以不承担雇主责任」——法院不支持这种主张。

司法实践还表明：骑手一般**不能直接起诉雇主责任险的保险公司**（骑手不是合同当事人），需要先确定雇主的赔偿责任。劳动关系模糊时，保险利益可能存在瑕疵，保险公司可以拒赔。

5. **不得强制骑手购买指定保险或装备**（GB/T 46862 明确禁止）。

## 5. 电动自行车（GB 17761-2024）

新国标已于 2025-09-01 起对生产实施，2025-12-01 起禁止销售不符合的车辆。

关键参数：
- **最高车速 ≤ 25 km/h，且超速时电机必须自动断电**
- 防篡改：电池、控制器、**限速器**三码绑定，限速器不可修改
- **随车必须配备 3C 认证的电动自行车头盔**
- 已购车辆不强制淘汰

对本项目的影响：
1. ETA 绝不能隐含超过 25 km/h 的假设。GB/T 46862 的 15 km/h 平均速度远低于这个上限，用它就安全。
2. **上班检查清单里加入头盔确认**（`rider_shift.helmet_confirmed`）。
3. 若统一采购车辆，买新国标车并登记车架号/车牌到 `rider.vehicle_plate`。
4. 部分城市（如北京）要求配送用电动车悬挂**专用号牌**，需核实本地规定。
5. 可考虑后续增加超速检测告警（有人大代表公开建议平台增加速度监测并对多次超速限制接单，这是可能的监管方向）。

## 6. 健康证

**各地规定不一致，且正在分化：**

- **四川（2025 年 5 月）** 明确骑手**不需要**健康证，依据是《网络餐饮服务食品安全监督管理办法》第 19 条（食品应封装，骑手不直接接触）+ 食安封签的推广。四川已停止为骑手提供该项体检。
- **无锡（2026 年 6 月）** 的适用范围明确包含「加工、包装、**配送**人员」，需年检、有效期 1 年。
- 南京设有面向外卖骑手的专门办理通道。

**对生鲜门店的判断**：**拣货和打包人员在任何解读下都必然需要健康证**（直接接触未包装的生鲜）。骑手是否需要，**必须咨询本地卫健委**。

系统设计：`rider.health_cert_no` + `health_cert_expire_at`，到期前 30 天提醒，是否作为上班硬门禁由 `delivery_config` 开关控制（默认非强制，便于适配不同地区）。

## 7. 生鲜配送标准的空白

需要明确知道的一点：**GB/T 42500-2023《即时配送服务规范》在适用范围里明确排除了「生鲜末端配送」**，而且**没有专门针对生鲜末端配送的国家标准**。

这意味着我们处在无标准区，**必须自己写一份内部服务规范（SOP）**。建议照 GB/T 42500 的结构写：基本要求（平台侧/配送员侧）→ 服务流程（订单创建·响应·分配·履行·完成）→ 服务设备（车辆·配送箱·头盔）→ 服务评价与改进。

冷链方面可参考北京《食品冷链宅配服务规范》的做法：
- 使用冷藏/保温箱运输，**装载前预冷**
- 温度分区：冷冻 ≤ −18 ℃ / 冷鲜 0–4 ℃ / 冷藏 2–8 ℃ / 常温 10–20 ℃
- 末端：配送前与消费者确认时间；**提醒消费者当面查验**；退货需保持同等冷链条件
- 每次配送后清洁消毒配送箱

系统对应：`cold_chain_level` 字段 + 路径规划的冷链惩罚项 + 骑手端的冷链高亮提示。

**注意**：网上流传的《2026 年生鲜电商服务规范》在国家标准数据库中查无此标准，**疑为内容农场伪造，不要引用**。

## 8. 系统安全

### 现有系统的安全债（本项目不修复，但要知道）

| 问题 | 现状 | 本项目的态度 |
| --- | --- | --- |
| 管理员密码明文存配置 | `ADMIN_PASSWORD` 默认 `Admin@123456` | 不改，但骑手密码**必须** BCrypt |
| 会话存内存、无过期 | 重启即失效，令牌永不过期 | 骑手会话用**持久化 + 双令牌 + 过期**，不沿用 |
| 无速率限制 | 任何接口都能无限调 | 骑手登录和位置上报**必须**加简单限流 |
| CORS 允许所有来源 | `/api/**` 全开 | 不改（改动影响面大），但新接口不放宽 |
| 微信支付私钥在仓库里 | `server/secrets/wechat-pay/*.pem` 实际存在于工作区 | **应告知客户轮换密钥**，虽不属本项目范围 |

### 配送域必须做到的

| 项 | 要求 |
| --- | --- |
| 骑手密码 | BCrypt（若依赖不可用，用 PBKDF2WithHmacSHA256，迭代 ≥ 120000） |
| 令牌 | 32 字节随机 + `rider_` 前缀；access 30 天滑动，refresh 90 天；支持服务端强制撤销 |
| 越权防护 | 骑手只能操作分配给自己的任务（校验 `task.rider_id == currentRiderId`，否则 `1012`）；顾客只能查自己的订单 |
| 限流 | 登录接口按手机号 5 次/分钟；位置上报按骑手 20 次/分钟 |
| 上传校验 | 只接受 jpg/png/webp；校验文件头魔数不只看扩展名；≤5 MB；文件名重命名为 UUID |
| 图片水印 | 时间 + 坐标 + 任务号，防止照片被复用 |
| SQL 注入 | 全部用 `JdbcTemplate` 参数化查询，**禁止字符串拼接 SQL**（尤其是动态排序字段，要用白名单） |
| 审计 | 所有状态流转、改派、人工加减分、配置变更都写事件表，记录操作人 |
| 日志脱敏 | 日志里不得出现完整手机号、坐标、令牌 |
| 设备绑定 | 一个骑手同时只允许一个活跃会话，新登录踢掉旧会话（防账号共享代跑） |
