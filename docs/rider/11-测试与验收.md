# 测试与验收

## 0. 现状与基线

现有项目的测试家底：`server/src/test/java/` 下 8 个 JUnit 5 测试类，跑法是 `cd server && ./mvnw.cmd test`。测试 profile（`src/test/resources/application.yml`）排除了 DataSource/Flyway 自动配置、强制 `persistence.mode: file`，所以**不需要跑 MySQL 就能测**。`MysqlStateStoreTests` 自建 H2 数据源。前端只有 lint，没有测试；没有 CI。

**基线红线：既有 8 个测试类必须始终全绿。** 任何 Agent 的改动导致既有测试失败，都必须立刻修复。

## 2. 各 Agent 必交的测试

### A1 核心与账号
- 27 张表的 Repository 基础 CRUD（H2）
- 密码哈希与校验；弱密码被拒
- 令牌签发、过期、刷新、撤销
- **疲劳阈值三个边界**：3h59m 不提醒 / 4h00m 提醒且停派 20 分钟 / 8h 需确认 / 12h 强制下班
- 未同意定位时 `isLocationConsentGranted` 返回 false
- 配置读取与缓存失效

### A2 任务生命周期
- **状态机全矩阵**：10×10 的流转表，合法的通过、非法的抛 `1011`
- 幂等：同一 `clientEventId` 提交 3 次，只产生 1 条事件、结果一致
- 订单状态同步：`PICKED_UP → 配送中`、`DELIVERED → 已完成`、`CANCELLED → 备货中`
- 订单非 `备货中` 时创建任务被拒（`1013`）
- 同一订单重复创建任务被拒（`1014`）
- 波次任务增删与站点重排

### A3 智能派单
- **【必测】15 km 的远单 + 1 个空闲骑手 → 断言被成功派出**（单任务波次豁免里程上限）
- **【必测】20 km 的冻品远单 → 断言被派出且被排为首站**（冷链是 warning 不是 blocker）
- **【必测】所有骑手都被排除时，任务留在 PENDING 且触发运力预警，不被丢弃**
- 压单窗口动态收缩：剩余 < 15 分钟时窗口为 0
- 分层聚类：同门牌**必定**同簇；同楼栋同簇；超容量拆簇
- 评分：给定固定输入，五个分项和总分可预期
- 疲劳骑手被排除（即使 `force=true` 也不派）
- 满载骑手被排除（`1021`）
- 冻品会化时 `f_冷链 = 0` 且标记 `COLD_CHAIN_VIOLATION`
- 自动改派五个条件的组合矩阵；`reassign_count >= 2` 时不再改派
- 已取货任务不改派
- breakdown 完整写入 `detail_json`

### A4 路径与 ETA
- **暴力枚举正确性**：构造一个 6 点算例，手工算出最优序列，断言算法输出一致
- 2-opt 不会让目标函数变差（单调性）
- 同门牌强制相邻约束生效
- 冻品排最后一站的解被惩罚淘汰
- Haversine 与高德两种 provider 都能产出可用结果
- 矩阵缓存：同一坐标对第二次调用不发起外部请求，`hit_count` 递增
- 坐标网格量化正确（相距 5 m 的两点命中同一缓存）
- ETA = `max(模型, 三个保护时间)`，任一保护时间更大时以它为准
- **`ebike_speed_kmh` 被设为 20 时抛异常或被钳制到 15**
- 楼栋交付时长分桶统计正确；样本 < 5 时回退默认值
- **级联补时**：波次中第 1 站延迟 5 分钟，第 2/3/4 站的 `extra_time_seconds` 都增加 300
- 求解超时保护生效

### A5 轨迹与实时
- 批量上报幂等：同一批次提交两次，`rider_location` 不增加行
- 拒收：未上班 / 未同意定位（`1004`）/ 精度 200 m / 坐标在 100 km 外
- `rider_location_latest` 被正确更新为最新点
- 轨迹清洗：速度 50 m/s 的跳变点被剔除
- 历史轨迹降采样后 ≤ 1000 点
- 围栏：进入 80 m 并停留 30 s 触发 `MARK_ARRIVED`
- **顾客脱敏四条**（每条一个测试）：终态后 `rider = null`、发车前不返回位置、越权 404、短轨迹仅最近清洗点
- SSE 连接建立、收到事件、断开后清理
- 保留期清理任务分批执行，不会一次删过多

### A6 异常结算集成
- 13 种异常类型各自的默认引导文案与 `allowedNextActions`
- 联系不上顾客的 30 分钟挂起与到期处理
- 收入计算七项，含边界：里程 999 m（免计）/ 1001 m、重量 5.0 kg / 5.1 kg、无电梯 1 层 / 6 层
- `calcDetail` 文案可读且数值正确
- 服务分：超时扣 2、准时加 1、异常成立免除超时扣分、20 单准时恢复 5 分
- **grep 断言：`settlement` 和 `score` 包内不存在任何减少骑手金额的路径**
- 公平秤三档：差异 2%（PASS）/ 10%（AUTO_REFUND）/ 5%（MANUAL_REVIEW）
- Noop 实现全部不抛异常且返回合理降级结果
- 隐私号降级时 `status = DEGRADED` 被记录

### A7/A8/A9 Android
- `LocationSampler` 三档切换（构造速度序列断言间隔）
- `TrackCleaner` 跳变点剔除
- `pending_action` FIFO 顺序；同任务失败时阻塞后续；不同任务可并行
- 幂等键唯一约束
- 网络层：`code != 0` 抛业务异常；401 触发刷新；刷新失败跳登录
- `SlideToConfirm`：位移不足不触发；足够位移触发一次（不重复）
- 疲劳 12h 弹窗不可关闭
- 任务卡片关键信息可见（Compose UI Test）
- Room 迁移测试

### A10 前端
- 调度台 SSE 断开后降级轮询
- 页面切换后定时器与 SSE 已释放（切 10 次内存不涨）
- 小程序 `onHide` 停止轮询、终态停止轮询
- 老订单（无经纬度）不白屏
- 地图弹窗层级正确

## 3. 端到端剧本（Wave 2）

每个剧本都要在**真实环境**（真后端 + 真安卓机 + 真小程序 + 真管理后台）走通并录屏。

### 剧本 1 · 单单顺畅流程
1. 小程序下单支付 → 订单 `备货中`
2. 后台「拣货完成」（填件数/重量/冷链，上传电子秤照片）
3. 系统压单 120 秒后自动派单给唯一在岗骑手
4. 骑手手机响铃 + 语音播报 + 全屏弹出
5. 骑手滑动接单 → 到店取货核对 → 出发
6. **小程序上出现地图，骑手图标平滑移动，ETA 显示为区间**
7. 骑手到达（围栏自动识别）→ 拍照 → 滑动送达
8. 订单变 `已完成`，小程序地图消失，评价入口出现
9. 后台可查完整事件时间轴和收入明细

### 剧本 2 · 合单与路径规划
1. 3 分钟内在同一小区不同楼栋下 5 单
2. 后台批量拣货完成
3. 系统合成 1 个波次，规划出配送顺序
4. 骑手 App 显示「1/5、2/5……」，顺序符合楼栋逻辑
5. 骑手手动调整顺序 → 系统接受并重算 ETA，不推翻
6. 全部送达，波次完成，返店时间准确

### 剧本 3 · 远单必送
1. 用一个距门店 15 km 的地址下单（远超默认 3 km 的「远单」标记阈值）
2. 后台拣货完成
3. **系统正常派单**，不出现「超出配送范围」之类的拒绝
4. 该单独占一个波次，不与近单混在一起
5. 调度台上带「远单 15.2 km」标签
6. ETA 按实际距离计算；若赶不上顾客选的时段，标记超时风险但**仍然派送**
7. 骑手收入明细里的里程费按 15 km 计算

### 剧本 4 · 冷链优先
1. 同时下 1 单冻品（远）+ 3 单常温（近）
2. 系统规划的顺序中，**冻品不在最后一站**
3. 骑手 App 上冻品任务有明显的冷链标识和优先提示

### 剧本 5 · 异常处理
1. 骑手到达后上报「顾客联系不上」+ 拍照
2. 系统挂起 30 分钟，骑手可继续送其他单
3. 后台异常队列出现该异常，可查看照片
4. 调度员处理为「退回门店」
5. 任务变 `RETURNED`，骑手服务分未被扣，超时未计入

### 剧本 6 · 自动改派
1. 骑手 A 接了 3 单
2. 模拟骑手 A 位置停滞（不上报）
3. 某单进入 HIGH 风险
4. 系统自动改派给骑手 B
5. 双方都收到消息，改派留痕可在后台查到，A 未被扣分

### 剧本 7 · 断网与离线
1. 骑手进入电梯（关闭网络）
2. 执行「到达」「拍照」「送达」三个动作，UI 立即响应
3. 恢复网络
4. 三个动作按顺序同步成功，**服务端记录的时间是骑手按下按钮的时刻**
5. 位置轨迹补传，无重复点

### 剧本 8 · 保活
1. 骑手上班
2. 锁屏，手机静置 30 分钟
3. 期间位置持续上报，无中断超过 2 分钟
4. **在小米/华为/OPPO/vivo 四台真机上各跑一遍**

### 剧本 9 · 疲劳管控
1. 骑手连续在岗 4 小时（可用配置调小阈值加速测试）
2. 收到提示，20 分钟内不再派单（后台可见「疲劳停派中」）
3. 8 小时时弹出模态确认，可选休息或继续
4. 12 小时强制下班，未完成任务自动改派

### 剧本 10 · 零外部密钥降级
1. 清空高德 Key、极光 Key、隐私号 Key
2. **全部剧本 1–6 仍能走通**（路径用 Haversine、推送用轮询、拨号用明文并提示）
3. 后台能看到隐私号 `DEGRADED` 记录

### 剧本 11 · 备份恢复
1. 产生若干配送数据
2. 后台创建备份
3. 手动改坏一些数据
4. 恢复备份
5. **订单域和配送域数据一致，无错位**

### 剧本 12 · 顾客隐私
1. 用账号 A 的订单 id，以账号 B 的令牌访问 tracking → 404
2. 订单送达后再访问 tracking → `rider` 为 `null`
3. 骑手未发车时访问 tracking → 无 `rider.location` / `recentTrail`

## 4. 性能压测

| 场景 | 目标 | 方法 |
| --- | --- | --- |
| 位置批量上报 | 10 骑手 × 每 20 秒 1 批 × 每批 2 点，P99 < 200 ms | 脚本模拟，持续 1 小时 |
| 顾客 tracking 轮询 | 100 并发 × 5 秒间隔（20 QPS），P99 < 150 ms | —— |
| 调度循环 | 30 待派任务 × 10 骑手，单轮 < 2 秒 | —— |
| 路径规划 | 8 站点精确求解 < 50 ms；20 站点启发式 < 500 ms | 单元基准测试 |
| 调度台看板 | `GET /board` P99 < 500 ms | —— |
| **写放大回归** | **确认位置上报不触发 `StorefrontService.persist()`** | 加断言/日志验证；这是本项目最重要的性能红线 |
| 长跑稳定性 | 连续 24 小时，内存无泄漏，无连接泄漏 | —— |

**最后两项是重点。** 如果有任何代码路径让位置上报触发了全量快照重写，系统会在生产环境崩溃。

## 7. 建议引入的最小 CI

项目目前没有 CI。建议至少加一个 GitHub Actions 工作流跑：`mvnw test` + `npm run build` + `gradlew assembleDebug`。这三条命令能挡掉 80% 的集成事故，配置成本不到半小时。
