# 随机减免与分享触发

## 1. 功能范围

随机减免在待支付订单上运行。符合资格的用户可以：

1. 原价支付，不参加活动；
2. 进入专用活动页，手动点击微信右上角菜单并选择“分享到朋友圈”；
3. 菜单事件被服务端记录后获得一次抽奖资格；
4. 抽中一等奖、二等奖、三等奖或谢谢惠顾；
5. 按服务端锁定后的最终金额本人支付，或生成好友代付链接。

全活动只有一套全局奖池，不再按订单金额划分阶梯。转盘固定四个展示槽位，顺序永远是
`FIRST` / `SECOND` / `THIRD` / `NONE`，对应一等奖、二等奖、三等奖、谢谢惠顾。
四个扇形视觉面积都是 25%，视觉面积不代表中奖概率。

抽奖主体和减免均归订单发起人。好友代付人只能查看付款摘要并支付，不能抽奖或修改结果。

## 2. 微信能力边界

微信小程序不允许页面代码直接拉起朋友圈分享，也不提供“最终发布成功、取消或失败”的回调。
本功能的 `share-trigger` 口径只能确认 `Page.onShareTimeline` 被调用，即用户点击了右上角
“分享到朋友圈”入口，不能证明内容最终发布。不得在产品说明中声称系统能够验证朋友圈最终发布成功。

朋友圈打开活动页时处于场景值 `1154` 的单页模式：

- 没有登录态，不能调用 `wx.login`；
- 不能跳转其他页面；
- 本地存储与普通小程序不共享；
- 页面只读取公开活动展示接口，不读取订单或用户信息。

## 3. 活动配置

管理后台入口：

- `营销中心 / 随机减免`
- `营销中心 / 中奖记录`

单活动配置包含：

- 总开关、开始/结束时间；
- 单用户每日次数；
- 每日现金减免预算（`null` 表示不限预算，不能写成 0）；
- 分享标题、描述和图片地址；
- 四个固定奖项的名义概率，精度 0.01%，保存时总和必须精确等于 100.00%；
- 一等奖、二等奖、三等奖各自独立的减免模式，可以混用。

谢谢惠顾固定为无减免，不能配置任何减免字段。新配置页不再允许创建 GOODS 奖项。
历史 GOODS 流水仍可查询、履约、退款和对账。

金额全部以“分”传输，概率和比例全部以基点传输：`10000` 表示 100.00%。

## 4. 两种减免模式

满减门槛和百分比计算基数都使用抽奖前 `order.payableAmount`，即包含运费、包装费及抽奖前已生效优惠后的最终应付金额。

- `THRESHOLD`：满 X 元减 Y 元。未达门槛时该奖项退出本次候选。保存时要求 `Y < X`。
- `PERCENTAGE`：`floor(应付分 * 比例基点 / 10000)`，再与最大减免金额、`应付 - 1 分` 取最小。
  百分比只做整数向下取整，不使用浮点数或四舍五入。结果不足 1 分时该奖项退出候选。

任何减免后订单至少保留 1 分应付金额。抽奖流水保存实际减免金额 `discountAmount`，
不能只保存比例或满减规则，否则订单、支付、退款和审计无法按历史事实还原。

明确示例：

- 应付 50.00 元，20%，封顶 30.00 元 → 减 10.00 元。
- 应付 50.00 元，20%，封顶 6.00 元 → 减 6.00 元。
- 应付 29.99 元，满 30.00 减 8.00 → 该奖项退出候选。
- 应付 50.00 元，满 30.00 减 8.00 → 减 8.00 元。

## 5. 名义概率与有效概率

后台配置的是名义概率。候选过滤顺序固定：

1. `probabilityBp <= 0`：退出候选。
2. 满减未达门槛或百分比结果为 0：退出候选。
3. 减免项的 `spentToday + actualDiscount > dailyBudgetAmount`：退出候选。
4. 谢谢惠顾只受名义概率影响，不占现金预算。

剩余候选按各自基点重新归一化抽取，不要把退出奖项的概率强行转给谢谢惠顾。
转盘始终显示完整四格，即使某奖项概率为 0、未达门槛或预算不足。
候选为空时返回 `NO_AVAILABLE_PRIZE`，不写 draw、不写 decision、不消费 challenge。

## 6. 服务端锁奖和弱网恢复

客户端不得本地随机开奖结果。必须先收到服务端已经落库的结果，再播放转动动画。

`POST /draw` 按订单幂等：一张订单只能有一条抽奖流水。服务端事务未提交时不得消费 challenge；
服务端已提交但响应丢失时，重复抽奖或查询状态必须返回同一 `drawId`。

网络语义：

- 请求未到服务端或事务失败：资格仍在。
- 服务端已提交但响应丢失：客户端 GET 状态或重试 draw 得到同一结果。
- 客户端只有拿到服务端结果后才开始动画。

可能改价时先关闭旧微信预支付单，再进入抽奖事务。锁顺序仍为用户每日护栏，再锁预算护栏。
写 draw、应用订单促销、写 decision、消费 challenge 必须在同一成功路径。

概率和减免配置只允许管理端读取；公开接口不下发概率。

## 7. 金额、支付和好友代付

现金结果直接写入订单促销投影并降低 `payableAmount`。微信下单、支付回调金额校验、可退金额和退款
总额全部继续以 `payableAmount` 为唯一锚点。

应用现金减免前会关闭旧微信预支付单并轮换 `out_trade_no`，避免旧金额支付成功后无法确认订单。
同一订单存在有效好友代付链接时禁止抽奖；生成代付链接前会把订单决策锁定为“已抽取”或“已跳过”。

代付摘要展示商品金额、配送费、包装费、随机减免和最终支付金额，但不暴露收货地址、订单状态和配送进度。

## 8. 历史 GOODS 兼容

旧 GOODS 奖项和旧抽奖流水必须继续可查询、履约、退款和对账。新配置页不再允许创建 GOODS。
保存活动时不得删除 `pool_code IS NULL` 或 `prize_code IS NULL` 的 legacy 行。

历史实物中奖时仍可能同时预留营销库存和 Storefront 实际库存。待支付订单超时关闭时释放赠品库存；
重启支付时重新预留并保留原抽奖结果。全额退款发生在履约前时撤销赠品；已经随单送达的赠品不追缴。

## 9. 数据与一致性

Flyway `V10` / `V13` 不得修改。固定四奖项与双减免模式由 `V21__fixed_four_prize_lottery.sql` 新增。
生产迁移保持活动开关、时段、预算、每日次数和分享配置不变，并把四项初始概率写成 `0% / 0% / 0% / 100%`。

抽奖流水和库存使用关系表；`application_state` 的 storefront 快照只保存按订单索引的最终促销投影。
关系表先写 `RESERVED`，Storefront 应用成功后改为 `APPLIED`，失败则补偿库存并作废。
定时一致性检查会修复缺失投影，或清理无法应用的保留流水。

## 10. 上线检查

1. 备份 MySQL 抽奖相关表和 `application_state` / Storefront 快照。
2. 构建并部署后端，执行 V21。
3. 验证活动仍开启，活动时间、预算、每日次数和分享配置未变。
4. 验证四项初始概率为 `0 / 0 / 0 / 100%`，抽奖只会谢谢惠顾。
5. 部署管理后台，填写正式概率和每个奖项的模式/参数；保存前再次核对总和 100.00%。
6. 用测试订单验证满减、百分比、封顶、预算和弱网恢复。
7. 小程序代码只准备并验证，由运营在微信开发者工具上传、审核和发布。
8. 分别真机验证 Android 和 iOS 的朋友圈菜单、取消分享、切后台、弱网恢复和场景值 `1154`。
