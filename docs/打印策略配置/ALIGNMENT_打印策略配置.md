## 智能决策与疑问澄清

### 决策 1：手动批量打印的触发场景

**场景分析**：
1. **自动打印关闭时**：所有已支付订单需要手动触发打印
2. **打印失败补救**：某些订单自动打印失败，需批量补打
3. **历史订单补打**：之前未打印的旧订单需要批量补打

**决策**：
- 目标用户群：已支付（PAID 状态）但没有成功打印任务的订单
- 筛选逻辑：`status = PAID` 且 `printJobStatus != SUCCESS`

### 决策 2：批量打印的实现位置

**方案 A**：在现有"订单管理"页面增加批量打印功能
- ✅ 符合用户工作流（查看订单 → 选择 → 打印）
- ✅ 复用现有订单列表和筛选逻辑
- ❌ 需要修改订单模型，增加打印状态字段

**方案 B**：创建独立的"待打印队列"页面
- ✅ 职责分离，不影响订单管理
- ✅ 可以专注于打印状态和操作
- ❌ 增加一个新页面，用户需要切换

**采用方案**：**方案 A**（在订单管理页面增加批量打印）
- 理由：生鲜配送场景下，打印是订单处理的一部分，集成在订单管理更符合业务流程

### 决策 3：打印状态的数据关联

**现状分析**：
- 后端 `OrderDetail` 模型没有打印状态字段
- 打印任务通过 `orderId` 关联到订单
- `PrintJobService` 维护独立的打印任务队列

**实现方案**：
1. **后端增强**：
   - 在 `OrderDto` / `AdminOrderDto` 增加 `printStatus` 字段
   - 查询订单时关联查询打印任务状态
   
2. **前端增强**：
   - 订单列表显示打印状态列
   - 支持批量选择并提交打印

### 决策 4：批量打印接口设计

**接口设计**：
```java
POST /api/admin/printing/orders/batch
Request Body: {
  orderIds: [1, 2, 3, ...]
}
Response: {
  success: 3,
  failed: 0,
  jobs: [PrintJobDto, ...]
}
```

**业务逻辑**：
- 检查订单是否已支付（`status = PAID`）
- 避免重复创建：如果订单已有 `SUCCESS` 状态的打印任务，跳过
- 对每个有效订单调用 `enqueuePaidOrder` 创建任务

## 待确认问题（需用户决策）

### 问题 1：批量打印时是否需要订单状态过滤？

**选项 A**：仅允许已支付（PAID）订单打印
- 优点：符合业务逻辑，避免误操作
- 缺点：限制了灵活性

**选项 B**：允许任意状态订单打印（包括未支付、已取消）
- 优点：灵活，管理员可自行判断
- 缺点：可能打印无效订单

**推荐**：**选项 A**（仅已支付订单）

---

### 问题 2：批量打印功能是否需要额外的权限控制？

**选项 A**：复用现有 `/api/admin/*` 管理员认证
- 优点：简单，与现有系统一致
- 缺点：所有管理员都有批量打印权限

**选项 B**：增加独立的打印权限标识
- 优点：更精细的权限控制
- 缺点：需要扩展权限系统

**推荐**：**选项 A**（复用现有认证）
- 理由：项目暂无细粒度权限系统，管理员默认拥有所有操作权限

---

### 问题 3：打印状态在订单列表中的显示方式？

**选项 A**：新增独立的"打印状态"列
```
订单号 | 状态 | 打印状态 | 金额 | 时间 | 操作
```
- 优点：信息清晰
- 缺点：列太多可能显得拥挤

**选项 B**：在订单状态中合并显示（如标签/图标）
```
订单号 | 状态（含打印标签） | 金额 | 时间 | 操作
```
- 优点：节省空间
- 缺点：信息密度高

**推荐**：**选项 A**（独立列）
- 理由：打印状态是关键业务信息，应该显式展示

### 前端约束

- 遵循现有 Vue 3 Composition API 风格
- 复用 `art-lnb-master/src/api/admin.ts` API 请求封装
